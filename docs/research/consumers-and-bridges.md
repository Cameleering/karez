# Consumers and bridges for a Rust database-connectivity core (karez)

Research notes, checked 2026-11-09. Scope: who would consume a high-performance Rust connectivity core, through which FFI bridges, what those bridges cost, which precedents exist, and which "driver export" (JDBC / ODBC / ADBC / Flight SQL) reaches the most tools per unit of work. Every number is tagged [vendor] (the project or company whose product is measured), [third party] (independent measurement or report), and [checked 2026-11-09] (date I read the page). Where a page could not be fetched I say so rather than guess.

Tool-availability note: WebSearch + WebFetch were used throughout. Three primary pages refused automated fetch (voltrondata.com DNS failure; duckdb.org Java installation page 404; oracle.com/legal/trademarks 403) — their content is reported only to the extent it surfaced in search snippets or mirrors, and flagged as such.

## Q1. Java: native-backed (Type 2) JDBC drivers, JNI vs FFM, Arrow C Data, and "faster than pgJDBC"

### Takeaway
A Rust core behind a JDBC facade is well precedented (sqlite-jdbc, DuckDB JDBC, Oracle OCI, Snowflake's Arrow result format); FFM (final in Java 22, JEP 454) makes the per-call boundary ~20–35 ns, roughly 10–15 % cheaper than JNI, and the Arrow Java C Data Interface (`arrow-c-data`, still JNI-based) lets a native producer hand whole off-heap batches to Java. The published Java-side evidence that columnar/native transfer beats row-oriented JDBC is strong (ADBC-over-DuckDB vs DuckDB JDBC: 13x faster, 5x less heap [third party]), but I found no direct, published benchmark of any native-backed driver against pgJDBC on PostgreSQL — that comparison would have to be produced.

### Cited Findings

**Type 2 / native-backed JDBC precedents**
- sqlite-jdbc bundles native SQLite builds for Windows, macOS and Linux (glibc and musl), FreeBSD and Android into a single JAR and "is automatically extracted into your OS's temporary folder" at load; it supports GraalVM native-image "out of the box starting from version 3.40.1.0"; latest 3.54.1.0; licence Apache-2.0 (+ BSD-2 component) [vendor][checked 2026-11-09] — [xerial/sqlite-jdbc README](https://github.com/xerial/sqlite-jdbc)
- DuckDB Java client 2.0.0 "implements the main parts of the standard Java Database Connectivity (JDBC) API, version 4.1", adds "Apache Arrow interchange", bulk loading and GraalVM Native Image support; repository licence MIT [vendor][checked 2026-11-09] — [duckdb.org Java overview](https://duckdb.org/docs/2.0/clients/java/overview.html), [duckdb/duckdb-java](https://github.com/duckdb/duckdb-java). The installation page (bundled-platform list) returned HTTP 404 on fetch; platform list not verified.
- DuckDB JDBC exposes `DuckDBResultSet.arrowExportStream(allocator, 256)` returning an `ArrowReader`, and `DuckDBConnection.registerArrowStream(name, ArrowArrayStream)` for ingest, using `org.apache.arrow.c.ArrowArrayStream` and `org.apache.arrow.c.Data` [vendor][checked 2026-11-09] — [duckdb.org result handling](https://duckdb.org/docs/2.0/clients/java/result_handling.html)
- Oracle's JDBC OCI driver "is a Type 2 driver that uses Java native methods to call entrypoints in an underlying C library"; the Thin driver is "pure Java, Type IV"; Oracle recommends OCI only for OCI-dependent features such as Transparent Application Failover [vendor][checked 2026-11-09] — [Oracle 21c JDBC guide, Introducing JDBC](https://docs.oracle.com/en/database/oracle/oracle-database/21/jjdbc/introducing-JDBC.html)
- Snowflake JDBC 3.11.0+ fetches results in Arrow; "Internal tests show an improvement of up to 5x for fetching result sets over these clients" and "up to a 10x improvement if you download directly into a Pandas DataFrame" (blog dated 2020-02-12) [vendor][checked 2026-11-09] — [Snowflake blog](https://www.snowflake.com/blog/fetching-query-results-from-snowflake-just-got-a-lot-faster-with-apache-arrow/)
- Snowflake Spark connector 2.6 (Arrow over JDBC instead of staged CSV/JSON): "4x improvement in the end-to-end performance" attributed to "a 10x performance improvement in the time spent by the Spark Connector to fetch and process the results" [vendor][checked 2026-11-09] — [Snowflake Spark 2.6 announcement](https://www.snowflake.com/wp-content/uploads/2020/04/SnowflakeConnectorforSparkVersion2.6Turbochar.html)
- Arrow Flight SQL JDBC driver (Arrow 10.0.0, software grant from Dremio) "adapts the Arrow result set to the JDBC interface"; the blog notes JDBC's row-oriented API is the opposite of Arrow's columnar layout and gives no benchmark [vendor][checked 2026-11-09] — [arrow.apache.org blog 2022-11-01](https://arrow.apache.org/blog/2022/11/01/arrow-flight-sql-jdbc/)
- Dremio marks its legacy JDBC driver end-of-life ("will not be updated or fixed moving forward") in favour of the Flight SQL JDBC driver, which returns native List/Map/Struct types but "does not support the setDate() method" [vendor][checked 2026-11-09] — [Dremio docs](https://docs.dremio.com/cloud/sonar/client-apps/drivers/arrow-flight-sql-jdbc). Dremio marketing claimed Flight is "100x-1000x" faster than JDBC/ODBC; a user in Dremio's own forum reported "Arrow Flight and JDBC have similar performance" in their test — unresolved [vendor claim, third-party counter-report][checked 2026-11-09] — [Dremio community thread](https://community.dremio.com/t/jdbc-vs-arrow-flight-for-java/7158)
- ADBC JDBC Adapter (`org.apache.arrow.adbc:adbc-driver-jdbc`, status Beta, ADBC spec 1.0.0) wraps any JDBC driver behind the Java ADBC API — the reverse direction of what rdbc wants, but shows the Arrow<->JDBC adaptation code exists in the Arrow Java tree [vendor][checked 2026-11-09] — [ADBC JDBC driver docs](https://arrow.apache.org/adbc/current/driver/jdbc.html)

**Measured Java-side gains from columnar native transfer**
- Columnar (Ian Cook, David Li), 2025-11-14, M3 MacBook Air 16 GB, `SELECT *` on TPC-H SF1 lineitem (6,001,215 rows), both paths over DuckDB: JDBC CachedRowSet 16,315.58 ms and 5,196 MB JVM heap; ADBC `List<ArrowRecordBatch>` 1,261.18 ms, 139 MB heap + 1,000 MB Arrow allocator — "about 13x faster", "about 5x less memory" [third party (Columnar is the ADBC maintainers' company; treat as vendor-adjacent)][checked 2026-11-09] — [columnar.tech/blog/adbc-java](https://columnar.tech/blog/adbc-java/)
- ADBC 21 (announcement 2025-11-07) ships "JNI bindings to the C++ driver manager" (Java 0.21.0) with prebuilt binaries for amd64/arm64 Linux, arm64 macOS, amd64 Windows; "does not yet bind every ADBC function" [vendor][checked 2026-11-09] — [ADBC 21 release](https://arrow.apache.org/blog/2025/11/07/adbc-21-release/)

**JNI vs FFM per-call overhead**
- JEP 454 (FFM API) is "Closed / Delivered" in Java 22; goal: "overhead comparable to, if not better than, JNI and sun.misc.Unsafe"; restricted methods warn by default and "will be blocked in a future release unless native access is enabled" (`--enable-native-access` or `Enable-Native-Access` manifest attribute); Java 22 added "a linker option for passing heap segments to downcall handles"; automatic arenas free memory when "the JVM's garbage collector detects that the memory segment is unreachable"; "Part of the FFM API, however, is inherently unsafe" [vendor][checked 2026-11-09] — [openjdk.org/jeps/454](https://openjdk.org/jeps/454)
- Lemire, 2026-01-17, MacBook M4: Java->C downcall via FFM 22.7 ns per query; with `Linker.Option.critical` 19.5 ns; pure Java 2.5 ns; "about 20 ns per C function calls from Java"; JNI not measured [third party][checked 2026-11-09] — [lemire.me](https://lemire.me/blog/2026/01/17/a-new-way-to-call-c-from-java-how-fast-is-it/)
- SoftwareMill JMH: JNI 34.7 ns/op, Panama `invokeExact` 29.5 ns/op, Panama with type conversion 34.3 ns/op (~15 % gain, erased by argument conversion) [third party][checked 2026-11-09] — [softwaremill.com/welcome-to-panama](https://softwaremill.com/welcome-to-panama/)
- Java Code Geeks (citing zakgof/java-native-benchmark): FFM "outperforms raw JNI by ~12%" on call-only path; not caching the downcall handle adds "hundreds of nanoseconds" per invocation [third party][checked 2026-11-09] — [javacodegeeks](https://www.javacodegeeks.com/?p=142209)
- Inside.java (Minborg, 2023-08): FFM string handling in Java 22 is "massively" faster than earlier previews (see page for figures) [vendor][checked 2026-11-09] — [inside.java](https://inside.java/2023/08/29/ffm-strings-performance)

**Arrow Java C Data Interface**
- `arrow-c-data` is the "Java implementation of C Data Interface - JNI"; `org.apache.arrow.c.Data` exposes `exportVector/importVector`, `exportVectorSchemaRoot/importVectorSchemaRoot`, `exportArrayStream/importArrayStream`; on import "the ArrowArray struct has its contents moved (as per the C data interface specification) to a private object held alive by the resulting array"; build requires CMake 3.11+ and a C++17 compiler for the JNI shim [vendor][checked 2026-11-09] — [arrow.apache.org/docs/java/cdata.html](https://arrow.apache.org/docs/java/cdata.html), [arrow-java c/README](https://apache.googlesource.com/arrow-java/+show/refs/heads/main/c/README.md)
- I found no apache/arrow-java issue or release note announcing an FFM/Panama port of `arrow-c-data`; the only hit was a 2022 PR comment that the new API "lets us optionally use the garbage collector for managing memory" [vendor][checked 2026-11-09] — [PR #14066 comment](https://mail-archive.com/github@arrow.apache.org/msg139044.html)

**pgJDBC comparisons**
- No rows-per-second benchmark of pgJDBC vs vertx-pg-client vs R2DBC was found; a Habr commenter ranked vertx-pg fastest and R2DBC slowest with pools; vertx-pg-client README claims "#1 in TechEmpower Round 15 single-query" [third party / vendor][checked 2026-11-09] — [r2dbc-postgresql discussion #607](https://github.com/pgjdbc/r2dbc-postgresql/discussions/607), [vietj/vertx-pg-client](https://github.com/vietj/vertx-pg-client)

### Inferences
- The per-call boundary (~20–35 ns) is irrelevant for a connector if the design moves *batches*, not cells: one FFM downcall per Arrow batch of thousands of rows amortises to sub-nanosecond per cell. The JDBC facade's cost will be dominated by `ResultSet.getXxx()` row/column accessors reading from off-heap `MemorySegment`s, not by FFM.
- The Columnar measurement (13x, 5x less heap, same engine both sides) is the closest existing evidence that a native, columnar result path in a JVM beats a conventional JDBC `ResultSet` path; the win is from avoiding per-cell boxing and heap copies, which a Rust core delivering Arrow batches to FFM `MemorySegment`s would also avoid.
- "Faster than pgJDBC" is plausible for bulk reads (pgJDBC materialises rows as `byte[][]` and boxes on access) but unproven; expect parity or loss on small OLTP round-trips where network latency dominates and the JNI/FFM transition plus Arrow batch framing adds fixed cost. A credible claim needs a published JMH harness against pgJDBC on identical hardware with TPC-H-style scans *and* 1-row lookups.
- Packaging: sqlite-jdbc and DuckDB show the accepted pattern — one JAR, per-platform `.so/.dll/.dylib` extracted at load — and both already support GraalVM native-image, which a Rust cdylib also fits. Java 22+ requirement for FFM excludes Java 8/11/17 LTS users unless a JNI fallback is kept; `arrow-c-data` itself still requires JNI.
- GC interaction: FFM Arenas (confined/shared/automatic) give deterministic release of native Arrow buffers; a JDBC facade should tie an Arena to `ResultSet.close()`.

### Gaps
- No published head-to-head of any native/Arrow JDBC driver against pgJDBC on PostgreSQL.
- Exact per-platform list bundled in the DuckDB Java JAR not verified (page 404).
- No quantified JNI pinning / GC cost figures for bulk transfer; JEP 454 does not discuss pinning.
- Whether Arrow Java intends to port `arrow-c-data` from JNI to FFM is unknown.

## Q2. Python: PyO3/maturin, Arrow PyCapsule, DB-API 2.0, precedents, GIL and free-threading

### Takeaway
PyO3 + maturin with abi3 wheels is the standard route (used by Turso, ConnectorX, Polars); the Arrow PyCapsule Interface (`__arrow_c_stream__`) gives zero-copy hand-off to pandas/Polars/pyarrow/DuckDB without a pyarrow dependency; per-call PyO3 overhead is tens of ns and irrelevant for batch APIs. Free-threaded CPython (3.13t/3.14t) is supported by PyO3 since 0.23 and is the default assumption since 0.28, but abi3 does not apply to free-threaded builds, so a separate wheel per Python version is needed for 3.13t/3.14t until abi3t (CPython 3.15) lands.

### Cited Findings
- ConnectorX (Rust, PyO3): "ConnectorX uses up to 3x less memory and 21x less time (3x less memory and 13x less time compared with Pandas)" loading a 10x TPC-H lineitem (8.6 GB) from Postgres with 4 cores [vendor][checked 2026-11-09] — [sfu-db/connector-x README](https://cdn.jsdelivr.net/gh/sfu-db/connector-x@main/README.md); VLDB 2022 paper: pandas 12.46 min / 95.6 GB peak vs ConnectorX 0.97 min / 31.4 GB on 7.2 GB lineitem, and "the main overhead for read_sql comes from the client-side instead of query execution and data transfer" [third party (peer-reviewed, by authors)][checked 2026-11-09] — [VLDB vol15 p2994](https://www.vldb.org/pvldb/vol15/p2994-wang.pdf)
- Polars `read_database_uri` defaults to ConnectorX ("written in Rust and stores data in Arrow format"), ADBC via `engine="adbc"` requires the per-backend `adbc-driver-*` package; `execute_options` parameters work only with ADBC ("connectorx does not support this parameter"); partitioned reads require connectorx>=0.3.1 [vendor][checked 2026-11-09] — [Polars read_database_uri](https://docs.pola.rs/api/python/stable/reference/api/polars.read_database_uri.html), [Polars DB user guide](https://docs.pola.rs/user-guide/io/database/)
- pandas `read_sql` accepts an ADBC connection "where available"; "ADBC support was added in version 2.2.0" [vendor][checked 2026-11-09] — [pandas.read_sql](https://pandas.pydata.org/docs/reference/api/pandas.read_sql.html)
- Arrow PyCapsule Interface: methods `__arrow_c_schema__`, `__arrow_c_array__(requested_schema=None)`, `__arrow_c_stream__(requested_schema=None)` plus device variants; capsule names `"arrow_schema"`, `"arrow_array"`, `"arrow_array_stream"`; "The callee should attempt to provide the data in the requested schema" and must raise if incompatible [vendor][checked 2026-11-09] — [PyCapsule Interface spec](https://arrow.apache.org/docs/format/CDataInterface/PyCapsuleInterface.html)
- pyo3-arrow 0.19.0: "zero-copy FFI conversions" between Python and Rust `arrow` crate types via the PyCapsule interface; helpers `to_stream_pycapsule`, `to_array_pycapsules`, `to_schema_pycapsule`; handles requested-schema negotiation on export [vendor][checked 2026-11-09] — [docs.rs/pyo3-arrow](https://docs.rs/pyo3-arrow)
- PyO3 free-threading guide: "Since PyO3 0.28, PyO3 defaults to assuming Python modules created with it are thread-safe" (0.23–0.27 default was `gil_used = true`); opting out makes the interpreter "re-enable the GIL at runtime while importing your module and print a RuntimeWarning"; "The free-threaded build uses a completely new ABI and there is not yet an equivalent to the limited API" — PyO3 warns and ignores `abi3` when building for free-threaded Python; mutable `#[pyclass]` borrows can raise `RuntimeError: Already borrowed` under concurrency [vendor][checked 2026-11-09] — [pyo3.rs free-threading](https://pyo3.rs/latest/free-threading)
- PyO3 0.23.0–0.23.2 abi3 wheels built by maturin for multiple Python versions were "highly unstable and will crash the Python interpreter"; fixed in 0.23.3 [vendor][checked 2026-11-09] — [PyO3 releases](https://github.com/PyO3/pyo3/releases?page=1)
- CPython 3.15 adds a stable ABI for free-threaded builds ("abi3t"); maturin tests it only through a dev branch of PyO3 [vendor][checked 2026-11-09] — [docs.python.org abi3t migration](https://docs.python.org/ru/3.15/howto/abi3t-migration.html), [maturin bridge source](https://docs.rs/crate/maturin/1.13.3/source/src/bridge/mod.rs)
- ADBC 21 dropped Python 3.9 and "added Python 3.14 (including the free-threaded variant)" [vendor][checked 2026-11-09] — [ADBC 21 release](https://arrow.apache.org/blog/2025/11/07/adbc-21-release/)
- PyO3 call overhead: a maintainer measured a no-op Python function at ~18 ns vs no-op PyO3 function at ~25 ns (issue #3787, older API) [vendor][checked 2026-11-09] — [PyO3 issue 3787](https://github.com/PyO3/pyo3/issues/3787); a 2021 third-party post measured trivial Cython ~30 ns vs plain Python ~62 ns and said PyO3's call overhead was then higher than Cython's [third party][checked 2026-11-09] — [pythonspeed via pycoders](https://pycoders.com/link/6235/web)
- Turso's Python binding is built with PyO3 and "should mirror the sqlite3 DB-API 2 interface"; Node binding `@tursodatabase/database` is a napi-rs addon positioned as a better-sqlite3 drop-in; all bindings call one synchronous Rust core [vendor][checked 2026-11-09] — [limbo py-bindings.mdx mirror](https://git.joshthomas.dev/mirrors/limbo/src/branch/valueref-decouple/bindings/python/py-bindings.mdx), [turso bindings summary (third-party mirror)](https://instagit.com/tursodatabase/turso/turso-language-bindings-operation-go-js-python-java-net.md)
- dbt-postgres installs `psycopg2-binary` by default (pin `>=2.9,<3.0`), i.e. dbt adapters consume a DB-API 2.0 driver, not Arrow [vendor][checked 2026-11-09] — [pypi dbt-postgres](https://pypi.org/project/dbt-postgres)
- Superset "requires a Python DB-API database driver and a SQLAlchemy dialect to be installed for each database engine"; Superset 4.x pins SQLAlchemy 1.4 [vendor][checked 2026-11-09] — [superset.apache.org databases](https://superset.apache.org/user-docs/6.0.0/configuration/databases), [Denodo note on SQLAlchemy 1.4](https://community.denodo.com/docs/html/document/denodoconnects/7.0/Denodo%20Dialect%20for%20SQLAlchemy%20-%20User%20Manual)
- Write-path ADBC vs SQLAlchemy: 2.3x faster at 10 M rows and 2.2x at 40 M rows into PostgreSQL [third party][checked 2026-11-09] — [AliMassoud/ADBC-Driver-with-PostgreSQL](https://github.com/AliMassoud/ADBC-Driver-with-PostgreSQL); dlt: DuckDB->MySQL 5 M rows 344 s (SQLAlchemy rows) vs 92 s (Arrow + ADBC), 3.7x [vendor (dlt)][checked 2026-11-09] — [dlthub blog](https://dlthub.com/blog/arrow-adbc-vs-sqlalchemy)

### Inferences
- Two Python surfaces are needed, not one: (a) an Arrow-native API (`fetch_arrow()` / `__arrow_c_stream__`) for pandas 2.2+, Polars, DuckDB, pyarrow, and (b) a PEP 249 DB-API 2.0 class with a SQLAlchemy dialect, because dbt adapters, Superset, Airflow hooks and most ORMs only speak DB-API. The second is what ConnectorX lacks and why it is used only as a bulk reader.
- Wheel matrix: abi3 covers all GIL builds with one wheel per platform; free-threaded 3.13t and 3.14t each need their own wheel until abi3t (3.15). Budget 3 extra wheels per platform.
- A Rust core that releases the GIL during I/O (and is `gil_used = false`-clean) directly benefits free-threaded Python users, a differentiator over psycopg2/pyodbc-style C extensions that still serialise on the GIL.

### Gaps
- No current (2025–2026) per-call PyO3 vs CPython benchmark; only the 2021 blog and the older issue.
- No direct read-path benchmark of pandas `read_sql` via ADBC vs SQLAlchemy; only write-path and mixed-pipeline figures.

## Q3. Node.js: napi-rs, the Prisma retreat, and N-API Arrow interchange

### Takeaway
napi-rs v3 (July 2025) is the mature path and is what Turso ships; per-call cost is ~tens to ~100 ns, but Prisma's 2025 exit from Rust shows that *per-row serialisation* across the JS/Rust boundary — not the call itself — destroys the benefit when the Rust side returns row-shaped JSON. A connector that returns Arrow buffers (one copy or zero-copy via `ArrayBuffer` externals) avoids exactly the cost Prisma hit.

### Cited Findings
- Prisma, 2025-01-30: moving query engine from Rust to TypeScript because "Contributing to the query engine requires a combination of Rust and TypeScript proficiency", "Each operating system and OpenSSL library version needs its own binary", "Modern JavaScript runtimes, serverless, and edge environments aren't always compatible with large Rust binaries"; with driver adapters "data must be serialized from JavaScript to Rust and then back to JavaScript, reducing efficiency"; bundle ~14 MB (7 MB gz) -> ~1.6 MB (600 KB gz) [vendor][checked 2026-11-09] — [prisma.io blog](https://www.prisma.io/blog/from-rust-to-typescript-a-new-chapter-for-prisma-orm)
- Prisma, 2025-03-03: new TypeScript Query Compiler vs Rust engine — findMany 25,000 records 55.0 ms vs 185.0 ms (3.4x); findMany take 2000 3.1 ms vs 6.6 ms; filters mostly 1.1–1.6x; one case Rust 1.01x faster; explanation: "the cost of serializing data between Rust and TypeScript is very high" and "negates any benefit gained from having our Query Engine in Rust" [vendor][checked 2026-11-09] — [prisma.io performance update](https://www.prisma.io/blog/rust-to-typescript-update-boosting-prisma-orm-performance)
- napi-rs v3 announced 2025-07-07; "WebAssembly" is "the biggest update", compiles to `wasm32-wasip1-threads` with Node and browser loaders; `napi build --use-napi-cross` for cross-compilation [vendor][checked 2026-11-09] — [napi.rs/blog/announce-v3](https://napi.rs/blog/announce-v3), [napi.rs WebAssembly docs](https://napi.rs/docs/concepts/webassembly)
- napi-rs per-call cost: a Medium post (member-only, Node 22.22.0, Linux x86_64, 2 vCPU) reports "roughly 100 ns of overhead per call" and a trivial add function "19x slower" via napi-rs than plain JS [third party, paywalled, not independently verified][checked 2026-11-09] — [levelup.gitconnected.com](https://levelup.gitconnected.com/calling-rust-from-node-with-napi-rs-6x-faster-for-heavy-work-19x-slower-for-tiny-calls-fe0f8828924b); old napi-rs repo benchmark commits show noop ~54.6 M ops/s (napi-rs) vs ~713 M ops/s (JS), i.e. ~18 ns/call [vendor, old][checked 2026-11-09] — [napi-rs commit](https://github-redirect.dependabot.com/napi-rs/napi-rs/commit/0731e00217e67843e11d25860117a1e35615f074)
- Turso's `@tursodatabase/turso` moved to napi v3 and dropped its separate WASM target because "napi v3 can compile to WASM" [vendor][checked 2026-11-09] — [limbo bindings/javascript mirror](https://git.joshthomas.dev/mirrors/limbo/src/commit/a254f0ecaae68e17254b06596ba0f8a2ab3c3aa7/bindings/javascript)
- ADBC has a JavaScript driver manager (docs for ADBC 23 list `ConnectOptions`; short-name fallback goes to `LD_LIBRARY_PATH`/`PATH`) [vendor][checked 2026-11-09] — [ADBC JS driver manager](https://arrow.apache.org/adbc/23/javascript/api/interfaces/types.ConnectOptions.html)

### Inferences
- Prisma's rationale was mostly product-driven (TS-only team, edge/serverless, binary matrix) and its perf losses came from serialising row objects through N-API. A database *driver* has the opposite shape — large, regular, columnar results — where N-API `Buffer`/external `ArrayBuffer` hand-off of Arrow IPC or C-Data pointers moves bytes once. The lesson is: never return `Vec<Row>` of JS objects from Rust; return Arrow and decode lazily in JS (apache-arrow JS) or expose typed-array columns.
- The Node consumer base for a *generic* SQL driver is smaller than Python/Java (ORMs like Prisma/Drizzle/Knex each bind to `pg`/`mysql2`/`better-sqlite3` APIs). Highest leverage: a `better-sqlite3`/`pg`-compatible facade (Turso's strategy) or an ADBC JS driver-manager-loadable library.

### Gaps
- No peer-reviewed or vendor-neutral napi-rs per-call benchmark (the only figure is paywalled).
- No published Arrow-over-N-API throughput numbers for a database driver.

## Q4. .NET, Go, R, Ruby: P/Invoke, cgo, extendr, rb-sys

### Takeaway
.NET P/Invoke with blittable types is cheap (tens of instructions) and well-trodden (DuckDB.NET, ADBC C#); cgo costs ~40–60 ns per call and Go projects actively avoid it (CGO_ENABLED=0 builds, wasm/transpiled SQLite), so the Go route to a Rust core is best served by the ADBC Go driver manager + `database/sql` adapter rather than a bespoke cgo wrapper; R already has `adbcdrivermanager`/`adbi`; Ruby has `red-adbc` and `activerecord-adbc-adapter`. For all four, exporting an ADBC driver reaches them without writing language-specific bindings.

### Cited Findings
- cgo on Go 1.21: trivial cgo call 40 ns/op on 1 core, 4.281 ns/op aggregate across 16 cores; non-inlined empty Go func ~1.5 ns; scales roughly linearly to ~16 cores then contends [third party][checked 2026-11-09] — [shane.ai all-posts](https://github.com/shanemhansen/shane.ai/blob/main/docs/content-org/all-posts.org); Go issue #42469 (Go 1.15 era): ~60 ns per trivial cgo call, ">80%" in scheduler work [vendor][checked 2026-11-09] — [go.dev/issue/42469](https://go.dev/issue/42469)
- Cloud Foundry Stratos release binaries are built with `CGO_ENABLED=0`; `mattn/go-sqlite3` compiled to a runtime-error stub, fixed by switching to `ncruces/go-sqlite3` (SQLite compiled to wasm on wazero) [third party][checked 2026-11-09] — [stratos PR #5662](https://github.com/cloudfoundry/stratos/pull/5662); ncruces: "memory usage will be higher than alternatives because each connection runs in a Wasm sandbox" [vendor][checked 2026-11-09] — [ncruces/go-sqlite3](https://github.com/ncruces/go-sqlite3); modernc.org/sqlite is a machine-translated pure-Go port [third party][checked 2026-11-09] — [HN thread](https://hn.nuxt.dev/item/48434906)
- ADBC Go: "the Go ADBC client library provides an adapter" for `database/sql`; Go driver manager has `drivermgr.LoadFlags*`; ADBC 25 (2026-10-26) split Go core and drivers into separate modules [vendor / third party for the 25 date][checked 2026-11-09] — [ADBC integrations](https://arrow.apache.org/adbc/current/integrations.html), [ADBC 25 upgrade guide (third party)](https://datalakehousehub.com/blog/adbc-25-upgrade-guide/)
- Go validation package: "driver-agnostic test suite intended to aid in driver development" via a `DriverQuirks` interface [vendor][checked 2026-11-09] — [pkg.go.dev adbc/validation](https://pkg.go.dev/github.com/apache/arrow-adbc/go/adbc/validation)
- .NET: Microsoft's older guidance puts P/Invoke at "between 10 and 30 x86 instructions per call" and "no marshaling cost between blittable types"; `SetLastError=true` caused a 4x slowdown in a 2011 test; `Marshal.PtrToStructure` 575.86 ns vs ~64 ns for a UTF-8 read until a stub-caching fix [vendor / third party, dated][checked 2026-11-09] — [MS Learn calling native functions](https://learn.microsoft.com/hu-hu/cpp/dotnet/calling-native-functions-from-managed-code), [dotnet/runtime #45100](https://github.com/dotnet/runtime/issues/45100). ADBC ships C# bindings (C# 0.21.0 in ADBC 21) [vendor][checked 2026-11-09] — [ADBC 21 release](https://arrow.apache.org/blog/2025/11/07/adbc-21-release/)
- R: "R adbi" provides "a DBI compliant interface to ADBC drivers"; `adbcdrivermanager` is "a DBI-compatible backend" for dplyr [vendor][checked 2026-11-09] — [ADBC integrations](https://arrow.apache.org/adbc/current/integrations.html). One R user reported Snowflake ADBC taking ~57 min vs ODBC ~50 s on their largest dataset (cause unknown) [third party][checked 2026-11-09] — [arrow-adbc issue #2508](https://mail-archive.com/issues@arrow.apache.org/msg81060.html)
- Ruby: `activerecord-adbc-adapter` "allows you to use ADBC drivers as Active Record database adapters"; `red-adbc` gem is the Ruby ADBC binding (cited by ClickHouse as the route for Ruby) [vendor][checked 2026-11-09] — [ADBC integrations](https://arrow.apache.org/adbc/current/integrations.html), [ClickHouse ADBC blog](https://clickhouse.com/blog/introducing-the-clickhouse-adbc-driver)

### Inferences
- Go is the one ecosystem where a native core is actively resisted; shipping an ADBC driver and relying on the Go driver manager (which already accepts the cgo cost once per batch) is the only realistic Go story. A pure-Go port is out of scope.
- For .NET, two options exist: DuckDB.NET-style hand-written P/Invoke over the C ABI, or the ADBC C# driver manager. The latter is zero incremental work once an ADBC driver exists.
- R and Ruby come "for free" through ADBC (DBI / ActiveRecord adapters already exist); extendr/rb-sys bespoke bindings are not worth building.

### Gaps
- extendr (R) and rb-sys (Ruby) were not researched beyond the ADBC adapters; no measurements found.
- No modern (.NET 8/9) P/Invoke nanosecond benchmark found.

## Q5. C ABI design for the core (handles, errors, Arrow C Data/Stream, versioning; adbc.h as a model)

### Takeaway
adbc.h is the best available template: an opaque-handle (`private_data`) object model, a version-negotiated function table filled by a single `AdbcDriverInit(version, driver*, error*)` entry point, an error struct that was extended in 1.1.0 without breaking ABI by sentinel `vendor_code`, and results delivered as `ArrowArrayStream`. SQLite and libpq show the payoff of never breaking the exported C surface (libpq has kept SONAME 5 since 8.2 in practice). abi_stable/stabby are for Rust-to-Rust plugin ABIs and are not needed for a `repr(C)` driver surface.

### Cited Findings
- adbc.h: `AdbcDriverInitFunc` is "the common entry point" loaded via "dlopen(3)/LoadLibrary"; parameters `version` (e.g. `ADBC_VERSION_1_0_0` = 1000000, `ADBC_VERSION_1_1_0` = 1001000), `driver` (pointer to the struct for that version), `error`; returns `ADBC_STATUS_NOT_IMPLEMENTED` for unsupported versions; recommended name "AdbcDriverInit", derived names e.g. `libadbc_driver_sqlite.so.2.0.0` -> `AdbcDriverSqliteInit` [vendor][checked 2026-11-09] — [adbc.h on GitHub main](https://raw.githubusercontent.com/apache/arrow-adbc/main/c/include/arrow-adbc/adbc.h)
- `struct AdbcDriver`: `private_data`, `private_manager`, `release`, then 1.0.0 function pointers (Database*, Connection*, Statement*), then 1.1.0 additions (ErrorGetDetailCount/ErrorGetDetail/ErrorFromArrayStream, typed Get/SetOption variants, ConnectionCancel, ConnectionGetStatistics, StatementCancel, StatementExecuteSchema, ...). Compatibility rule: a 1.0.0 driver loaded by a 1.1.0 manager "must not access the new fields, which will carry undefined values" (manager requests 1.1.0, retries with 1.0.0); a 1.1.0 driver under a 1.0.0 manager "must not access the new fields, and should initialize the old fields" [vendor][checked 2026-11-09] — same URL
- `struct AdbcError`: `char* message`, `int32_t vendor_code`, `char sqlstate[5]`, `void (*release)(AdbcError*)`; 1.1.0 added `void* private_data` and `AdbcDriver* private_driver`, read/written "if and only if vendor_code is equal to" `ADBC_ERROR_VENDOR_CODE_PRIVATE_DATA` (= INT32_MIN); callers must zero-initialise (`ADBC_ERROR_INIT`) [vendor][checked 2026-11-09] — same URL
- `AdbcDatabase/Connection/Statement` each hold `private_data` (NULL when uninitialised/freed) and `private_driver`; results are consumed "equivalent to reading from what many Arrow libraries call a RecordBatchReader"; 1.1.0 added cancellation, rich error metadata, statistics, incremental execution; `ADBC_INFO_DRIVER_ADBC_VERSION` reports the driver's version [vendor][checked 2026-11-09] — [ADBC specification page](https://arrow.apache.org/adbc/current/format/specification.html)
- Rust: implement `Driver, Database, Connection, Statement` traits, build as `crate-type = ["lib", "cdylib"]`, and `adbc_ffi::export_driver!` (docs also show it under `adbc_core` for older versions) to "Export a Rust driver as a C driver"; ADBC 21 Rust = 0.21.0 [vendor][checked 2026-11-09] — [adbc_core README](https://docs.rs/crate/adbc_core/0.24.0/source/README.md), [adbc_ffi](https://docs.rs/adbc_ffi), [ADBC Rust driver manager docs](https://arrow.apache.org/adbc/main/rust/driver_manager.html)
- libpq: Makefile moved shlib version "5.1 as compared to 5.0 in PG 8.2" (adding functions is a minor bump, not a SONAME change); "no document that describes libpq ABI versioning and compatibility rules"; a 2007 thread notes an 8.3 change that "breaks ABI compatibility without announcing it in the SONAME" [vendor mailing lists / third party packager][checked 2026-11-09] — [pgsql-hackers: bump libpq major for 8.3?](https://postgrespro.com/list/thread-id/1699444), [build2 libpq bootstrap.build](https://cgit.build2.org/cgit/packaging/postgresql/libpq/tree/build/bootstrap.build), [libpq compatibility policy thread](https://www.postgresql.org/message-id/524AC850.7000109@4js.com)
- SQLite's C-interface intro page describes the API as objects, constants and functions but states no stability policy on that page [vendor][checked 2026-11-09] — [sqlite.org/c3ref/intro.html](https://sqlite.org/c3ref/intro.html). (SQLite's separate compatibility/“35% of the API is deprecated but kept” statements were not fetched — see Gaps.)
- abi_stable uses `#[repr(C)]` data structures and requires choosing an existing stable enum representation; stabby ("stable ABI for Rust focused on compact sum types") encodes layout via associated types, treats unions as having no niches, and warns that Rust 1.78+ trait objects "may raise performance issues" [vendor][checked 2026-11-09] — [stabby README](https://docs.rs/crate/stabby/72.1.4/source/README.md), [Rust internals thread](https://internals.rust-lang.org/t/a-stable-modular-abi-for-rust/12347)

### Inferences
- Design the rdbc C ABI as: opaque `*mut` handles with `private_data`; a versioned init function filling a `repr(C)` function table (so new functions append, never reorder); an error struct with embedded `release` and a sentinel for extension; all result data via `ArrowArrayStream` (and `ArrowSchema` for metadata); option get/set with typed variants. If this *is* adbc.h, the ADBC manager loads it directly and the JDBC/ODBC/Python layers are thin facades over the same table — one ABI serves every bridge.
- Do not use abi_stable/stabby for the public surface; they solve Rust-plugin ABI, add build complexity, and no consumer (JVM, CPython, Node, .NET, ODBC DM) can read them. Keep them out unless an in-process Rust plugin system is wanted.
- Versioning lesson from libpq: never bump SONAME; add functions and new table entries; publish a written compatibility policy (libpq's absence of one is a recurring complaint).

### Gaps
- SQLite's explicit API-stability statements (c3ref/intro did not contain them) were not retrieved.
- `AdbcDriverInitFunc` typedef line itself was cut off in the fetched header (page truncated at 100,000 chars); semantics were taken from its doc comment.

## Q6. ODBC driver export

### Takeaway
An ODBC driver is a shared library exporting the ODBC 3.x `SQL*` entry points (Unicode drivers must export `SQLConnectW` and accept all `W` functions), optionally a setup DLL exporting `ConfigDSN`/`ConfigDSNW`; registration is a section in `odbcinst.ini` (unixODBC/iODBC) or the Windows registry. I found **no shipping Rust-implemented ODBC driver** — all Rust ODBC crates (odbc-sys, odbc-api, rs-odbc) are client-side — so this would be a first; C++ precedents (ClickHouse ODBC, Dremio Flight SQL ODBC) show the surface area. Once an ODBC driver exists, Power BI (via `Odbc.DataSource`), Tableau ("Other Databases (ODBC)", tunable via TDC/SQLGetInfo), Excel and most ETL tools connect with no further work, though with tool-specific gotchas (64-bit only in Power BI, "may work only for extracts" in Tableau).

### Cited Findings
- Microsoft "Developing an ODBC Driver" section: ODBC Driver Architecture, Upgrading 3.5->3.8, connection-pool awareness, async completion notification [vendor][checked 2026-11-09] — [MS Learn](https://learn.microsoft.com/en-us/sql/odbc/reference/develop-driver/developing-an-odbc-driver)
- Conformance: three levels Core, Level 1, Level 2; "Conformance with a given level implies complete conformance with all lower levels"; applications discover the level via `SQLGetInfo(SQL_ODBC_INTERFACE_CONFORMANCE)` and functions via `SQLGetFunctions`; "all the features implied by ODBC 2.x API conformance Level 1 are now part of the Core interface conformance level" [vendor][checked 2026-11-09] — [Interface Conformance Levels](https://learn.microsoft.com/en-us/sql/odbc/reference/develop-app/interface-conformance-levels)
- Unicode: "A Unicode driver must export SQLConnectW to be recognized as a Unicode driver by the Driver Manager"; it "must accept Unicode functions (with a suffix of W)"; the DM strips the `A` suffix before passing ANSI calls; a Unicode driver must convert `SQL_WCHAR` to `SQL_CHAR` when the app binds `SQL_C_CHAR`; the DM sets `SQL_ATTR_ANSI_APP` at connect [vendor][checked 2026-11-09] — [Unicode Drivers](https://learn.microsoft.com/en-us/sql/odbc/reference/develop-app/unicode-drivers)
- Setup: `BOOL ConfigDSN(HWND, WORD fRequest, LPCSTR lpszDriver, LPCSTR lpszAttributes)` with `ODBC_ADD_DSN / ODBC_CONFIG_DSN / ODBC_REMOVE_DSN`; "It can be in the driver DLL or a separate setup DLL"; Unicode version "must be called ConfigDSNW"; it writes DSNs through `SQLWriteDSNToIni` / `SQLWritePrivateProfileString` [vendor][checked 2026-11-09] — [ConfigDSN function](https://learn.microsoft.com/en-us/sql/odbc/reference/syntax/configdsn-function)
- unixODBC: drivers are registered as a section in `odbcinst.ini` with `Driver=` (and optional `Setup=`) paths; `odbcinst -j` shows file locations, `odbcinst -q -d` lists drivers [vendor / third party (CData, Debian unixODBC manual)][checked 2026-11-09] — [unixODBC 2.1.1 admin manual (Debian)](https://sources.debian.org/src/unixodbc/2.1.1-8/doc/AdministratorManual/odbcinst.html), [CData unixODBC on Linux](https://cdn.cdata.com/help/RDN/odbc/pg_unixODBConlinux.htm)
- Rust ODBC crates are client-side only: odbc-sys "links against odbc32.dll on Windows... libodbc.so" (the driver manager); odbc-api "built on top of the odbc-sys ffi bindings"; rs-odbc requires "ODBC Driver Manager installed" [vendor][checked 2026-11-09] — [docs.rs/odbc-sys](https://docs.rs/crate/odbc-sys/latest), [docs.rs/odbc-api](https://docs.rs/crate/odbc-api/latest), [lib.rs/rs-odbc](https://www.lib.rs/crates/rs-odbc). No crate or repo exporting `SQLAllocHandle`/`SQLDriverConnect`/`SQLGetDiagRecW` with `#[no_mangle]` was found in three searches [checked 2026-11-09].
- ClickHouse ODBC: Apache-2.0, needs "C++17 and C11 capable compiler", ships ANSI and Unicode DSNs, supports Windows MDAC/WDAC DM, unixODBC, iODBC; "The driver and the application must use the same driver manager" [vendor][checked 2026-11-09] — [ClickHouse/clickhouse-odbc](https://github.com/ClickHouse/clickhouse-odbc)
- Dremio Arrow Flight SQL ODBC driver: open source, "licensed under GNU Library General Public License, Version 2", 0.9.6 (June 2025) fixed TLS Flight endpoints, 0.9.7.x latest per third-party listing, Windows + Linux (+ Apple Silicon from 0.9.4); Arrow blog: "not yet part of the Arrow project due to dependency licensing issues" [vendor / third party][checked 2026-11-09] — [Dremio docs](https://docs.dremio.com/cloud/sonar/client-apps/drivers/arrow-flight-sql-odbc), [Dremio release notes](https://docs.dremio.com/current/release-notes/arrow-flight-sql-odbc), [Arrow blog 2022](https://arrow.apache.org/blog/2022/11/01/arrow-flight-sql-jdbc/)
- arrow-odbc (reverse direction, Rust consuming ODBC into Arrow) exists via odbc-api; adbcBridge "loads an ODBC driver and exposes it through the ADBC API" [vendor][checked 2026-11-09] — [ADBC integrations](https://arrow.apache.org/adbc/current/integrations.html)
- Power Query: `Odbc.DataSource` is the preferred base for custom connectors over existing ODBC drivers — "provides a default navigation table" and connectors "inherit default query folding behavior based on the capabilities reported by your driver"; `Odbc.Query` is passthrough without folding; Power BI Desktop is 64-bit so needs a 64-bit driver; Power BI Report Server does not support custom connectors but does use installed ODBC drivers [vendor / third party][checked 2026-11-09] — [MS Learn Power Query ODBC](https://learn.microsoft.com/en-us/power-query/odbc), [Fabric community PBIRS thread](https://community.fabric.microsoft.com/t5/Report-Server/Connect-to-Denodo-as-datasource-with-PBIRS/td-p/4666475)
- Tableau: "some ODBC drivers will support the full Tableau interactive experience, while others may work only for creating extracts"; Tableau support "can't create or customise a connector to work with a specific ODBC driver"; behaviour is tuned via TDC files containing `<connection-customization>` with Tableau capabilities and `SQLGetInfo` overrides matched on vendor/driver name [vendor][checked 2026-11-09] — [Tableau and ODBC](https://help.tableau.com/current/pro/desktop/en-us/odbc_tableau.htm), [ODBC/SQL Customizations Reference](https://help.tableau.com/current/pro/desktop/en-us/odbc_sql.htm)

### Inferences
- Work estimate: the ODBC surface is the largest of the exports (≈ 70+ entry points for Core, descriptors `SQLGetDescField/SetDescField`, `SQLBindCol`/`SQLGetData` with every C-type conversion, `SQLGetInfo` with ~170 info types, catalog functions `SQLTables/SQLColumns/...`, diagnostics, both ANSI and W variants). Rust `#[no_mangle] extern "system"` exports from a cdylib are straightforward; the effort is semantic conformance and BI-tool quirks, not FFI.
- The ODBC driver is best built *on top of* the ADBC/Arrow core: `SQLFetch` pulls from an `ArrowArrayStream`, converting one batch at a time into bound column buffers — the same approach adbcBridge takes in reverse.
- Being first Rust ODBC driver has marketing value but no reusable Rust scaffolding exists; budget time to write descriptor/DSN plumbing and a setup DLL (Windows) and to test against unixODBC, iODBC (macOS/Tableau) and the Windows DM, plus Power BI/Tableau/Excel smoke tests.

### Gaps
- No Rust ODBC driver precedent found (odbc-sys-based drivers, "Rust ODBC driver for Exasol") — the Exasol product could not be located; the Exasol Metabase driver found is Clojure.
- Microsoft's full ODBC function/attribute/descriptor conformance tables were not fetched (only the overview page).
- Qlik and specific ETL tools (Informatica, SSIS, Talend) were not individually verified; they are assumed to use the system DM like Excel/Power BI.

## Q7. ADBC driver export (loading model, consumers, measured gains, validation) and Flight SQL as server-side export

### Takeaway
ADBC is the highest-leverage export: one `cdylib` with `AdbcDriverInit` + a TOML manifest is loadable by the C/C++, Python (`adbc_driver_manager`), R, Go, Java (JNI, since ADBC 21), C#, Ruby, JavaScript and Rust driver managers, and is consumed by pandas 2.2+, Polars, DuckDB (adbc/adbc_scanner), DataFusion, GDAL 3.11+, dbt Fusion, dlt and others. Distribution via Columnar's `dbc` and the ADBC Driver Foundry (adbc-drivers org, launched 2025-10-29) is the emerging channel; ClickHouse shipped exactly this (a Rust ADBC driver, July 2026). Measured gains vs row drivers range 2–13x depending on consumer. Flight SQL is a server-side protocol and only matters if rdbc also hosts a server.

### Cited Findings
- Driver manifests: TOML with optional `manifest_version` (default 1; managers "must error upon reading a manifest with manifest_version higher than 1"), `name`, `version`, `publisher`, `license`, `url`, `[ADBC] version`, `[ADBC.features] supported/unsupported`, `[Driver] entrypoint`, `[Driver.shared]` keyed by platform tuple (`linux_amd64`, suffixes `_musl`, `_mingw`) — only `Driver.shared` required. Search order (Unix): `ADBC_DRIVER_PATH` (colon-separated) -> `$VIRTUAL_ENV/etc/adbc/drivers` -> `$CONDA_PREFIX/etc/adbc/drivers` -> user (`~/Library/Application Support/ADBC/Drivers` on macOS, `$XDG_CONFIG_HOME/adbc/drivers` or `~/.config/adbc/drivers`) -> system (`/Library/Application Support/ADBC/Drivers`, `/etc/adbc/drivers`). Windows: `ADBC_DRIVER_PATH` (semicolon) -> venv/conda -> `HKEY_CURRENT_USER\SOFTWARE\ADBC\Drivers\${name}` (sub-keys name/version/source/entrypoint/driver) or `%LOCALAPPDATA%\ADBC\Drivers` -> `HKEY_LOCAL_MACHINE\SOFTWARE\ADBC\Drivers\${name}`. Load flags `SEARCH_ENV/SEARCH_USER/SEARCH_SYSTEM/ALLOW_RELATIVE_PATHS/DEFAULT`; relative paths disabled "for security reasons"; a bare name resolves `<name>.toml` then falls back to `LD_LIBRARY_PATH`; URI scheme (`postgresql://`) selects the driver when `driver` is unset; `profile.toml` is reserved [vendor][checked 2026-11-09] — [ADBC Driver Manager and Manifests](https://arrow.apache.org/adbc/main/format/driver_manifests.html)
- Consumers listed on the official integrations page: adbcBridge (ODBC->ADBC), Apache DataFusion ("available as an ADBC driver" and an "ADBC table provider"), databow CLI, dbc (Columnar's installer), DuckDB ("DuckDB itself is an ADBC driver"; `adbc` and `adbc_scanner` community extensions), GDAL 3.11+ (read-only OGR driver), Go `database/sql` adapter, pandas, Polars (`read_database`/`write_database`), R adbi and dplyr via adbcdrivermanager, Ruby ActiveRecord adapter [vendor][checked 2026-11-09] — [ADBC integrations](https://arrow.apache.org/adbc/current/integrations.html)
- Release cadence/versions: ADBC 22 (2026-01-09, C/C++ 1.10.0), 23 (2026-04-07, 1.11.0), 24 (2026-07-28, 1.12.0; DataFusion/BigQuery/Databricks/Snowflake drivers moved to the Driver Foundry; C++20 required from next release), 25 (2026-10-26 per third-party guide; Go core/drivers split into modules); API spec at 1.1.0 [vendor; 25 date third party][checked 2026-11-09] — [ADBC 22](https://arrow.apache.org/blog/2026/01/09/adbc-22-release/), [ADBC 23](https://arrow.apache.org/blog/2026/04/07/adbc-23-release/), [ADBC 24](https://arrow.apache.org/blog/2026/07/28/adbc-24-release/), [ADBC 25 guide](https://datalakehousehub.com/blog/adbc-25-upgrade-guide/)
- ADBC Driver Foundry: announced 2025-10-29 by Columnar with Databricks, dbt Labs, Improving, Microsoft, Snowflake and the Arrow community; GitHub org `adbc-drivers` ("similar to datafusion-contrib"); provides "precompiled, signed driver binaries"; `dbc install <name>` installs [vendor][checked 2026-11-09] — [Columnar announcement](https://columnar.tech/blog/announcing-columnar/), [dev@arrow thread](https://go.mail-archive.com/dev@arrow.apache.org/msg34206.html), [Introducing dbc](https://columnar.tech/blog/introducing-dbc/)
- ClickHouse ADBC driver 0.1.0 (2026-07-10): "written in Rust", speaks ClickHouse HTTP with TLS, distributed via the Foundry and `dbc install clickhouse`, loaded via `clickhouse://` URI; targets Ruby (`red-adbc`), R, C, Polars, pandas, dlt and dbt Fusion (which bundles it); no benchmarks given [vendor][checked 2026-11-09] — [ClickHouse blog](https://clickhouse.com/blog/introducing-the-clickhouse-adbc-driver)
- Validation: Go `validation` package (DriverQuirks); Java `adbc-driver-validation` module with per-DB suites (Derby, SQL Server, PostgreSQL) and a JNI validation suite against SQLite; Python `adbc-drivers/validation` ("reusable, pluggable test suite... written with Python and pytest"); chDB runs both "the Apache Arrow ADBC conformance suite, which checks the C contract" and "the ADBC Driver Foundry validation suite" (SQL behaviour, type round-trips, metadata, bulk ingest) [vendor / third party][checked 2026-11-09] — [Go validation](https://pkg.go.dev/github.com/apache/arrow-adbc/go/adbc/validation), [adbc-drivers/validation](https://github.com/adbc-drivers/validation), [chDB ADBC docs](https://clickhouse.com/docs/chdb/install/adbc)
- Measured gains: Java ADBC vs JDBC 13x / 5x memory (see Q1) [third party]; Snowflake ADBC vs JDBC "~20–30% faster" at 1K–100K rows, "roughly tied" at 1 M mixed-type rows (user report) [third party][checked 2026-11-09] — [arrow-adbc issue #4271 comment](https://mail-archive.com/github@arrow.apache.org/msg403775.html); the Voltron Data Flight SQL ADBC-vs-JDBC Python benchmark repo exists (TPC-H SF1 DuckDB behind Flight SQL, JDBC via Py4J) but publishes no numbers in its README and the blog host did not resolve [vendor][checked 2026-11-09] — [voltrondata/flight-sql-adbc-vs-jdbc](https://github.com/voltrondata/flight-sql-adbc-vs-jdbc)
- Flight SQL: "a protocol for interacting with SQL databases using the Arrow in-memory format and the Flight RPC framework"; server skeletons in C++ and Java; Apache ships a PostgreSQL extension exposing a Flight SQL endpoint; community servers include Voltron Data's DuckDB/SQLite example and Porter (Go, DuckDB) [vendor / third party][checked 2026-11-09] — [Arrow Flight SQL format](https://arrow.apache.org/docs/format/FlightSql.html), [arrow-flight-sql-postgresql](https://arrow.apache.org/flight-sql-postgresql/devel/_sources/overview.md.txt), [TFMV/porter](https://awesome.ecosyste.ms/projects/github.com%2FTFMV%2Fporter)
- datafusion-table-providers supports PostgreSQL, MySQL, SQLite, ClickHouse, DuckDB, Flight SQL and ODBC sources with opt-in `datafusion-federation` join push-down; "not an official Apache Software Foundation project"; docs.rs build of 0.9.0 failed [vendor][checked 2026-11-09] — [datafusion-table-providers README](https://docs.rs/crate/datafusion-table-providers/0.9.3/source/README.md)

### Inferences
- Per unit of work, ADBC export dominates: one cdylib + TOML reaches pandas, Polars, DuckDB, DataFusion, R, Ruby, Go, C#, Java (JNI DM) and dbt Fusion, with a ready-made validation suite and a signed-binary distribution channel. The ClickHouse precedent is the exact shape rdbc should copy.
- Passing validation means: Go/Python Foundry suites for SQL behaviour, type round-trips, `GetObjects` metadata depth, bulk ingest modes (`append/create/replace/create_append`), plus the C-contract conformance suite (zero-initialised structs, `release` semantics, 1.0.0/1.1.0 negotiation).
- Flight SQL export is orthogonal: it turns rdbc into a *server* (a proxy in front of Postgres/MySQL/etc.), which gains the Flight SQL JDBC/ODBC drivers and Dremio-style BI connectivity for free but adds a deployable component; it is not a client-library export.

### Gaps
- Exact `libadbc_driver_manager` shared-library version for ADBC 25 not confirmed from an Apache source.
- Which ADBC release introduced manifests was not stated on the manifests page.
- Voltron Data's ADBC-vs-JDBC Python numbers not retrieved (host unreachable).

## Q8. Query engines and tools that need a generic connector; which protocols they accept; reach per unit of work

### Takeaway
JVM engines (Spark, Trino/Presto, Kafka Connect, Airbyte DB connectors, Metabase) accept only JDBC; Python tooling (dbt classic, Superset, Airflow) accepts DB-API 2.0 + SQLAlchemy; Arrow-native engines (DataFusion, Polars, DuckDB, pandas 2.2+) accept ADBC (and DuckDB/DataFusion also ship bespoke libpq/ODBC/Flight SQL scanners); BI desktops (Power BI, Tableau, Excel, Qlik) accept ODBC. The documented JDBC bottleneck in Spark and Trino (single-connection row extraction ≈ 32 MB/s in Abadi's Trino test vs ≈ 10 GB/s from HDFS) is the specific pain a Rust core with parallel, columnar extraction can relieve — but only if it is reachable *as a JDBC driver*.

### Cited Findings
- Spark JDBC source: single partition unless `partitionColumn/lowerBound/upperBound/numPartitions` are all set; `fetchsize` "determines how many rows to fetch per round trip" and helps "drivers which default to low fetch size (e.g. Oracle with 10 rows)" [vendor][checked 2026-11-09] — [Spark 3.5.1 JDBC docs](https://spark.apache.org/docs/3.5.1/sql-data-sources-jdbc.html); a practitioner report: unpartitioned read >1 h vs 32 partitions <10 min [third party][checked 2026-11-09] — [Mercedes-Benz tech blog](https://medium.com/mercedes-benz-techinnovation-blog/increasing-apache-spark-read-performance-for-jdbc-connections-a028115e20cd); Sail (Spark-compatible engine) exposes a `jdbc` format "based on the Python connectorx library. No actual JDBC driver or JVM is involved" [vendor][checked 2026-11-09] — [Sail JDBC docs](https://docs.lakesail.com/sail/main/guide/sources/jdbc/)
- Trino JDBC bottleneck (Abadi/Song, Starburst, 2026-01-27, TPC-H SF100, CloudLab): lineitem 52.71 GB from HDFS in 5.11 s with 2,537 parallel connections vs part 8.72 GB from Oracle over one JDBC connection in 273 s — "320x" extraction-rate gap; Q14 277 s open-source Trino vs 37.7 s Starburst parallel JDBC (>7x); partition sweep gains flatten after ~20 partitions; manual logical partitioning in Trino gave ~3x [third party (commissioned by Starburst)][checked 2026-11-09] — [starburst.io blog](https://www.starburst.io/blog/benchmarking-the-jdbc-bottleneck-in-trino/)
- Trino connectors must implement the Trino SPI; Starburst's Metabase driver is Clojure over the Trino JDBC driver; Metabase drivers "are written in Clojure" with a generic SQL-JDBC base that makes JDBC drivers "simpler" to write [vendor][checked 2026-11-09] — [Metabase driver guide](https://www.metabase.com/docs/latest/developers-guide/drivers/start), [Metabase forum](https://discourse.metabase.com/t/java-for-driver-development/12235)
- Kafka Connect JDBC: "Find the JDBC 4.0 driver JAR file for each database system... Place these JAR files into the share/java/kafka-connect-jdbc" on every worker [vendor][checked 2026-11-09] — [Confluent JDBC drivers](https://docs.confluent.io/kafka-connectors/jdbc/10.9/jdbc-drivers.html)
- Airbyte: "most database sources and destinations are written in Java"; the newer Kotlin Bulk CDK has JDBC partition classes with sequential/concurrent modes (`airbyte.connector.extract.jdbc.mode`) [vendor][checked 2026-11-09] — [Airbyte connector development](https://docs.airbyte.com/connector-development/), [Bulk CDK extract-jdbc docs (mirror)](https://airbyte-kotlin-cdk.vercel.app/toolkits/bulk-cdk-toolkit-extract-jdbc/io.airbyte.cdk.read/index.html)
- Grafana data sources reach SQL databases through backend plugins written with the Go SDK, running as separate processes over RPC [vendor][checked 2026-11-09] — [Grafana backend plugins](https://grafana.com/developers/plugin-tools/key-concepts/backend-plugins/)
- DuckDB postgres extension: statically links libpq, reads via `COPY ... TO STDOUT (FORMAT binary)`, parallelises by ctid page ranges (1000 pages per task), pool capped at 32 connections, `pg_use_binary_copy` default true [vendor][checked 2026-11-09] — [DuckDB postgres scanner blog](https://duckdb.org/2022/09/30/postgres-scanner.html), [DuckDB postgres extension docs](https://duckdb.org/docs/current/core_extensions/postgres/overview)
- Superset/dbt/pandas/Polars/DataFusion/GDAL/R/Ruby protocol acceptance: see Q2 and Q7 citations.

### Inferences — reach per unit of work (my ranking)
1. **ADBC cdylib + manifest** (smallest work, largest Arrow-native reach): pandas, Polars, DuckDB, DataFusion, dbt Fusion, dlt, R, Ruby, Go, C#, Java-via-JNI, plus Foundry distribution and validation suites.
2. **Python DB-API 2.0 + SQLAlchemy dialect over the same core** (moderate work): unlocks dbt classic adapters, Superset, Airflow, SQLAlchemy ORMs — the long tail of Python tooling that ADBC does not reach.
3. **JDBC driver (FFM, Java 22+, JNI fallback)** (large work: JDBC 4.x surface, type mapping, metadata): the only way into Spark, Trino/Presto, Kafka Connect, Airbyte Java connectors, Metabase, and all enterprise Java apps — and the only place the "faster than pgJDBC" claim can be made. Spark/Trino bottleneck evidence gives the marketing hook, but note Spark/Trino parallelism is decided by the engine, not the driver; the driver can only make each connection's extraction columnar and cheaper.
4. **ODBC driver** (largest work, zero reusable Rust scaffolding): BI desktops and legacy ETL. Worth doing after JDBC, built over the ADBC core as adbcBridge does in reverse.
5. **Flight SQL server** (separate deployable): optional; gives Flight SQL JDBC/ODBC drivers for free when a proxy architecture is acceptable.

### Gaps
- Qlik, Informatica, Talend and Vector (the Rust observability pipeline) were not individually verified for protocol acceptance.
- No benchmark exists of ConnectorX vs partitioned Spark JDBC; Sail's claim is architectural, not measured.

## Q9. Business and licensing

### Takeaway
An Apache-2.0 Rust core is compatible with MIT/BSD/MPL crates, but linking `libmysqlclient` (GPL with Oracle's Universal FOSS Exception) or `FreeTDS` (LGPL, must allow relinking) imports copyleft obligations — pure-Rust protocol implementations avoid both. SQLite is public domain; Oracle Instant Client may be redistributed under OTN terms with pass-through conditions and no charge. "JDBC" and "ODBC" do not appear in Oracle's or Microsoft's registered-mark lists found here, but Oracle's third-party guidelines forbid using its marks "as all or part of your company, product or service names", so product naming should avoid "Oracle"/"Java"/"MySQL" and treat "JDBC"/"ODBC" as descriptive API names only.

### Cited Findings
- MySQL client library: GPL with the "Universal FOSS Exception, version 1.0", whose text says linking "does not by itself require that the other FOSS be relicensed"; packagers note the exception requires derivative works to carry an approved licence [vendor / third party][checked 2026-11-09] — [MySQL 8.4 Licensing Information](https://docs.oracle.com/cd/E17952_01/mysqld-8.4-license-gpl-en/licensing-information.html), [Fedora legal thread](https://lists.fedoraproject.org/pipermail/legal/2012-January/001800.html), [Debian EXCEPTIONS-CLIENT](https://sources.debian.org/src/mysql-dfsg-5.0/5.0.32-7etch12/EXCEPTIONS-CLIENT)
- FreeTDS (LGPL): maintainers state static or dynamic linking both bind the program by the LGPL and distributors must let recipients relink against modified FreeTDS; static linking "allowed, but there are some caveats" [vendor mailing list, 2010–2015][checked 2026-11-09] — [freetds list 2015-08](https://lists.ibiblio.org/sympa/arc/freetds/2015-08/msg00001.html), [freetds list 2011-05](https://lists.ibiblio.org/sympa/arc/freetds/2011-05/msg00119.html)
- Oracle Instant Client: "subject to the license, Instant Client can be bundled and redistributed for free"; redistributors must bind end users to "terms materially consistent with the OTN License" and the redistribution right "does not flow through to your end users" [vendor / third party packager][checked 2026-11-09] — [Instant Client FAQ](https://www.oracle.com/database/technologies/faq-instant-client.html), [OTN Instant Client licence](https://www.oracle.com/downloads/licenses/instant-client-lic.html), [ThinkGeo NuGet licence note](https://feed.nuget.org/packages/ThinkGeo.Dependency.Oracle/14.5.2/License)
- Oracle trademark guidelines: "Oracle, Java, MySQL, and NetSuite are registered trademarks"; "do not use Oracle trademarks or potentially confusing variations as all or part of your company, product or service names"; JDBC not listed as a mark on the pages retrieved [vendor][checked 2026-11-09] — [Oracle Third Party Usage Guidelines](https://www.oracle.com/legal/trademarks/) (fetch of the full list returned 403; content from search snippets)
- Dremio's Flight SQL ODBC driver is LGPL-2 and was kept out of the Arrow project "due to dependency licensing issues" — a precedent that ODBC drivers tend to drag in copyleft dependencies [vendor][checked 2026-11-09] — [Dremio docs](https://docs.dremio.com/cloud/sonar/client-apps/drivers/arrow-flight-sql-odbc), [Arrow blog](https://arrow.apache.org/blog/2022/11/01/arrow-flight-sql-jdbc/)
- Licences of key precedents: sqlite-jdbc Apache-2.0 (+BSD-2); duckdb-java MIT; ClickHouse ODBC Apache-2.0; Columnar's Foundry drivers "precompiled, signed" under Apache-2.0 per the ADBC project [vendor][checked 2026-11-09] — see Q1/Q6/Q7 URLs

### Inferences
- Keep the core free of C database client libraries (pure-Rust Postgres/MySQL/TDS/SQLite-via-bundled-amalgamation) to stay cleanly Apache-2.0 and to avoid the libmysqlclient/FreeTDS questions entirely; Oracle (which has no wire-protocol open implementation) is the one backend that forces an optional, separately-downloaded Instant Client with OTN pass-through terms — ship it as an opt-in feature, never bundled.
- Use "JDBC driver"/"ODBC driver" descriptively ("rdbc JDBC driver") and never in a product name combined with Oracle/Microsoft marks; register the ADBC manifest `name`/`publisher` fields with the project's own name.

### Gaps
- Microsoft's trademark list was not fetched; whether "ODBC" is claimed as a mark is unverified (no source found asserting it is).
- Current (2026) Oracle OTN Instant Client wording was not re-read in full; the "no charge to end users" clause comes from a 2010 copy.
- No legal opinion sources on Rust `cdylib` + LGPL relinking obligations specifically.
