# Wire protocols and client APIs of the major databases, for a from-scratch high-performance Rust driver

Research notes, current as of 2026-11-09. Tags: [vendor] = first-party documentation or source; [third party] = independent source; [checked YYYY-MM-DD] = date the URL was fetched by me. Protocol and product versions are named where the source names them. Where a fetched page did not contain a detail that I expected, the detail is listed under Gaps rather than asserted.

Scope note: the brief asked for enough detail to estimate bytes per row, syscalls per query and allocations per row. Byte-level layouts are given in the Cited Findings; the per-row arithmetic for a 10-column mixed row is in the Inferences of each section and consolidated in the Cross-cutting section.

## PostgreSQL frontend/backend protocol 3.0 and 3.2 (PostgreSQL 18, 2025)

### Takeaway
PostgreSQL has the most completely documented open wire protocol of the group: fixed 1-byte-type + Int32-length framing, an extended-query sub-protocol (Parse/Bind/Describe/Execute/Sync) with per-column text-or-binary result formats, a binary COPY format that reuses the per-type binary send/recv encodings, and server-side support for pipelining that needs no server changes. Protocol 3.2 (PG18) only changes the cancel key (4 bytes -> variable, up to 256 bytes) and adds NegotiateProtocolVersion-based minor-version downgrade; libpq still defaults to 3.0. The fastest clients (asyncpg, pgx, tokio-postgres) all use the extended protocol with binary result formats, prepared-statement caching and zero-copy row buffers.

### Cited Findings

**Framing, versions, negotiation**
- Every message starts with a 1-byte type followed by an Int32 length that "includes itself, but not the message-type byte"; the startup message alone has no type byte; integers are network byte order (big-endian); text/binary format codes are 0 and 1 and "all other codes are reserved"; "binary representations for complex data types might change across server versions". — [vendor] [checked 2026-11-09] [PostgreSQL 18 docs, 54.1 Overview](https://www.postgresql.org/docs/current/protocol-overview.html)
- Version table: 3.2 is current (PG18+), "the cancellation secret key grew from 4 bytes to a variable-length field"; 3.1 was "reserved, never used ... skipped because old pgbouncer versions incorrectly claimed to support it"; 3.0 is PG 7.4+ and "libpq still uses 3.0 by default for compatibility"; minor-version negotiation via NegotiateProtocolVersion was introduced in 9.3.21. — [vendor] [checked 2026-11-09] [54.1 Overview](https://www.postgresql.org/docs/current/protocol-overview.html)
- StartupMessage: Int32 length, Int32 version (3.2 = 196610 = 0x00030002), NUL-terminated name/value pairs, final NUL. `user` required; names starting `_pq_.` reserved for protocol extensions. NegotiateProtocolVersion ('v'): Int32 newest supported minor, Int32 count of unrecognised options, then option names. — [vendor] [checked 2026-11-09] [54.7 Message Formats](https://www.postgresql.org/docs/current/protocol-message-formats.html)
- BackendKeyData ('K'): Int32 PID + secret key "runs to end of message"; in 3.2 the key is 4..256 bytes and "the server currently sends at most 32 bytes". CancelRequest: Int32 length = 12 + key_len, Int32 80877102, Int32 PID, key bytes. — [vendor] [checked 2026-11-09] [54.7 Message Formats](https://www.postgresql.org/docs/current/protocol-message-formats.html)
- PG18 release notes: "Make cancel request keys 256 bits ... only possible when the server and client support wire protocol version 3.2, introduced in this release"; adds `PQfullProtocolVersion()`, min/max protocol-version connection parameters, OAuth (`oauth` in pg_hba.conf, `--with-libcurl`), MD5 password deprecation with `md5_password_warnings`, `sslkeylogfile`, `PQtrace()` for all message types, COPY `REJECT_LIMIT` and `LOG_VERBOSITY silent`, `search_path` reported to the client, SCRAM pass-through (`scram_client_key`/`scram_server_key`). — [vendor] [checked 2026-11-09] [PG18 release notes](https://www.postgresql.org/docs/18/release-18.html)
- libpq `min_protocol_version` / `max_protocol_version`: values `3.0`, `3.2`, `latest`; max defaults to "version 3.0 ... unless the connection string specifies a feature that relies on a higher protocol version"; "If the server does not support the protocol version requested by the client, the connection is automatically downgraded". — [vendor] [checked 2026-11-09] [libpq connect params](https://www.postgresql.org/docs/current/libpq-connect.html)

**Startup, SSL, authentication**
- SSLRequest: Int32 8, Int32 80877103; server answers a single byte `S` or `N`; read exactly one byte (CVE-2021-23222); GSSENCRequest is Int32 8, Int32 80877104 and server answers `G`/`N`; GSS wrap packets are length-prefixed, server accepts < 16 kB per packet, ~8 kB plaintext per wrap typical. Direct SSL: client starts TLS immediately and "must send ALPN `postgresql`" (RFC 7301); the server then expects a normal StartupMessage. — [vendor] [checked 2026-11-09] [54.2 Message Flow](https://www.postgresql.org/docs/current/protocol-flow.html)
- libpq `sslnegotiation`: `postgres` (default) or `direct` ("start SSL handshake directly after establishing the TCP/IP connection ... only allowed with sslmode=require or higher"; "introduced in PostgreSQL version 17"). `sslmode` default `prefer`; `channel_binding` default `prefer` with SSL builds, "only supported over SSL connections with PostgreSQL 11 or later servers using the SCRAM authentication method"; `gssencmode` default `prefer`; `sslcompression` default 0 and "PostgreSQL 14 disabled compression completely in the backend"; `require_auth` accepts `password, md5, gss, sspi, scram-sha-256, oauth, none`. — [vendor] [checked 2026-11-09] [libpq connect params](https://www.postgresql.org/docs/current/libpq-connect.html)
- PG17 release notes: "Allow TLS connections without requiring a network round-trip negotiation ... enabled with the client-side option sslnegotiation=direct, requires ALPN, and only works on PostgreSQL 17 and later servers"; also `PQsendPipelineSync()`, `PQsetChunkedRowsMode()`, `PQclosePrepared/PQclosePortal`, non-blocking and encrypted cancel requests, "Improve performance when transferring large blocks of data to a client". — [vendor] [checked 2026-11-09] [PG17 release notes](https://www.postgresql.org/docs/17/release-17.html)
- Authentication messages all start `R`, Int32 length, Int32 code: Ok=0 (8 bytes), MD5Password=5 with 4-byte salt (12 bytes), SASL=10 (mechanism list, extra NUL), SASLContinue=11, SASLFinal=12. — [vendor] [checked 2026-11-09] [54.7 Message Formats](https://www.postgresql.org/docs/current/protocol-message-formats.html)
- MD5 is "deprecated, scheduled for removal": PasswordMessage = `concat('md5', md5(concat(md5(concat(password, username)), random-salt)))`. GSS/SSPI: AuthenticationGSS/SSPI -> GSSResponse -> AuthenticationGSSContinue rounds. — [vendor] [checked 2026-11-09] [54.2 Message Flow](https://www.postgresql.org/docs/current/protocol-flow.html)
- SCRAM: server advertises `SCRAM-SHA-256-PLUS` and `SCRAM-SHA-256` when built with SSL; channel-binding type is `tls-server-end-point` (server certificate signature, RFC 5929); the server ignores the `n=` username and uses the startup-message user; passwords are SASLprep'd as UTF-8 and used raw if invalid. Sequence: AuthenticationSASL -> SASLInitialResponse (client-first) -> AuthenticationSASLContinue (server-first) -> SASLResponse (client-final) -> AuthenticationSASLFinal (server-final) -> AuthenticationOk. OAUTHBEARER (PG18): client-initiated, no channel binding, no SASLFinal; discovery flow sends an empty `auth`, gets SASLContinue with a well-known URI and scopes, replies with a single `0x01` byte, receives ErrorMessage, obtains a token out of band and reconnects; "libpq does not cache tokens". — [vendor] [checked 2026-11-09] [54.3 SASL Authentication](https://www.postgresql.org/docs/current/sasl-authentication.html)

**Extended query, portals, pipelining**
- Parse ('P'): statement name, query, Int16 n param OIDs, Int32 OIDs (0 = unspecified). Bind ('B'): portal name, statement name, Int16 C format codes (0 = all text, 1 = applies to all, else per-param), Int16 N params each Int32 length (-1 NULL) + bytes, Int16 R result format codes (same rules). Describe ('D'): 'S' or 'P' + name. Execute ('E'): portal name, Int32 max rows (0 = unlimited). Sync 'S' and Flush 'H' are 5 bytes. — [vendor] [checked 2026-11-09] [54.7 Message Formats](https://www.postgresql.org/docs/current/protocol-message-formats.html)
- RowDescription ('T'): Int16 field count; per field: name, Int32 table OID, Int16 attnum, Int32 type OID, Int16 typlen, Int32 typmod, Int16 format code ("always 0 in the response to a statement Describe"). DataRow ('D'): Int16 column count; per column Int32 length (-1 NULL) + bytes. CommandComplete ('C'): tag string e.g. `SELECT 10`. PortalSuspended ('s'): 5 bytes, "sent only when an Execute's row limit is reached". — [vendor] [checked 2026-11-09] [54.7 Message Formats](https://www.postgresql.org/docs/current/protocol-message-formats.html)
- Flow: Parse -> ParseComplete, Bind -> BindComplete, Describe S -> ParameterDescription + RowDescription/NoData, Describe P -> RowDescription/NoData, Execute -> DataRow* then CommandComplete/EmptyQueryResponse/ErrorResponse/PortalSuspended, Sync -> ReadyForQuery. After an error the backend "discards messages until Sync"; exactly one ReadyForQuery per Sync. Unnamed statement/portal replaced by next Parse/Bind; named statements live for the session, named portals until end of transaction. Result format is set by Bind, "not by BINARY on a cursor". Partial fetch: Execute with maxRows > 0 returns PortalSuspended; re-Execute the same portal. — [vendor] [checked 2026-11-09] [54.2 Message Flow](https://www.postgresql.org/docs/current/protocol-flow.html)
- Pipelining (server side): send several requests without waiting; omit Sync between dependent steps so they fail together; "Track completion by counting ReadyForQuery messages, not CommandComplete"; DDL that cannot run in a transaction block fails unless first after a Sync. — [vendor] [checked 2026-11-09] [54.2 Message Flow](https://www.postgresql.org/docs/current/protocol-flow.html)
- libpq pipeline mode (libpq 14+): `PQenterPipelineMode`, `PQpipelineSync` (Sync + flush), `PQsendPipelineSync` (no flush), `PQsendFlushRequest`; results `PGRES_PIPELINE_SYNC` once per sync point, `PGRES_PIPELINE_ABORTED` for skipped queries; `PQexec`, `PQsendQuery` (simple protocol), multi-statement strings and COPY are disallowed; blocking mode can deadlock when "the client sends enough queries to fill both its output buffer and the server's receive buffer before it reads input", so non-blocking + poll loop is recommended; "100 statements at 300 ms RTT take about 30 s without pipelining, and possibly about 0.3 s with it"; cost is memory, "no meaningful overhead per query". — [vendor] [checked 2026-11-09] [libpq pipeline mode](https://www.postgresql.org/docs/current/libpq-pipeline-mode.html)

**Binary type encodings** (from the tokio-postgres `postgres-protocol` codecs and pgx)
- bool 1 byte; "char" i8; int2/int4/int8 big-endian; oid u32; float4/float8 IEEE big-endian; text/varchar/bpchar/name raw UTF-8 no prefix; bytea raw; timestamp/timestamptz i64 microseconds since 2000-01-01; date i32 days since 2000-01-01; time i64 microseconds since midnight; uuid 16 raw bytes; macaddr 6 bytes; point 2×f64; inet/cidr u8 family (2 = IPv4, 3 = IPv6), u8 netmask, u8 is_cidr, u8 address length, address bytes (8 or 20 bytes total); varbit i32 bit count + ceil(bits/8) bytes; hstore i32 count then per entry i32 key len + key, i32 value len (-1 NULL) + value; array: i32 ndim, i32 has-nulls flag, u32 element OID, per dim i32 length + i32 lower bound, per element i32 length (-1 NULL) + data (header 12 + 8·ndim); range: u8 flags (empty 0x01, lower-inc 0x02, upper-inc 0x04, lower-unbounded 0x08, upper-unbounded 0x10) then bounded sides as i32 len + data; ltree u8 version (1) + text. — [third party] [checked 2026-11-09] [rust-postgres postgres-protocol/src/types/mod.rs](https://raw.githubusercontent.com/sfackler/rust-postgres/master/postgres-protocol/src/types/mod.rs)
- numeric: u16 ndigits, i16 weight (power of 10000 of first digit), u16 sign (0x0000 positive, 0x4000 negative, 0xC000 NaN, 0xD000 +Inf, 0xF000 -Inf), i16 dscale, then ndigits × i16 base-10000 digits most-significant first; pgx's decoder "allocates a big.Int for the accumulator and a new big.Int for each four-digit group" and loops once per decimal digit when adjusting dscale. — [third party] [checked 2026-11-09] [pgx pgtype/numeric.go](https://raw.githubusercontent.com/jackc/pgx/master/pgtype/numeric.go)
- interval: i64 microseconds, i32 days, i32 months = exactly 16 bytes. — [third party] [checked 2026-11-09] [pgx pgtype/interval.go](https://raw.githubusercontent.com/jackc/pgx/master/pgtype/interval.go)

**COPY**
- CopyInResponse 'G' / CopyOutResponse 'H' / CopyBothResponse 'W': Int8 overall format (0 text, 1 binary), Int16 N columns, Int16×N per-column format codes; CopyData 'd' ("frontend chunks may split rows arbitrarily; backend sends one row per message"); CopyDone 'c'; CopyFail 'f' + message. — [vendor] [checked 2026-11-09] [54.7 Message Formats](https://www.postgresql.org/docs/current/protocol-message-formats.html)
- Copy-in flow: CopyInResponse -> CopyData* -> CopyDone/CopyFail -> CommandComplete/ErrorResponse; "Flush and Sync are ignored during copy-in". Copy-out: the frontend "cannot abort except by closing the connection or sending a cancel". — [vendor] [checked 2026-11-09] [54.2 Message Flow](https://www.postgresql.org/docs/current/protocol-flow.html)
- Binary COPY file: 11-byte signature `PGCOPY\n\377\r\n\0`, Int32 flags (bit 16 = OIDs, must be 0 now; bits 16–31 critical), Int32 header-extension length (currently 0); per tuple Int16 field count then per field Int32 length (-1 NULL) + data "in the same representation as the binary send function"; trailer Int16 -1; "no alignment padding"; "Binary is faster than text and CSV, but is less portable". Text format: tab delimiter, `\N` null, backslash escapes (`\b \f \n \r \t \v \digits \xdigits`), `\.` end marker. CSV: quote `"`, escape defaults to quote, NULL is unquoted empty string, `HEADER MATCH`. Options `ON_ERROR ignore`, `REJECT_LIMIT`, `LOG_VERBOSITY`, `FREEZE` (table must be created/truncated in the same subtransaction). Note: the page says "15 bytes of fixed fields" but the listed fields sum to 19. — [vendor] [checked 2026-11-09] [COPY reference](https://www.postgresql.org/docs/current/sql-copy.html)

**Notifications, cancel, limits**
- NotificationResponse 'A': Int32 PID, channel, payload; ParameterStatus 'S' name/value (tracked: `client_encoding, DateStyle, TimeZone, search_path, session_authorization`, ...); NotificationResponse "currently occurs only outside transactions, but frontends should accept it at any point". Cancel: open a new connection, send CancelRequest, "server processes it, closes the connection, and sends no reply". — [vendor] [checked 2026-11-09] [54.2 Message Flow](https://www.postgresql.org/docs/current/protocol-flow.html) and [54.7](https://www.postgresql.org/docs/current/protocol-message-formats.html)

**What the fast clients do, and measurements**
- asyncpg: "implementation of PostgreSQL server binary protocol"; "In our testing asyncpg is, on average, 5x faster than psycopg3" (geometric mean, June 2023, MagicStack/pgbench). — [third party] [checked 2026-11-09] [asyncpg README](https://raw.githubusercontent.com/MagicStack/asyncpg/master/README.rst)
- asyncpg 2016 benchmark post: "1M rows/s" reading all ~350 rows of `pg_type` repeatedly; "at least 3x faster" than psycopg2/aiopg on average; four queries (wide pg_type row; 1000 rows × 1 int; 100 rows × 1 KB bytea; 100 rows × int[100]); hardware Xeon E5-1620 v2, PG 9.5.2, asyncpg 0.5.2, psycopg2 2.6.2, lib/pq and pgx at 2016 commits, Node pg 6.0.0, single-threaded async; reasons: binary I/O protocol ("psycopg2 exchanges data in text format, which requires non-trivial parsing"), extensive prepared statements with cached per-statement I/O pipelines, "written almost entirely in Cython, with careful buffer management"; array query slower than Go lib/pq "because of the cost of creating and freeing Python tuples". — [third party] [checked 2026-11-09] [1M rows/s from Postgres to Python (Gel/MagicStack)](https://www.geldata.com/blog/m-rows-s-from-postgres-to-python)
- Timescale 2024 rerun of pgbench (PG 16.2, psycopg2 2.9.9 vs psycopg 3.1.18, t2.xlarge): rows/s psycopg2 | psycopg3 | psycopg3-async: pg_type 150,418 | 491,519 | 457,796; generate_series(1000) 626,674 | 1,250,967 | 1,286,341; 1 KB large_object 209,909 | 101,391 | 133,010; int[100] arrays 109,184 | 101,523 | 113,906; copyfrom 444,407 | 456,626 | 470,290; batch insert 13,257 | 4,933 | 11,041; `SELECT 1+1` 9,250 | 4,437 | 7,190 q/s. — [third party] [checked 2026-11-09] [Timescale psycopg2 vs psycopg3](https://www.tigerdata.com/blog/psycopg2-vs-psycopg3-performance-benchmark)
- psycopg3: "sends the query and the parameters to the server separately" (extended protocol, server-side binding); `ClientCursor` falls back to client-side merge + simple protocol; multi-statement queries fail with binary results and in pipeline mode; `psycopg[c]` and `psycopg[binary]` are the optional speed-ups. Pipeline mode is `with conn.pipeline():`, "experimental", requires libpq 14+, no COPY, no server-side cursors; `executemany()` uses pipeline mode internally since 3.1; implicit transaction until Sync even in autocommit. — [vendor] [checked 2026-11-09] [psycopg3 from_pg2](https://www.psycopg.org/psycopg3/docs/basic/from_pg2.html), [psycopg3 pipeline](https://www.psycopg.org/psycopg3/docs/advanced/pipeline.html)
- pgJDBC defaults: `binaryTransfer=true` (only with server-side prepared statements), `prepareThreshold=5` (server-side prepare on 5th execution; -1 forces immediately), `preferQueryMode=extended`, `defaultRowFetchSize=0` ("fetches all rows in one trip"), `preparedStatementCacheQueries=256`, `preparedStatementCacheSizeMiB=5`, `reWriteBatchedInserts=false` ("can give 2-3x speedups"; merged rows capped at `min(65535 / parametersPerRow, 32768)`), `maxSendBufferSize=8192`, `tcpNoDelay=true`, `tcpKeepAlive=false`, `sslNegotiation=postgres` (`direct` needs server 17+), `channelBinding=prefer`, `gssEncMode=allow`, `adaptiveFetch=false`. — [vendor] [checked 2026-11-09] [pgJDBC connection parameters](https://jdbc.postgresql.org/documentation/use/)
- pgx text-vs-binary bytes on the wire (100,000 rows of 2×uuid, 2×timestamp, int4, int8, bool; measured with strace): pgx simple protocol 17.7 MB, pgx extended/binary 9.6 MB (-46%), lib/pq 17.8 MB in both modes ("pq always receives results as text"); savings dominated by uuid 36 -> 16 bytes and timestamp 26 -> 8 bytes. — [third party] [checked 2026-11-09] [boosterkrd, Dec 2025](https://boosterkrd.github.io/2025/12/20/golang-postgresql-binary-protocol.html)
- pgx author (2020) reported that selecting text-type values in binary format was "significantly slower" than text in a 1,000-row × 5 text-column test (profiling thread, no rows/s given). — [third party] [checked 2026-11-09] [pgsql list thread](https://postgrespro.com/list/thread-id/2492734)
- A 2006 pgJDBC profile found hotspots in `org.postgresql.core.Encoding.decode` and suspected "excessive new String creation" per row. — [third party] [checked 2026-11-09] [pgsql-jdbc 2006](https://postgresql.org/message-id/20060823195511.93081.qmail%40web32004.mail.mud.yahoo.com)

### Inferences
- Bytes per row, 10-column mixed row (int4, int8, float8, numeric(12,2), bool, timestamp, date, uuid, varchar(20 ASCII), text(100 ASCII)). DataRow framing is 7 bytes (type + Int32 len + Int16 ncols) plus 4 bytes per column = 47 bytes. Binary payload ≈ 4+8+8+(8+3·2)+1+8+4+16+20+100 = 183 bytes -> ≈230 bytes/row. Text payload ≈ 7+12+17+13+1+26+10+36+20+100 = 242 -> ≈289 bytes/row. Binary saves ~20% for this mix; for narrow uuid/timestamp-heavy rows the saving approaches the 46% measured above. Strings dominate either way; the per-column Int32 length is the fixed overhead a driver cannot avoid (4 bytes × ncols).
- Syscalls per query: all of Parse+Bind+Describe+Execute+Sync fit in one `write`; the response needs as many `read`s as the result size divided by the driver's read-buffer size (DataRows have no server-side packetization beyond message framing, unlike MySQL/TDS). Pipelining amortizes the write and the ReadyForQuery wait across queries. Direct SSL (PG17, ALPN `postgresql`) removes one RTT at connect; 3.2 does not change per-query cost.
- Allocations per row: with binary formats and a driver that keeps the DataRow in a reference-counted read buffer (as tokio-postgres does with `Bytes`), fixed-width columns decode in place with zero allocation; text/bytea can be borrowed as slices; `numeric` is the one common type whose binary form needs real arithmetic (base-10000 digits) and, in pgx, allocates big.Int per 4 digits. Arrays and composites are decodable without per-element allocation only if the driver exposes a lazy view.
- Protocol-level limits that bound a design: Int16 column count and Int16 parameter-format/param counts in Bind and RowDescription (max 65,535); pgJDBC's `min(65535 / parametersPerRow, 32768)` batch cap is a direct consequence. The Int32 length field bounds a message at 2 GiB; the server's actual 1 GB cap was not confirmed by a fetched page (see Gaps).

### Gaps
- The protocol-changes page fetched (54.10) covers only 2.0 -> 3.0; the 3.0 -> 3.2 differences were taken from the 54.1 version table and 54.7; a complete 3.2 diff list from the official docs was not found.
- The "max message length 1 GB" limit is not stated on any fetched page; verify in the server source (`PqRecvMessage`/`MaxAllocSize`).
- jsonb binary format (1-byte version prefix + JSON text), json/money/timestamp infinity sentinels were not in the fetched tokio-postgres file; verify against `src/backend/utils/adt/jsonb.c` (`jsonb_send`) before relying on them.
- No current (2024–2026) published rows/s numbers for pgx or tokio-postgres were found; the only pgx figures were a vendor benchmark by a competing Rust driver (QAIL, 3,903 q/s wide rows) which should not be relied on.
- The magic.io domain is dead; the 2016 asyncpg post is now at geldata.com and its per-driver charts are images not extractable as text.

## MySQL / MariaDB client/server protocol

### Takeaway
MySQL's protocol is packet-oriented (3-byte little-endian length + 1-byte sequence id, 16 MiB max per packet, so large payloads split) with a text protocol (COM_QUERY, every value a length-encoded string) and a binary protocol (COM_STMT_PREPARE/EXECUTE, fixed-width little-endian numerics, NULL bitmap with a 2-bit offset). Decoding cost is dominated by length-encoded integers and, in text mode, string-to-number parsing; MySQL has no protocol-level pipelining (the server treats a pipeline as unrelated requests and the sequence id resets per command), while MariaDB adds COM_STMT_BULK_EXECUTE, metadata-skipping and extended capability bits that its connectors exploit to post 2–30x gains on their own benchmarks. caching_sha2_password is the default since 8.0 and mysql_native_password is removed from the 9.x server.

### Cited Findings

**Framing, handshake, capabilities**
- Connection phase: server sends Protocol::Handshake (may be ERR), client may send SSLRequest, then HandshakeResponse; the server's default plugin challenge is sent in the handshake "to save a round trip"; mismatches produce AuthSwitchRequest; extra server packets are AuthMoreData "prefixed with 0x01, so they can't be confused with ERR (0xFF) or OK (0x00)"; mysql_native_password default 4.1–5.7, caching_sha2_password default from 8.0, "mysql_native_password was removed from the 9.0 server" (client library still has it as a plugin); the 9.0 server rejects pre-4.1 clients. — [vendor] [checked 2026-11-09] [MySQL Connection Phase](https://dev.mysql.com/doc/dev/mysql-server/latest/page_protocol_connection_phase.html)
- MariaDB initial handshake layout: protocol version (1), server version (NUL string), connection id (4), auth-plugin-data part 1 (8), reserved (1), capabilities part 1 (2), collation (1), status (2), capabilities part 2 (2), plugin-data length (1), filler (6), then 4 filler bytes if CLIENT_MYSQL else MariaDB capabilities part 3, auth-plugin-data part 2 (max(12, len-9)) + reserved byte, plugin name. SSLRequest = 4 capability + 4 max packet + 1 charset + 19 reserved + 4 extended capabilities (or reserved). MariaDB 10.x prefixes its version string with `5.5.5-`; 11.0+ does not. Native password token = `SHA1(passwd) ^ SHA1(seed + SHA1(SHA1(passwd)))`. — [vendor] [checked 2026-11-09] [MariaDB KB: Connection](https://mariadb.com/kb/en/connection/)
- Capability bits (MariaDB KB): CLIENT_MYSQL 0x1, FOUND_ROWS 0x2, CONNECT_WITH_DB 0x8, COMPRESS 0x20, LOCAL_FILES 0x80, PROTOCOL_41 0x200, SSL 0x800, TRANSACTIONS 0x2000, SECURE_CONNECTION 0x8000, MULTI_STATEMENTS 0x10000, MULTI_RESULTS 0x20000, PS_MULTI_RESULTS 0x40000, PLUGIN_AUTH 0x80000, CONNECT_ATTRS 0x100000, PLUGIN_AUTH_LENENC_CLIENT_DATA 0x200000, SESSION_TRACK 0x800000, DEPRECATE_EOF 0x1000000, OPTIONAL_RESULTSET_METADATA 0x2000000 (not used by MariaDB), ZSTD 0x4000000. MariaDB-only bits above 31: MARIADB_CLIENT_PROGRESS 1<<32, COM_MULTI 1<<33 (deprecated), STMT_BULK_OPERATIONS 1<<34, EXTENDED_METADATA 1<<35, CACHE_METADATA 1<<36 ("permits skipping metadata"), BULK_UNIT_RESULTS 1<<37. — [vendor] [checked 2026-11-09] [MariaDB KB: Connection](https://mariadb.com/kb/en/connection/)
- Compression is a separate layer enabled only when the server announces CLIENT_COMPRESS or CLIENT_ZSTD_COMPRESSION_ALGORITHM and the client's flags match; a zstd client sends one extra byte (level) in HandshakeResponse; "If both CLIENT_COMPRESS and CLIENT_ZSTD_COMPRESSION_ALGORITHM are set, zlib is used." — [vendor] [checked 2026-11-09] [MySQL Compression](https://dev.mysql.com/doc/dev/mysql-server/latest/page_protocol_basic_compression.html)
- MariaDB ed25519 plugin: client plugin `client_ed25519`, "hashes and signs the password using the Elliptic Curve Digital Signature Algorithm (ECDSA)"; server stores a hash created by the `ed25519_password` UDF; shipped but not installed by default (`INSTALL SONAME 'auth_ed25519'`); supported by Connector/C, ODBC, J, Node.js and MySqlConnector (.NET). — [vendor] [checked 2026-11-09] [MariaDB ed25519 plugin](https://mariadb.com/docs/server/reference/plugins/authentication-plugins/authentication-plugin-ed25519)

**Prepared statements and the binary protocol**
- COM_STMT_PREPARE: `0x16` + query. COM_STMT_PREPARE_OK: status 0x00, statement_id int4, num_columns int2, num_params int2, reserved int1, warning_count int2 (if length >= 12), metadata_follows int1 only with CLIENT_OPTIONAL_RESULTSET_METADATA; followed by num_params column definitions (+EOF unless DEPRECATE_EOF) then num_columns column definitions (+EOF). `LOAD DATA` cannot be prepared. — [vendor] [checked 2026-11-09] [COM_STMT_PREPARE](https://dev.mysql.com/doc/dev/mysql-server/latest/page_protocol_com_stmt_prepare.html)
- COM_STMT_EXECUTE: `0x17`, statement_id int4, flags int1 (cursor type), iteration_count int4 (always 1); if params: parameter_count lenenc (only with CLIENT_QUERY_ATTRIBUTES), NULL bitmap `(parameter_count + 7) / 8` bytes offset 0, new_params_bind_flag int1, per param type int2 (low byte type, MSB = unsigned) and name lenenc (only with QUERY_ATTRIBUTES), then values. Worked example is an 18-byte payload for one VARCHAR param `"foo"`. — [vendor] [checked 2026-11-09] [COM_STMT_EXECUTE](https://dev.mysql.com/doc/dev/mysql-server/latest/page_protocol_com_stmt_execute.html)
- Binary resultset: column-count packet (lenenc, 1 byte under 251), column definition packets (catalog, schema, table, org_table, name, org_name as lenenc strings; fixed block marker 0x0c then charset int2, column length int4, type int1, flags int2, decimals int1 + 2 filler), terminator EOF (5-byte payload) or OK with DEPRECATE_EOF. Binary row: header 0x00, NULL bitmap `(column_count + 7 + 2) / 8` bytes with offset 2 (byte `(i+2)/8`, bit `(i+2)%8`), then only the non-NULL values. Fixed sizes: TINY 1, SHORT/YEAR 2, LONG/INT24 4, LONGLONG 8, FLOAT 4, DOUBLE 8; DECIMAL/NEWDECIMAL, all string/BLOB/JSON/BIT/GEOMETRY types are lenenc strings; DATE/DATETIME/TIMESTAMP = 1 length byte + 0/4/7/11 bytes (year int2, month, day, [hour, minute, second], [microseconds int4]); TIME = 1 length byte + 0/8/12 bytes (is_negative, days int4, h, m, s, [micro int4]). Example 1-column row for "foobar": 9-byte payload = 1 header + 1 bitmap + 7. — [vendor] [checked 2026-11-09] [Binary Protocol Resultset](https://dev.mysql.com/doc/dev/mysql-server/latest/page_protocol_binary_resultset.html)
- WL#3359 (MySQL worklog) notes that prepared statements cost "an extra round trip for the prepare phase" and that "using MySQL's binary protocol for result sets is almost always good for performance". — [vendor] [checked 2026-11-09] [WL#3359](https://dev.mysql.com/worklog/task/?id=3359)

**Bulk and local-infile paths**

### Inferences
- Bytes per row for the 10-column mixed row. Binary row: 4 packet header + 1 (0x00) + 2 bitmap + 4+8+8+(1+13 decimal text)+1+(1+11 datetime)+(1+4 date)+(1+16 binary(16) uuid)+(1+20)+(1+100) ≈ 198 bytes. Text row: 4 + Σ(1 + text length) ≈ 4 + 10 + 242 = 256 bytes. Binary saves ~23%, mostly on ints/doubles/datetime; DECIMAL is still text in both modes (a decode-cost trap for numeric-heavy workloads).
- Decode hot spots: (a) the lenenc integer prefix on every string column and on every text-mode value; (b) text-mode `atoi`/`strtod` per numeric column; (c) the 16 MiB packet split, which forces a reassembly path for large rows; (d) per-row packet headers (4 bytes/row plus one header per 16 MiB), so a driver should read into a large buffer and walk packets in memory rather than one `read` per packet.
- Syscalls per query: text COM_QUERY is one write; the prepared path costs a separate COM_STMT_PREPARE round trip unless the statement is cached (all major drivers keep an LRU of prepared statements per connection). Because the protocol has no pipelining, a Rust driver can still batch writes (as MariaDB Connector/J 3.1 does) but must consume each result set fully before reading the next; MariaDB's bulk command is the only true server-side batch path.
- Compression: with zlib/zstd the inner packets are re-framed inside a 7-byte compressed-packet header, which adds a copy; worthwhile only on bandwidth-constrained links.

## Microsoft SQL Server: TDS 7.4 and TDS 8.0

### Takeaway
TDS is a packetised token stream: 8-byte packet headers (default 4,096-byte packets, negotiable 512–32,767), a PRELOGIN option table, a LOGIN7 fixed header with offset/length string pointers (UCS-2LE, password nibble-swapped and XOR 0xA5), then responses as tokens (COLMETADATA 0x81, ROW 0xD1, NBCROW 0xD2 with a null bitmap, DONE 0xFD/0xFE/0xFF). TDS 7.x tunnels the TLS handshake inside PRELOGIN packets; TDS 8.0 (SQL Server 2022+) does TLS first with ALPN `tds/8.0` and ignores the PRELOGIN encryption byte. The dominant decode costs are UCS-2 -> UTF-8 conversion for every N-string, collation-codepage conversion for VARCHAR, PLP chunk reassembly for MAX types, and the per-packet header strip.

### Inferences
- Bytes per row, 10-column mixed row as a ROW token: 1 token byte + INTN(4) 5 + INTN(8) 9 + FLTN 9 + DECIMALN(12,2) 1+1+8 = 10 + BITN 2 + DATETIME2N(7) 9 + DATEN 4 + GUID 17 + VARCHAR(20) 2+20 = 22 + NVARCHAR(100) 2+200 = 202 => ≈290 bytes; with VARCHAR(100) instead of NVARCHAR ≈190 bytes. UCS-2 doubles every N-string and then forces a transcode to UTF-8, so TDS is the only protocol here where string columns cost both bandwidth and CPU on the client. NBCROW only saves the per-column length byte for NULL columns.
- Packetisation: a 1 MB result at the 4,096-byte default is ~256 packets, each with an 8-byte header that must be stripped and whose boundary may fall mid-token, so the token parser must operate on a logical byte stream (go-mssqldb and tiberius both do). Raising the packet size to 32,767 cuts header overhead 8x and reduces fragmentation; TLS-wrapped connections are capped at 16,383 in go-mssqldb.
- Syscalls per query: SQL Batch or RPC is a single write (multi-packet if > packet size); reads scale with result size / read buffer, not with packet count, provided the driver reads into a buffer larger than the packet size. TDS 7.x costs one extra RTT for PRELOGIN before TLS; TDS 8.0 collapses that into the TLS handshake.
- Allocation per row: fixed-width numerics decode in place; every NVARCHAR requires a UTF-16LE -> UTF-8 conversion (allocation + ~1 byte/char saved), every VARCHAR with a non-UTF-8 collation needs a code-page table lookup, and PLP values need chunk concatenation unless exposed as a chunk iterator. DECIMAL needs a 128-bit integer scale, not big-integer arithmetic (max 16 bytes).

## SQLite: in-process C API

### Takeaway
SQLite has no wire protocol; the cost model is FFI calls and copies. The documented accessor rules (call `sqlite3_column_type` before any accessor, `column_text/blob` before `column_bytes`, pointers valid only until the next step/reset/finalize or a type conversion) mean a minimum of two or three FFI calls per column per row, plus one copy if the value must outlive the step. Serialized is the default threading mode and takes a mutex per API call; `SQLITE_OPEN_NOMUTEX` (multi-thread) removes it per connection. Rust projects overwhelmingly bundle the amalgamation (rusqlite's `bundled` feature, SQLite 3.54.0 as of rusqlite 0.41). The pure-Rust rewrite (Turso, ex-Limbo) targets SQLite 3.50.4 compatibility, runs in production at a few organisations, is pre-1.0, and still lists Postgres compatibility, encryption and FTS as experimental.

### Cited Findings
- Key C functions: `sqlite3_prepare_v2/v3` (`v3` adds `SQLITE_PREPARE_PERSISTENT`), `sqlite3_step`, `sqlite3_reset` (keeps bindings), `sqlite3_clear_bindings`, `sqlite3_bind_*` with `SQLITE_STATIC` (zero-copy; buffer must outlive the statement use) vs `SQLITE_TRANSIENT` (copied), `sqlite3_bind_zeroblob64`, `sqlite3_bind_pointer`, `sqlite3_column_count/name/type/int/int64/double/text/blob/bytes`, incremental blob I/O `sqlite3_blob_open/read/write/bytes/reopen/close`, `sqlite3_config(SQLITE_CONFIG_SINGLETHREAD|MULTITHREAD|SERIALIZED)` before `sqlite3_initialize`, `sqlite3_open_v2` flags `SQLITE_OPEN_NOMUTEX`/`FULLMUTEX`, `sqlite3_db_config`, `sqlite3_vfs_register/find/unregister`, `sqlite3_carray_bind` (carray extension), `sqlite3_serialize/deserialize`. — [vendor] [checked 2026-11-09] [SQLite C API function list](https://www.sqlite.org/c3ref/funclist.html)
- Result accessors: "The pointers returned are valid until a type conversion occurs as described above, or until sqlite3_step() or sqlite3_reset() or sqlite3_finalize() is called"; "The value returned by sqlite3_column_type() is only meaningful if no automatic type conversions have occurred"; conversions BLOB->TEXT add a zero terminator, UTF-8<->UTF-16 reallocate and invalidate earlier pointers; call `column_text` then `column_bytes` (never mix with `_bytes16`); `column_blob` returns NULL for a zero-length blob; only `_blob/_text/_text16/_bytes/_bytes16` can fail with OOM and then look like NULL (check `sqlite3_errcode`). — [vendor] [checked 2026-11-09] [sqlite3_column_blob et al.](https://www.sqlite.org/c3ref/column_blob.html)

- Turso Database (Rust rewrite): "runs in production today at multiple organizations" (Turso Cloud, Kin, Spice.ai); not yet 1.0, keep independent backups; targets SQLite 3.50.4 for SQL dialect, file format and C API, "compatibility is not yet 100%"; `BEGIN CONCURRENT` MVCC writes; io_uring on Linux; bindings for Rust, JS, Python, Go, Java/JDBC, .NET, WASM; Postgres compatibility, encryption at rest, DBSP incremental computation, tantivy FTS and multi-process WAL coordination are experimental; MIT licensed; replaces libSQL as the project's direction. — [third party] [checked 2026-11-09] [Turso README](https://raw.githubusercontent.com/tursodatabase/turso/main/README.md)
- Third-party status summaries (2024–2026) describe the rewrite as beta, not a drop-in replacement, with libSQL (C fork) still powering Turso Cloud. — [third party] [checked 2026-11-09] [Better Stack guide](https://betterstack.com/community/guides/databases/turso-explained/); [Turso announcement](https://turso.tech/blog/turso-the-next-evolution-of-sqlite)

### Inferences
- FFI calls per row: `sqlite3_step` (1) + per column `sqlite3_column_type` (1) + accessor (1) + `sqlite3_column_bytes` for text/blob (1) => for 10 columns ≈ 21–31 calls per row. Ways to cut this: skip `column_type` when the declared affinity is trusted (unsafe for dynamic typing), read `column_int64/double` directly for numeric columns (1 call), and copy text/blob only when the caller needs ownership beyond the next `step`. A Rust API that yields borrowed `&str`/`&[u8]` tied to the row lifetime gives zero-copy reads.
- Serialized mode's per-call mutex is pure overhead when a Rust `Connection` is already `!Sync`; open with `SQLITE_OPEN_NOMUTEX` (multi-thread) and enforce exclusivity in Rust.
- Bundling is the de facto standard in Rust (rusqlite, sqlx, Turso's own bindings): it pins the version, allows compile-time options (`SQLITE_THREADSAFE=2`, `SQLITE_DEFAULT_WAL_SYNCHRONOUS`, omitting features), and avoids the >= 3.45.3 dynamic-linking floor. The cost is build time and binary size.
- A "pure Rust SQLite" is not yet a safe production target for a general driver in 2026; the practical option is a trait-level abstraction that can host either `libsqlite3-sys` or Turso's crate behind the same API.

### Gaps
- No published measurements of FFI overhead per `sqlite3_column_*` call or of serialized-mode mutex cost were found; the SQLite pages do not quantify it.
- Turso's COMPAT.md (indexes, triggers, views, VACUUM, savepoints) was not fetched; the README does not enumerate them.
- Default threading mode of the amalgamation as shipped (vs. the documented `SQLITE_THREADSAFE=1` default when the macro is absent) was not confirmed separately.

## Oracle (Net8/TNS, TTC), DuckDB, ClickHouse, and the HTTP+Arrow warehouses

### Takeaway
Oracle's wire protocol remains undocumented, but Oracle itself now ships "thin" reimplementations in Python (python-oracledb, DB 12.1+), Node.js, and since August 2026 Go (`github.com/oracle/go-oracledb`, UPL-1.0, DB 19c+), and third-party MIT-licensed go-ora has implemented it independently for years; I found no legal analysis either way. DuckDB and SQLite are in-process (DuckDB's C API is "modeled somewhat following the SQLite C API"; the v2 API is explicitly unstable, and the row-oriented `duckdb_value_*` accessors are deprecated in favour of 2048-row data chunks and the appender). ClickHouse's native TCP protocol is columnar (blocks of name/type/values), little-endian, with an optional LZ4/ZSTD compression frame checksummed by CityHash128. Snowflake, Databricks and BigQuery all deliver large results as Arrow batches fetched in parallel from cloud storage or gRPC streams, and all three report multi-x speedups over their row/JSON paths.

### Cited Findings

**Oracle**
- python-oracledb Thin mode (default) "connects directly to Oracle Database 12.1 or later" and "is established directly by python-oracledb over the Oracle Net protocol"; Thick mode loads Oracle Client 19+ and can reach DB 11.2+. — [vendor] [checked 2026-11-09] [python-oracledb introduction](https://python-oracledb.readthedocs.io/en/latest/user_guide/introduction.html)

**ClickHouse native TCP protocol**
- Packet type is a VarUInt; fixed-width ints are little-endian; String = VarUInt length + bytes; chunked framing (rev 54470+) = u32 LE size + payload, 0 ends a packet. ClientHello (type 0): client_name, version_major/minor, protocol_version, database, user, password; Addendum after rev 54458. **HTTP + Arrow warehouses**

### Inferences
- Oracle: a Rust thin driver is technically feasible (Oracle's own three thin drivers and go-ora prove the protocol can be reimplemented from observation) but there is no public specification; the realistic approaches are (a) port the structure of python-oracledb's `impl/thin` and go-oracledb's `ttc` packages, or (b) wrap OCI/ODPI-C (Thick) at the cost of a mandatory 19c+ client install and loss of pure-Rust builds. Thin fetch cost is governed by `arraysize`/`prefetchrows` round-trips rather than per-row encoding.
- DuckDB: a Rust driver should consume `duckdb_data_chunk` vectors (2048 rows per chunk by default, validity bitmask, inlined-or-pointer strings) and feed inserts through the appender or `duckdb_append_data_chunk`; the deprecated row accessors are the slow path. Arrow interop via the C Data Interface is the natural zero-copy bridge but its functions sit in the unread tail of the reference (see Gaps).
- ClickHouse: because data arrives columnar, per-row cost is near zero and decode cost is per column per block (one LZ4 decompress + checksum per ~1 MB frame, then fixed-width slices). The Nullable null-map and offsets layout make zero-copy column views straightforward in Rust. Bytes per row for the 10-column mixed row ≈ 4+8+8+8(Decimal64)+1+8(DateTime64)+2(Date)+16+21+101 ≈ 177 bytes before compression, with no per-row framing at all.
- Warehouses: the client's job is HTTP(S) fan-out, LZ4/zstd decompression and Arrow IPC parsing; Arrow is native in all three, so a Rust driver should expose Arrow `RecordBatch`es directly rather than rows.

### Gaps
- No Oracle legal analysis or Oracle statement about third-party protocol implementations was found; the position must be treated as unknown. Oracle Net/TTC message formats are not publicly documented; I did not fetch python-oracledb or go-oracledb source.
- DuckDB Arrow functions (`duckdb_query_arrow`, `duckdb_to_arrow`, `duckdb_arrow_scan`) and the `duckdb_string_t` inline threshold are in the unread final third of the C API page; whether `libduckdb` is distributed static or shared was not stated on the fetched pages.
- ClickHouse default TCP port and `min_compress_block_size` were not confirmed from the fetched pages.
- Snowflake's exact result-chunk mechanics (inline first chunk, S3/Azure chunk URLs, chunk sizes) and Databricks' Thrift inline-Arrow path for small results were not on the fetched pages; BigQuery quotas (max streams, response size) are on a separate limits page not fetched.

## Arrow Flight SQL

### Takeaway
Flight SQL layers SQL semantics (protobuf commands for queries, prepared statements and catalog metadata) over Arrow Flight's gRPC RPCs (GetFlightInfo -> endpoints/tickets -> DoGet streams of record batches; DoPut for parameter batches and uploads). It is positioned as a wire protocol that JDBC/ODBC drivers can sit on, not a replacement API. Published speedups over ODBC/JDBC range from 15–30x (Dremio, Teradata, TU Delft) up to 84x in multi-stream configurations, but single-stream queries measured 10–15% slower than JDBC at Teradata, and uploads only reach parity.

### Cited Findings
- Clients build a protobuf command (e.g. CommandStatementQuery, CommandGetTables) and send it via GetFlightInfo or GetSchema; GetFlightInfo returns FlightInfo with one or more endpoints each carrying an opaque ticket; DoGet(ticket) streams Arrow record batches; multiple endpoints enable parallel fetch; prepared statements are created via DoAction (opaque handle), parameters uploaded with DoPut (CommandPreparedStatementUpdate returns affected rows), closed via ActionClosePreparedStatementRequest; Flight already provides encryption and authentication; row-based APIs "force columnar databases to transpose data twice"; "Arrow Flight is already as much as 20x faster" than PyODBC (Dremio talk); JDBC driver was in progress and ODBC a possible future item at publication (Feb 2022, Arrow 7.0). — [vendor] [checked 2026-11-09] [Introducing Apache Arrow Flight SQL](https://arrow.apache.org/blog/2022/02/16/introducing-arrow-flight-sql/)
- TU Delft / IBM benchmark (arXiv 2204.03032, Ahmad, Al Ars, Hofstee, April 2022): Arrow Flight up to 6,000 MB/s DoGet and 4,800 MB/s DoPut, up to 95% of available bandwidth on Mellanox ConnectX-3/Connect-IB, uses up to half the system cores for bidirectional traffic; Flight on Dremio "performs 20x and 30x better as compared to turbodbc and ODBC connections respectively". — [third party] [checked 2026-11-09] [arXiv 2204.03032](https://arxiv.org/abs/2204.03032)
- Dremio's 2021 GA post reported "greater than 15x performance improvements over ODBC" on a simple SELECT * over Parquet "even without parallelization". A Dremio community user reported no gap (both ~45 s for 500 MB) using the sample Python client. — [vendor]/[third party] [checked 2026-11-09] [Dremio Flight post](https://www.dremio.com/blog/eliminating-data-exports-for-data-science-with-apache-arrow-flight); [community thread](https://community.dremio.com/t/run-time-comparison-arrow-flight-vs-odbc/7285)
- Teradata (Aug 2026): parallel multi-stream reads 15–30x JDBC on standard hardware, 47–84x on higher-tier AWS; sustained 270–350 MB/s stable to 20 concurrent users against an ~870 MB/s database I/O ceiling; single-stream direct queries (e.g. ORDER BY) 30.4 vs 33.8 MB/s (100 MB), 39.9 vs 46.2 (500 MB), 40.3 vs 47.5 (~780 MB), i.e. Arrow 10–15% slower "because it adds a format conversion and a gRPC/TLS hop"; DoPut uploads near parity (1.4% overhead at 1 GB); recommended 16 GB direct memory per driver node (2 GB failed at 5 sessions, 64 GB ran 5–23% slower). — [vendor] [checked 2026-11-09] [How fast is Arrow Flight SQL with Teradata](https://www.teradata.com/insights/data-architecture/how-fast-is-arrow-flight-sql-with-teradata)

### Inferences
- For a Rust driver, Flight SQL is the one protocol where the server hands over Arrow IPC bytes directly; the client's per-row cost collapses to IPC batch validation and gRPC/HTTP2 frame handling. The gains in published numbers come from parallel endpoints and avoiding row transposition; a single-stream, latency-bound workload gains nothing and pays the gRPC+TLS hop.
- The protocol fits analytical fetch, not OLTP point queries: GetFlightInfo + DoGet is two RPCs minimum per query versus one round trip in PG/MySQL/TDS.

### Gaps
- No Voltron Data publication with measured numbers was found in this pass; the Dremio/Teradata/TU Delft figures are vendor- or vendor-adjacent and use varied hardware and data sizes, so they are not directly comparable.
- Current (2025–2026) status of the Flight SQL JDBC and ODBC drivers was not re-verified.

## Cross-cutting: TCP_NODELAY and Nagle, TLS record overhead, bytes per row, where client time goes, default fetch sizes

### Takeaway
Request/response database protocols must either set TCP_NODELAY or write each message in a single `write`, otherwise Nagle plus delayed ACK adds ~40 ms per exchange on Linux. TLS 1.3 adds a fixed per-record cost (5-byte header + 1-byte inner type + 16-byte AEAD tag with ≤16 KiB plaintext), which is negligible for bulk rows but matters for small pipelined messages. For a 10-column mixed row the binary encodings come out at roughly 180–230 bytes (ClickHouse < MySQL binary < PostgreSQL binary < TDS with N-strings), text forms at 250–290 bytes, and the measured 46% saving for uuid/timestamp-heavy rows is the upper end. The published profiles that exist (asyncpg, pgJDBC, go-sql-driver) all put the time in per-value parsing and per-row object/`interface{}` allocation, not in syscalls, once the driver reads into a large buffer.

### Cited Findings
- Nagle + delayed ACK: "a sender that uses Nagle and a receiver that uses Delayed ACK may wait for an ACK that is delayed, adding ~40 ms to each request"; Linux `TCP_DELACK_MIN` 40 ms, `TCP_DELACK_MAX` 200 ms; the fix is TCP_NODELAY on the sender; "TCP_NODELAY does not control ACK generation, instead it modifies the Nagle algorithm behavior when sending data packets" (LKML); the stall arises mainly when one application message is split across several writes. — [third party] [checked 2026-11-09] [OneUptime Nagle debugging](https://oneuptime.com/blog/post/2026-03-20-debug-tcp-nagle-algorithm-delays/view); [LKML](https://lkml.indiana.edu/hypermail/linux/kernel/0507.2/0969.html); [HN discussion](https://news.ycombinator.com/item?id=10607422)
- pgJDBC sets `tcpNoDelay=true` by default and buffers up to `maxSendBufferSize=8192` bytes before sending. — [vendor] [checked 2026-11-09] [pgJDBC parameters](https://jdbc.postgresql.org/documentation/use/)
- TLS record size: the protocol limit is 2^14 (16,384) octets of plaintext for TLS 1.2 and earlier, 2^14+1 for TLS 1.3 because the limit includes the content-type byte; TLS 1.3 "reduces the allowed expansion to 256 octets"; in earlier versions expansion is "typically only 16 octets" (plus 1–256 of block padding); the `record_size_limit` extension lets endpoints negotiate smaller records. — [vendor/IETF] [checked 2026-11-09] [RFC 8449](https://www.rfc-editor.org/rfc/rfc8449.html)
- RFC 8446 (TLS 1.3) record protocol "divides traffic up into a series of records, each of which is independently protected using the traffic keys"; the record-layer section was beyond the fetched portion. — [vendor/IETF] [checked 2026-11-09] [RFC 8446](https://www.rfc-editor.org/rfc/rfc8446.html)
- Measured text vs binary bytes (PostgreSQL, 100k rows of 2 uuid + 2 timestamp + int4 + int8 + bool): 17.7 MB text vs 9.6 MB binary (-46%). — [third party] [checked 2026-11-09] [boosterkrd 2025](https://boosterkrd.github.io/2025/12/20/golang-postgresql-binary-protocol.html)
- Where time goes (published profiles): asyncpg found text parsing and Python tuple creation/free dominate; pgJDBC 2006 profile found `Encoding.decode` and String creation; go-sql-driver found `[]byte` -> `interface{}` boxing at ~32 bytes per string column per row; Boost.MySQL concluded correctly implemented binary-protocol clients converge on the same throughput. — see citations in the PostgreSQL and MySQL sections above.
- Default fetch sizes and batching knobs found: pgJDBC `defaultRowFetchSize=0` (all rows), `prepareThreshold=5`; python-oracledb `arraysize=100`, `prefetchrows=2`, statement cache 20; ClickHouse `max_block_size=65409`; Databricks Cloud Fetch 20 MB Arrow chunks with a 1 MB inline threshold; Snowflake batch size "set by Snowflake's back end"; libpq pipelining flushes on `PQpipelineSync`/`PQflush` only. — [vendor] see the per-section citations above.

### Inferences
- Bytes per row summary for the 10-column mixed row (int4, int8, float8, decimal(12,2), bool, timestamp, date, uuid, varchar(20), text(100), ASCII strings), including per-row framing: ClickHouse native ≈177 (no per-row framing; columnar), MySQL binary ≈198, PostgreSQL binary ≈230, TDS ROW with VARCHAR ≈190 / with NVARCHAR ≈290, MySQL text ≈256, PostgreSQL text ≈289. Per-column overhead is 4 bytes (PG), 1 byte lenenc for strings only (MySQL), 1–2 length bytes (TDS), 0 (ClickHouse). These are arithmetic from the documented layouts, not measurements.
- Syscalls per query (steady state, prepared statement, result fits the read buffer): PG 1 write + 1 read; MySQL 1 write + 1 read (plus a prepare round trip on cache miss); TDS 1 write + ceil(result / read buffer) reads regardless of 4 KiB packets if the buffer is large; ClickHouse 1 write + reads per compressed frame (~1 MB); SQLite 0. With TLS each `write` becomes at least one record (22-byte fixed overhead with AES-GCM: 5 + 1 + 16); a driver should coalesce all messages of a request into one record and avoid flushing per message.
- Allocation per row floor: zero for fixed-width binary columns when values are decoded in place from a shared buffer (PG binary, MySQL binary, TDS numerics, ClickHouse); one allocation per string column only when ownership must outlive the buffer; unavoidable transcoding allocations for TDS N-strings (UTF-16LE) and non-UTF-8 VARCHAR collations; arithmetic allocations for PG `numeric` if decoded to arbitrary precision (avoidable with a fixed 128-bit fast path for ≤ 38 digits).
- Design consequence: the protocol families split into (1) row-framed with per-column lengths (PG, MySQL, TDS) where the win is binary formats + zero-copy row views + pipelining/batching, and (2) columnar/Arrow (ClickHouse, Flight SQL, warehouse Cloud Fetch) where the win is handing out column slices or Arrow batches and never materialising rows.

### Gaps
- No primary-source profile (flamegraph or perf output) of a modern Rust/Go/C driver's hot path was found; the "where time goes" evidence is from 2006–2016 profiles and 2024–2026 benchmarks without profiles.
- RFC 8446's record-layer section (5-byte header, 2^14 limit, AEAD tag, 2^24.5 AES-GCM record limit) was not reached in the fetched text; the 22-byte per-record figure is derived from RFC 8449's statements plus the known 5-byte header and 16-byte tag, not quoted from RFC 8446.
- Default fetch sizes for MySQL Connector/J (streams all rows unless `useCursorFetch`), Oracle JDBC (`fetchSize=10`), mssql-jdbc (`responseBuffering=adaptive`), asyncpg cursor prefetch (50) and psycopg3 `prepare_threshold` (5) were not confirmed from fetched pages in this pass and should be verified before being quoted.
