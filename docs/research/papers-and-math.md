## 1. Client protocol and result-set transfer (Raasveldt & Mühleisen and follow-ups)

### Takeaway
"Don't Hold My Data Hostage" (PVLDB 10(10), 2017) shows that for large result sets the dominant cost is per-row protocol overhead plus (de)serialization, not query execution: every mainstream protocol was 10x–60x slower than netcat shipping a CSV over loopback. Their fix is a vector-based protocol (column-major chunks of about 1 MB, no per-row headers, fixed-width binary values, optional per-column NULL bitmask, lightweight whole-chunk compression chosen by network speed), which was an order of magnitude faster and transferred fewer bytes than the originals in PostgreSQL and MonetDB.

### Cited Findings

Baseline measurements (TPC-H SF10 `lineitem`, 60M rows, 7.2 GB CSV, server and client on one machine, ODBC fetch, warm run) [paper] [checked 2026-11-09]:
- Isolated result-set (de)serialization + transfer time and bytes on the wire: netcat CSV 10.25 s / 7.19 GB; MySQL 101.22 s / 7.44 GB; DB2 169.48 s / 7.33 GB; "DBMS X" 189.50 s / 6.35 GB; PostgreSQL 201.89 s / 10.39 GB; MonetDB 209.02 s / 8.97 GB; MySQL+GZIP compression 391.27 s / 2.85 GB; Hive (Thrift) 627.75 s / 8.69 GB; MongoDB 686.45 s / 43.6 GB (Table 1). — [Raasveldt & Mühleisen, PVLDB 2017, DOI 10.14778/3115404.3115408](http://www.vldb.org/pvldb/vol10/p1022-muehleisen.pdf)
- "Transferring a CSV file over a socket is an order of magnitude faster than exporting the same amount of data from any of the measured systems." Connection and query-execution time were "insignificant" compared with RSS + transfer (Figure 1). — same source.
- On loopback "sending data is not the main bottleneck... most time is spent (de)serializing the result set." — same source.

Why: per-row wire overhead [paper]:
- PostgreSQL sends every row as a separate DataRow message carrying total length, field count, and a 4-byte length per field (-1 for NULL); for a row of (INT32, VARCHAR(10)) "the amount of per-row metadata is greater than the actual data". On the ACS dataset (mostly 4-byte integers) the fixed 4-byte per-field length "almost doubles the size of the dataset" (PostgreSQL transferred 12.5 GB for a 5.38 GB CSV). — same source.
- MySQL: 3-byte packet length + 1-byte sequence number per row, varint field lengths, field data in ASCII text; NULL = 0xFB. Text integers are compact for small values (ACS: MySQL 5.78 GB vs their binary 8.24–9.49 GB). — same source.
- MonetDB: text-based rows, values as ASCII, per-row message type, redundant tabs/spaces; "converting the internally used binary value representations to strings and back is an expensive operation." — same source.
- Hive/Thrift: columnar since Hive 2 but one byte per value for NULLs and varint-encoded integers; "unnecessarily verbose". — same source.
- MongoDB BSON repeats field names per document: ~6x the CSV size. — same source.

Network sensitivity (1M lineitem rows, netem) [paper]:
- Contrary to their prediction, all protocols degrade with latency because TCP ACKs are per filled buffer, so "protocols that send more data trigger more acknowledgements and suffer more from a higher latency"; DB2 and DBMS X degrade much more because they send explicit client-to-server confirmation messages per batch. — same source.
- With reduced bandwidth, "compression becomes more effective"; PostgreSQL goes from best at high bandwidth to worst at low bandwidth. — same source.

Design-space experiments [paper]:
- Chunk size (vector-based columnar protocol, Snappy on/off), lineitem: 2 KB chunks 55.9 s / 6.56 GB; 10 KB 15.2 s; 100 KB 10.9 s; 1 MB 10.0 s / 5.80 GB (ratio 2.25); 10 MB 10.9 s; 100 MB 13.3 s. ACS: 1 MB best at 11.9 s; ontime: 10 MB best (6.2 s) but 1 MB within 11% (6.9 s). "For all three datasets, the performance is optimal when the chunk size is around 1MB." (Table 3) — same source.
- Column-major compresses better than row-major on identical binary data (1M lineitem rows): LZ4 column 50.0 MB (2.10x) vs row 57.0 MB (1.85x); Snappy 47.8 (2.20x) vs 54.8 (1.92x); GZIP 32.4 (3.24x) vs 38.1 (2.76x); XZ 23.7 (4.44x) vs 28.1 (3.74x) (Table 4). — same source.
- Compression vs link speed, SF10 lineitem, times in seconds for Local / 1000 Mbit / 100 Mbit / 10 Mbit, size: None 1.5 / 10.4 / 84.8 / 848, 1012 MB; Snappy 3.3 / 3.8 / 37.3 / 373, 447 MB; LZ4 4.5 / 4.9 / 38.4 / 383, 456 MB; GZIP 59.8 / 60.4 / 59.6 / 226, 272 MB; XZ 695 / 689 / 666 / 649, 203 MB (Table 5). Conclusion: no compression on localhost; lightweight compression pays from 1 Gbit/s down; heavy compression only wins at 10 Mbit/s; XZ never wins. Their heuristic: no compression if same machine, else lightweight compression. — same source.
- Column-specific integer codecs (binpacking, PFOR) beat Snappy on lineitem (LAN 8.0 s vs 12.3 s vs 15.7 s uncompressed) but lose badly on ACS (265 int columns => few rows per chunk => "called many times on small chunks"; binpack 133.9 s vs Snappy 22.8 s on LAN) and on ontime (large value ranges). They chose not to use them by default (Table 6). — same source.
- Protobuf vs custom serialization (lineitem, Local/LAN/WAN): Custom 10.3 / 64.1 / 498.9 s, 5943 MB; Protobuf 33.1 / 45.5 / 391.6 s, 4656 MB; Custom+Snappy 18.3 / 25.4 / 221.4 s; Protobuf+Snappy 35.7 / 47.3 / 195.2 s. Protobuf is 3.2x slower locally because of generic varint/endianness work (Table 7). — same source.
- Strings: null-terminated vs varint-length-prefixed are equal in size (114.54 MB for l_returnflag) and time; fixed width wins only for very narrow columns (VARCHAR(1): 57.34 MB) and blows up with padding (VARCHAR(1000): 55.9 GB). They use fixed width only for VARCHAR(1), null-termination otherwise because of compressibility (Tables 8, 9). — same source.
- NULL handling: MonetDB++ uses an in-domain sentinel (e.g., 2^-31 for INT4), PostgreSQL++ a per-column bitmask that is omitted for NOT NULL columns; the bitmask variant transfers far less when >50% of values are NULL (ontime: 2.24 GB vs 3.49 GB) but compresses worse. — same source.
- Row-to-column transposition in PostgreSQL++ costs an extra copy but "the chunks are small and generally fit in the L3 cache", mitigating the random access pattern. Max chunk size is negotiated by the client at authentication so "the client only needs to allocate a single buffer to hold the result set messages" and "directly access the data stored without needing to unnecessarily convert and/or copy the data." — same source.

Results of the proposed protocol (Tables 10–12; Local / LAN 1 Gbit 0.3 ms / WAN 100 Mbit 25 ms 1% loss; T = >1 h timeout) [paper]:
- lineitem: MonetDB++ 10.6 / 50.3 / 510.8 s, 5.80 GB; MonetDB++C(Snappy) 15.5 / 19.9 / 200.6 s, 2.27 GB; Postgres++ 39.3 / 46.1 / 518.8 s, 5.36 GB; Postgres++C 42.4 / 43.8 / 229.5 s, 2.53 GB; versus MySQL 98.8 / 108.9 / 662.8; PostgreSQL 205.8 / 301.1 / 2108.8; MonetDB 222.4 / 256.1 / 1381.5; DB2 166.9 / 598.4 / T; Hive 657.1 / 948.5 / T. Netcat CSV 9.8 / 62.0 / 696.5. — same source.
- ACS: MonetDB++ 11.8 / 82.7 / 837.0 s; PostgreSQL++C 70.6 / 72.0 / 192.2 s (2.17 GB) vs PostgreSQL 277.8 / 265.1 / 1455.0 (12.5 GB). — same source.
- ontime (55% NULLs): MonetDB++C 7.16 / 7.18 / 31.3 s (0.35 GB) vs PostgreSQL 111.3 / 102.8 / 836.7 (6.49 GB), DB2 113.2 / 314.1 / 3386.8. — same source.
- Observed effect of interleaving: MySQL+C timings barely change with network limits because GZIP compression is interleaved with sending and dominates; the uncompressed new protocol "degrades significantly when network limitations are introduced because it is bound by the network speed." — same source.

Follow-up work:
- "Vectorized UDFs in Column-Stores" (Raasveldt & Mühleisen, SSDBM 2016, DOI 10.1145/2949689.2949703) — MonetDB/Python passes whole column chunks (NumPy arrays) to UDFs instead of tuple-at-a-time; vectorized operation "can only be used when the system has access to chunks of the data at the same time." [third party summary of search result; primary not opened] — [CWI copy](https://ir.cwi.nl/pub/29669/29669.pdf)
- ConnectorX (Section 2) credits [63] = this paper for showing "existing wire protocols suffer from redundant information and expensive (de)serialization" and notes DuckDB was "developed to avoid the bottlenecks of result set serialization and value-based APIs by making DBMS and analytic tools in the same address space." — [ConnectorX, PVLDB 15(11)](https://www.vldb.org/pvldb/vol15/p2994-wang.pdf)

### Inferences

Cost model (derived from the paper's stage decomposition; the paper itself gives no closed-form formula):
- Sequential (store-and-forward) model: `T = T_ser + T_net + T_deser`, with `T_net = S/B + n_rt * RTT`, where S = bytes on the wire, B = link bandwidth (bytes/s), n_rt = number of request/acknowledge round trips the protocol forces (0 for a pure server-push stream, 1 per batch for DB2/DBMS X-style explicit confirmations), RTT = round-trip time. `T_ser = S_raw / C_ser`, `T_deser = S_raw / C_deser` where C_* are per-core (de)serialization throughputs (bytes/s) on raw data size S_raw.
- Streamed/overlapped model (what the measurements actually fit): with chunks pipelined through server-serialize -> send -> client-deserialize, `T ≈ max(T_ser, T_net, T_deser) + (pipeline fill ≈ one chunk's worth of the other two stages)`. Evidence: Snappy at 1 Gbit took 3.8 s, which is close to max(CPU 3.3 s, wire 447 MB / 125 MB/s = 3.6 s) and far from the sum (6.9 s); MySQL+C is flat across link speeds because its GZIP stage dominates the max.
- Compression break-even (derived). Let r = compression ratio, C_c, C_d = compress/decompress throughput (bytes/s), B = link bandwidth.
  - Sequential model: compress iff `1/C_c + 1/C_d < (1 - 1/r) / B`, i.e. `B < (1 - 1/r) / (1/C_c + 1/C_d)`.
  - Overlapped model: compress iff `max(1/C_c, 1/(r*B), 1/C_d) < 1/B`, i.e. `B < min(C_c, C_d)` (any r > 1 helps as long as neither compressor side is slower than the uncompressed link). Note also the local case is special: on loopback B is effectively memory bandwidth, so compression never pays (Table 5: None 1.5 s vs Snappy 3.3 s).
  - From the paper's own numbers: Snappy on lineitem gave effective combined CPU cost of 1.8 s per 1012 MB (about 560 MB/s for compress+decompress), so under the overlapped model Snappy pays below roughly 4.5 Gbit/s and under the sequential model below about 2.4 Gbit/s on that 2017 VM. See Section 9 for 2024-era LZ4/zstd numbers.
- Chunk size: the measured optimum (~1 MB, flat from 100 KB to 10 MB) is the point where per-chunk fixed costs (headers, syscalls, compression call overhead, poor compression on short columns) are amortized while the chunk still fits L2/L3 for the transposition step. This matches X100's cache-fit argument (Section 4) and Instant Loading's `0.25–1.0 * L3 / hardware_threads` rule (Section 4). For a Rust driver: default receive/decode chunk of 256 KB–1 MB, negotiated once per connection, allocated once and reused.
- Design consequences for karez: (a) expose a chunk/columnar fetch path so clients that want columns never pay row-major materialization; (b) never send/accept per-row acknowledgements; stream chunks; (c) keep values fixed-width binary; (d) treat compression as a per-connection policy keyed on measured link speed (localhost => off; LAN/WAN => LZ4/zstd-fast), never per value; (e) if a server protocol is text-based (MonetDB, MySQL text), expect decoding CPU, not the wire, to be the bottleneck on LAN.

### Gaps
- The paper does not give a closed-form cost model; the formulas above are derived from its stage decomposition and tables.
- Their machine (2017 Ubuntu VM, 8 cores, Snappy) is dated; the break-even bandwidths must be recomputed with current compressor throughputs (Section 9).
- MonetDBLite paper (Raasveldt & Mühleisen) — listed as unpublished in Raasveldt's 2020 dissertation; no DOI/arXiv found today. DuckDB's CIDR 2020 paper ("Data Management for Data Science – Towards Embedded Analytics") was not opened today.

## 2. ConnectorX (Wang et al., VLDB 2022)

### Takeaway
ConnectorX measured that >85% of `pandas.read_sql` time is client-side (deserialization to Python objects and conversion to NumPy, ~40% each) with peak memory ~4x the final dataframe because three copies (raw bytes, Python objects, dataframe) coexist. Its remedy — a Rust streaming pipeline that first runs a count/metadata query to preallocate the destination, then has one worker per range-partitioned subquery write decoded values directly into final slots — cut load time 13x and peak memory 3x versus pandas on a 10 Gbit link, and is bandwidth-bound enough that the gap shrinks on slow links.

### Cited Findings
Setup [paper] [checked 2026-11-09]: two AWS r5.4xlarge (16 vCPU, 128 GB, 10 Gbit/s), TPC-H SF10 lineitem (60M rows, 16 columns, 7.2 GB CSV), PostgreSQL/MySQL/SQLite/"DBMS-A". — [Wang et al., PVLDB 15(11):2994–3003, DOI 10.14778/3551793.3551847](https://www.vldb.org/pvldb/vol15/p2994-wang.pdf)
- Headline: pandas 12.46 min and 95.6 GB peak vs ConnectorX 0.97 min and 31.4 GB (Figure 1); "the actual time spent on query execution is less than 1 min (13x time overhead) and the final Pandas.DataFrame is only 24.4 GB (4x memory overhead)." — same source.
- Time breakdown: ">85% of time is spent in the client"; deserialization and conversion to dataframe "each accounting for approximately 40% of the running time." Default read_sql executes the steps sequentially (wait for all bytes, then all Python objects, then convert). — same source.
- Memory (Table 1): PostgreSQL raw bytes 12.4 GB -> Python objects 52.6 GB -> dataframe 24.4 GB, peak 95.6 GB; MySQL 8.18 / 51.5 / 23.3 / 99.1 GB. Cause: a Python int is 8 bytes of payload plus a 20-byte object header, and "Pandas.read_sql keeps three copies of the entire data in memory." — same source.
- Chunking (chunksize 1K–1M) reduces peak memory to about the final dataframe size but "has little help in improving the running time" and hurts at chunk 100. — same source.
- Architecture: Preparation phase (1) query metadata — row count and column types — (2) allocate NumPy arrays for the final dataframe, (3) partition the query; Execution phase per worker thread: fetch a small batch, convert each cell, write directly into the final slot. Partitioning: user gives partition column, count and optionally range; otherwise `SELECT MIN(col), MAX(col)` is issued and the range split evenly into subqueries `WHERE col < x`, etc. (nested as a subquery for complex SQL). — same source.
- String allocation: Python string construction needs the GIL; ConnectorX batches string-object creation under one GIL acquisition and copies bytes after releasing it. Disabling this costs 6% without partitioning but makes the run 4.6x slower with 4 partitions (GIL contention). Disabling the streaming workflow costs ~20% time and 2.3x memory (70.4 GB, still 20 GB below pandas). — same source.
- Rust: chosen for "efficient performance and guarantees memory safety" and because "there is a variety of high-performance client drivers for different databases in Rust"; a Rust macro DSL for type mapping cut mapping code "by 97% (from 37k to 1k lines of code)". — same source.
- Network utilization: "No Partition cannot saturate the network bandwidth at all"; more parallel connections saturate the 10 Gbit link (Figure 7). — same source.
- Server cost of client-side partitioning (Table 2, PostgreSQL): no partition 1 scan, 1.1M disk-block misses, 156.1 s; client-side with 2/4/8/16 partitions = 3/5/9/17 scans, 3.2M/3.8M/3.8M/17.1M misses, 86.4/49.1/30.4/26.7 s; their server-side result-partitioning prototype (one scan, 1.1M misses) 86.7/45.7/23.9/19.6 s. Downsides of client partitioning: user burden, load imbalance, snapshot inconsistency across sessions, repeated sub-plans. — same source.
- Speedups vs pandas (Table 3, PostgreSQL, ConnectorX with 4 partitions as baseline): Local 14.26x, 10 Gbit 12.80x, 200 Mbit 3.05x; vs Turbodbc 6.64x / 6.21x / 1.90x; vs Modin 3.88x / 3.45x / 1.58x; vs Dask 6.09x / 4.80x / 5.31x; ConnectorX without partitioning is 3.16x / 3.03x / 1.08x slower than with. "the gap ... becomes larger when the bandwidth is higher". — same source.
- Without partitioning ConnectorX beats pandas 4.2x (PostgreSQL), 5.2x (MySQL), 3.0x (DBMS-A), 2.3x (SQLite) on TPC-H; Turbodbc is 2.0x / 2.3x slower than ConnectorX on PostgreSQL/MySQL but can match or beat it on DBMS-A — "how efficient the DBMS's ODBC driver is implemented ... highly determines Turbodbc's performance." — same source.
- Memory: peak "consistently 3x less than Pandas" on client-server DBs, 2x less on SQLite; Turbodbc still needs ~10 GB more than ConnectorX; on the DDoS dataset (DECIMAL-heavy, which "Python inflates 13x") the advantage is larger. — same source.
- SPJ queries (Table 4): without partitioning 1.0x–3.8x faster than pandas; with partitioning up to 8.4x faster but as slow as 0.3x (Q19) when the result is small, because the partition range query and extra plans dominate. For complex queries they recommend Arrow as the intermediate destination to avoid "the potentially costly COUNT query". — same source.
- Scalability: linear from SF1 to SF100 on r5.16xlarge (64 vCPU, 512 GB). — same source.

### Inferences
- The count-then-preallocate technique trades one extra server round trip and a COUNT scan for zero reallocation and zero concatenation copies; it is worth it when result size >> cost of COUNT, and wrong for small/complex results (their own Q19 regression). A driver should make preallocation optional and fall back to chunked (Arrow-style) growth with amortized doubling or chunk lists.
- Parallel partitioned reads are a bandwidth technique: the benefit scaled with link speed (12.8x at 10 Gbit vs 3.05x at 200 Mbit) and costs the server k+1 scans and 3.5x–15.5x the disk-block misses. A driver should expose it as an explicit API (partition column, N) rather than default behaviour, and should prefer server-side parallel cursors/endpoints where protocols offer them (Flight's multiple endpoints, Section 3).
- The 20-byte-per-int Python header and 3-copies finding is the general argument against per-value boxed objects in any host language (JVM analogue in Section 7).

### Gaps
- No formula for speedup vs number of partitions; Figure 7 is a network-utilization chart only. Amdahl-style: with k partitions, time ≈ max(S/B, S_raw/(k*C_decode)) + per-partition overhead — derived, not from the paper.
- The technical report [69] with Arrow/Polars destination numbers was not opened.

## 3. Arrow and columnar interchange (Flight, Flight SQL, ADBC, C Data Interface, DataFusion)

### Takeaway
Arrow's interchange story rests on two guarantees — a frozen C ABI that lets two components share column buffers in-process with no copy, and an IPC/Flight wire format whose on-wire bytes are the in-memory layout so a batch can be sent and rebuilt "without any memory copying or deserialization" — and on the observation (ADBC, Flight SQL) that JDBC/ODBC force columnar engines to transpose results twice. Published numbers are mostly vendor or preprint: ~3.1 GB/s localhost for Flight C++ [vendor], up to 6 GB/s DoGet and 20x/30x over turbodbc/ODBC on Dremio [third-party preprint].

### Cited Findings
- Arrow C Data Interface goals: "Allow zero-copy sharing of Arrow data between independent runtimes and components running in the same process"; "Expose an ABI-stable interface"; "Enable integration without an explicit dependency" on Arrow libraries; it is "Zero-copy by design"; once released "the C ABI is frozen." Not for cross-process sharing or persistence. `ArrowArray` = {length, null_count (-1 if unknown), offset, n_buffers, buffers, n_children, children, dictionary, release callback, private_data}; "Consumers MUST call a base structure's release callback when they won't be using it anymore"; moving is a bitwise copy plus marking the source released; buffer alignment is "recommended, but not required"; exported data should be treated as immutable. [vendor docs] [checked 2026-11-09] — [Arrow C Data Interface](https://arrow.apache.org/docs/format/CDataInterface.html)
- Arrow Flight (2019): gRPC/HTTP2 bidirectional streaming; `FlightData` protobuf carries record batches; `GetFlightInfo` returns multiple endpoints (location + ticket) that "Clients can read ... in parallel"; C++/Java implementations produce the protobuf wire bytes "without going through any intermediate memory copying or serialization steps" and rebuild batches "without any memory copying or deserialization." Benchmark: `arrow-flight-benchmark` read 12,800,000,000 bytes in 3,900,466,413 ns = 3,129.63 MB/s on localhost without TLS; prose claim "in excess of 2-3GB/s on localhost". Dremio's Flight connector "20-50x better performance over ODBC" (vendor claim relayed). [vendor] — [Introducing Apache Arrow Flight](https://arrow.apache.org/blog/2019/10/13/introducing-arrow-flight/)
- Flight SQL (2022): "Row-based APIs such as JDBC and PEP 249 must transpose columnar data into rows. A columnar database therefore transposes data twice" (once into the row API, once back in the consumer); ODBC bulk arrays still must be copied into Arrow arrays. Design: `GetFlightInfo`/`GetSchema` -> endpoints -> `DoGet`; prepared statements via `DoAction`, parameters uploaded as record batches via `DoPut`; multiple endpoints for parallel pull. Claims Flight is "as much as 20x faster" than PyODBC citing a Dremio talk. [vendor] — [Introducing Apache Arrow Flight SQL](https://arrow.apache.org/blog/2022/02/16/introducing-arrow-flight-sql/)
- ADBC (2023): rationale — JDBC is row-oriented; ODBC can carry columns but its type system does not map to Arrow; libraries like Turbodbc and arrow-jdbc still do row-to-column conversion; vendor protocols avoid it but force per-vendor integration; PostgreSQL has no Arrow output. ADBC is an Arrow-native client API with a driver layer: Arrow-native sources pass data through unchanged via the C Data Interface, others convert once. ADBC (API) and Flight SQL (wire protocol) are complementary; no performance numbers given. [vendor] — [Introducing ADBC](https://arrow.apache.org/blog/2023/01/05/introducing-arrow-adbc/)
- Independent Flight benchmark (Ahmad, Al Ars, Hofstee, arXiv 2204.03032, preprint): "up to 6000 MB/s and 4800 MB/s throughput for DoGet() and DoPut()"; uses up to 95% of Mellanox ConnectX-3/Connect-IB bandwidth; uses "up to half of the available system cores efficiently"; on Dremio, Flight is "about 20x better than turbodbc and about 30x better than ODBC"; "more than 80% of the total time spent in accessing data is elapsed in serialization/de-serialization step." [third party, not peer reviewed] — [arXiv:2204.03032, DOI 10.48550/arXiv.2204.03032](https://arxiv.org/abs/2204.03032)
- Vendor claims of varying quality: Dremio reports >15x over ODBC on `SELECT *` of Parquet records; Teradata's own Flight SQL test found near parity with JDBC for 100 MB–1 GB single-session uploads once the database is the bottleneck. [vendor; search summaries, pages not opened] — [Dremio](https://www.dremio.com/is-time-to-replace-odbc-jdbc/), [Teradata datasheet](https://preview.kr.teradata.com/getattachment/a6f20b6f-749a-452c-8f7d-0f4daf7cdc66/arrow_flight_sql-datasheet.pdf?lang=en-us)
- DataFusion paper: Lamb, Shen, Heres, Chakraborty, Kabak, Hsieh, Sun, "Apache Arrow DataFusion: A Fast, Embeddable, Modular Analytic Query Engine", SIGMOD 2024, DOI 10.1145/3626246.3653368. [not opened; see Gaps] — [DOI](https://doi.org/10.1145/3626246.3653368)

### Inferences
- The C Data Interface gives a Rust driver a free, dependency-light, zero-copy export path: produce chunks as Arrow-layout buffers (validity bitmap + data + offsets) and hand out `ArrowArray` structs; this is the same shape Raasveldt's protocol converged on (Section 1), so one internal chunk layout can serve both a row API and a columnar export.
- Flight's "no deserialization" is literally true only when the client is Arrow-native; for text/binary row protocols (PostgreSQL, MySQL, TDS) the driver still decodes, so the win is one decode into a columnar chunk instead of decode-to-rows-then-transpose.
- Flight's parallel endpoints are the server-side partitioning ConnectorX asked for (Section 2), without the k extra scans.

### Gaps
- The DataFusion SIGMOD 2024 paper was not opened (no open PDF located today; ACM DL copy not fetched), so its specific statements on batch sizing/StringView are not cited here.
- No peer-reviewed, independent Flight vs JDBC measurement found; all speedup factors are vendor or preprint.
- Arrow C Stream Interface page not opened.

## 4. Vectorized execution and SIMD decoding (X100, simdjson, fast_float, UTF-8, Instant Loading, number formatting, base64)

### Takeaway
MonetDB/X100 quantified tuple-at-a-time interpretation at ~49 CPU cycles per arithmetic operation in MySQL versus ~2.2 cycles in a vectorized primitive, with vectors of ~1,000 values (128–8K all fine) being optimal because they fit in cache — the direct argument against per-value getter APIs in drivers. On the parsing side, SIMD techniques reach 2–3 GB/s for validated JSON, 12–24 GiB/s for UTF-8 validation at <0.4 instructions/byte, 45–50 million doubles/s per core for text-to-double, 0.2 cycles/byte for base64, and 1.6 GB/s CSV parse+deserialize on 4 cores — so text protocols can be made fast, but each text value still costs tens of nanoseconds while a binary fixed-width value costs a load.

### Cited Findings

MonetDB/X100 (Boncz, Zukowski, Nes, CIDR 2005) [paper] [checked 2026-11-09] — [CIDR 2005 PDF](https://www.cidrdb.org/cidr2005/papers/P19.pdf):
- MySQL 4.1 gprof trace on TPC-H Q1 (SF1): the five operations that do the "work" (+, -, *, SUM, AVG) take <10% of time; 28% is hash-table work; 62% is record navigation/copying such as `rec_get_nth_field`. `Item_func_plus::val` costs 38 instructions at IPC 0.8 = "49 cycles!" per addition versus ~3 cycles for the RISC sequence; ~20 cycles are dependent-instruction stalls (no loop pipelining possible on one value), ~20 cycles are the function call. — same source.
- Commercial DBMSs get an IPC of only 0.7 [their ref 6]; scientific code gets IPC up to 2. — same source.
- MonetDB/MIL (full column materialization) is memory-bandwidth bound at 500 MB/s; its multiplication costs 75 cycles per tuple, "even worse than MySQL." — same source.

- X100's 49-vs-2.2 cycles is the quantitative case for a chunk-oriented driver API: a per-value virtual `get_i32(row, col)` call re-introduces exactly the function-call-per-value and dependent-instruction stalls MySQL paid; a chunk API (`column_i32(col) -> &[i32]`) lets the compiler and SIMD do the work. Exposing both, with the row API implemented as a thin view over chunks, keeps compatibility without paying the cost on the bulk path.

- SSE/AVX text scanning is worth it for delimiter/structural search and validation; branch-free scalar is often better for very short tokens (Instant Loading: SSE integer parse loses below 4 chars). A Rust driver should use `memchr`/SIMD for finding field boundaries and `fast_float`/`atoi`-style branch-reduced code for values.

## 5. Queueing theory for connection pools (Little, M/M/c, HikariCP, PostgreSQL connection cost, two choices, statement caches)

### Takeaway
Little's law sizes a pool (connections in use = throughput × mean hold time); Erlang C gives the wait probability and mean queueing delay of a shared pool of c connections; the HikariCP/Oracle argument says the right pool is small — about `cores*2 + effective_spindles` — because beyond CPU saturation extra connections only add contention, and the Oracle demo cut response time from ~100 ms to ~2 ms by shrinking 2048 connections to 96. PostgreSQL makes this concrete: one process per connection, ~1.3–7.6 MiB each, and idle connections slow active ones via `GetSnapshotData` (10,000 idle connections cut a single active connection's TPS from 33,457 to 14,496 on PG12).

### Cited Findings
- Little's law (restated): `L = λ * W` — mean number in system equals arrival rate times mean time in system (Little, Operations Research 9(3), 1961, DOI 10.1287/opre.9.3.383). Applied to a pool: `in_use = throughput_per_s * mean_hold_seconds`. — primary not opened today.
- M/M/c with arrival rate λ, per-server rate μ, utilization `ρ = λ/(c μ) < 1` for stability. Erlang C probability that an arrival must wait: `C(c, a) = [ (cρ)^c / c! * 1/(1-ρ) ] / [ Σ_{k=0}^{c-1} (cρ)^k / k! + (cρ)^c / c! * 1/(1-ρ) ]` with a = λ/μ offered load; mean response time `W = C / (c μ - λ) + 1/μ`, so mean queueing wait `Wq = C / (c μ - λ)`; mean number in system `L = ρ/(1-ρ) * C + c ρ`. [third party encyclopedia, checked 2026-11-09] — [Wikipedia M/M/c queue](https://en.wikipedia.org/wiki/M/M/c_queue)
- HikariCP "About Pool Sizing": starting-point formula `connections = ((core_count * 2) + effective_spindle_count)` (core count excludes hyperthreads; effective spindles = 0 if the working set is fully cached; a 4-core, 1-disk server => 9, "round to 10"; SSD applicability "hasn't been analyzed"). Oracle Real-World Performance Group video: pool reduced "from 2048 down to just 96" and response times fell from ~100 ms to ~2 ms, >50x. "More threads only perform better when blocking creates opportunities for executing." Deadlock-avoidance minimum: `pool_size = Tn * (Cm - 1) + 1` (Tn = max threads, Cm = max connections one thread holds at once). Mixed long/short workloads: use two pools. [vendor wiki] [checked 2026-11-09] — [HikariCP wiki](https://github.com/brettwooldridge/HikariCP/wiki/About-Pool-Sizing), video [YouTube](https://www.youtube.com/watch?v=_C77sBcAtSQ)
- PostgreSQL architecture: "it starts ('forks') a new process for each connection." [vendor docs] — [PostgreSQL docs, Architectural Fundamentals](https://www.postgresql.org/docs/current/tutorial-arch.html)
- Per-connection memory (Freund, 2020): naive RSS of an idle backend 16,944 kB without huge pages but most is shared memory double-counting; corrected `Pss_Anon + VmPTE` ≈ 7,665 kB (~7.6 MiB) without huge pages, ≈ 1,305 kB (~1.3 MiB) with huge pages (page tables fall from 6,480 kB to 132 kB); conclusion "less than 2MiB" per connection with huge pages. [third party, PG committer blog] [checked 2026-11-09] — [anarazel.de](https://blog.anarazel.de/2020/10/07/measuring-the-memory-overhead-of-a-postgres-connection/)
- Connection scalability (Freund, PG12, read-only pgbench): 1 active connection 33,457 TPS with 0 idle, 30,558 with 1,000 idle, 23,284 with 5,000 idle, 14,496 with 10,000 idle; 48 active: 1,032,435 -> 521,558 TPS at 10,000 idle; mostly-idle (`\sleep 100ms; SELECT 1`) clients are worse: 1 active drops to 6,049 TPS (18% of baseline) with 10,000 of them. Bottleneck profiled to `GetSnapshotData()`. Shared memory rises only from 16,804 MiB (max_connections=100) to 21,463 MiB (max_connections=100000) with 16 GB shared_buffers. With simulated 1 ms network + 1 ms app delay, pgbench peaked around 3000 connections vs ~48 without delays. Poolers (PgBouncer, Odyssey) help only in transaction/statement modes, which exclude prepared statements and temp tables. [third party] [checked 2026-11-09] — [Microsoft Tech Community](https://techcommunity.microsoft.com/t5/azure-database-for-postgresql/analyzing-the-limits-of-connection-scalability-in-postgres/ba-p/1757266)
- Power of two choices (Mitzenmacher, Richa, Sitaraman survey, 2001): with n balls into n bins, one random choice gives max load `log n / log log n (1+o(1))`; choosing the least loaded of d ≥ 2 random bins gives `log log n / log d + Θ(1)` with high probability (Azar, Broder, Karlin, Upfal) — "even a small amount of choice can lead to drastically different results"; two choices give the large reduction, more choices only a constant factor. Fluid-limit tails for the static problem: `s_i(1) ≤ (s_1(1))^(d^(i-1))`, i.e. doubly exponential decrease. Supermarket (queueing) model: with one random choice the expected time in system is the M/M/1 value `1/(1-λ)`; with d ≥ 2 it grows only like `log(1/(1-λ))` as λ -> 1 (the survey states the limit of `T_d(λ)/log(1/(1-λ))`; the exact constant was not legible in today's OCR — standard form (restated): `s_i = λ^((d^i - 1)/(d - 1))` for the fraction of queues with ≥ i customers). [paper, partially read] [checked 2026-11-09] — [Harvard PDF](https://www.eecs.harvard.edu/~michaelm/postscripts/handbook2001.pdf)
- LRU cache hit ratio (Che approximation; Fricker, Robert, Roberts, arXiv 1202.3974): per-object hit probability `h_i = 1 - exp(-q_i * T_C)` where q_i is object i's request rate and the characteristic time T_C solves `Σ_i (1 - exp(-q_i * T_C)) = C` (C = cache size in objects); overall hit ratio `H = Σ_i p_i * h_i` with p_i the request probability. The approximation "proves remarkably accurate and is applicable to quite general distributions of object popularity." [third party; formula as given in the search synthesis and the paper abstract; details restated] — [arXiv:1202.3974](https://arxiv.org/abs/1202.3974); original: Che, Tung, Wang, IEEE JSAC 2002, DOI 10.1109/JSAC.2002.801752 (not opened).

### Inferences
- Pool sizing recipe (derived): `N_needed = λ * W_hold / target_utilization`; with ρ chosen (e.g. 0.7) Erlang C gives P(wait) and `Wq = C(c, a)/(cμ - λ)`. The HikariCP rule is the supply-side cap (how many the server can run usefully); Little's law is the demand side; the smaller of the two is the pool, and the application must queue above it.
- Partitioned vs shared pools (restated standard result): c independent M/M/1 queues each fed λ/c have mean wait `ρ/(μ(1-ρ))` per queue, while one M/M/c fed λ has `C(c,a)/(cμ-λ)` which is strictly smaller for c > 1 at equal ρ (resource pooling). A per-core/per-thread partitioned pool buys lock-free checkout at the cost of idle connections in one partition while another queues; use partitioning only when checkout contention is measured, and add work stealing or two-choice checkout (pick the shorter of two partitions' queues) to recover most of the pooled behaviour.
- Thundering herd on return: waking all waiters when one connection returns costs O(waiters) wakeups for one winner; a FIFO/LIFO handoff (give the connection directly to one waiter) is the standard fix; no paper measured this for DB pools today (gap).
- Multi-host routing: two-choice (query two replicas' in-flight counts, pick the lower) gets within a constant of least-loaded with O(1) information, per Mitzenmacher; round-robin is the d=1 case with log n / log log n imbalance.
- Connection cost argument for pooling: each new PostgreSQL connection is a fork plus ~1.3–7.6 MiB plus TLS/auth round trips (Section 6), and even idle connections tax `GetSnapshotData`; this justifies keeping pools small and warm, and favouring protocol-level pipelining over connection count for throughput.
- Prepared-statement caches: per-connection LRU of size C against D distinct statements with Zipf(α) popularity; use Che's approximation to pick C so that H ≥ target (e.g. 0.95). Because the cache is per connection, memory on both sides scales as `pool_size × C`; a pool of 50 with 1,000 cached statements each is 50,000 server-side prepared statements, so size C from the hit-rate model, not "unlimited".

- The Oracle video itself was not watched; the 100 ms -> 2 ms and 2048 -> 96 numbers come from the HikariCP summary of it.
- No measured study of pool fairness/thundering herd for database connection pools was found.
- Che's original 2002 paper and the Zipf-specific closed form were not opened; the formula is restated.
- The exact Mitzenmacher supermarket constant was not legible in the extracted PDF; the thesis/TPDS 2001 paper (DOI 10.1109/71.963420) was not opened.

## 6. Batching and pipelining mathematics (RTT bound, pipelining gain, Nagle/delayed ACK, BDP, fetch size, parallel connections)

### Takeaway
A request/response protocol is bounded by `X ≤ N / RTT` for N requests in flight; pipelining k statements per round trip turns k×RTT into ≈ RTT (PostgreSQL's own example: 100 statements at 300 ms RTT = 30 s unpipelined vs ~0.3 s pipelined). On Linux the Nagle + delayed-ACK interaction adds a 40 ms stall (`TCP_DELACK_MIN = HZ/25`) to write-write-read patterns unless `TCP_NODELAY` (or `TCP_QUICKACK`) is set. The fetch batch must carry ≥ several bandwidth-delay products of bytes to run near link speed, which is why 1 MB chunks and server-push streaming beat small cursor fetches with per-batch acknowledgements.

### Cited Findings
- libpq pipeline mode (PostgreSQL 14+): "a client will wait less for the server, since multiple queries/results can be sent/received in a single network transaction"; "most useful when the server is distant, i.e., network latency ('ping time') is high, and also when many small operations are being performed in rapid succession"; "A 100-statement operation run on a server 300 ms round-trip-time away would take 30 seconds in network latency alone without pipelining; with pipelining it may spend as little as 0.3 s waiting for results." Costs: more memory on both sides, client complexity (queue of pending queries), deadlock possible in blocking mode if both the client's send buffer and server's receive buffer fill — use non-blocking I/O; COPY and the simple-query protocol are disallowed; a fatal error aborts the rest of the pipeline up to the sync point; "The client must not assume that work is committed when it sends a COMMIT — only when the corresponding result is received." [vendor docs] [checked 2026-11-09] — [libpq pipeline mode](https://www.postgresql.org/docs/current/libpq-pipeline-mode.html)
- Raasveldt & Mühleisen: protocols that send explicit per-batch confirmations (DB2, DBMS X) collapse with latency (DB2 lineitem LAN 598 s vs 167 s local; WAN timeout >1 h), and even pure streams degrade because TCP ACKs scale with bytes sent. [paper] — [PVLDB 2017](http://www.vldb.org/pvldb/vol10/p1022-muehleisen.pdf)
- Linux delayed-ACK constants in `include/net/tcp.h`: `TCP_DELACK_MAX = HZ/5` ("maximal time to delay before sending an ACK", 200 ms at HZ=1000); `TCP_DELACK_MIN = HZ/25` for HZ ≥ 100 ("minimal time to delay before sending an ACK", 40 ms); `TCP_ATO_MIN = HZ/25` (40 ms). [primary source] [checked 2026-11-09] — [torvalds/linux tcp.h](https://raw.githubusercontent.com/torvalds/linux/master/include/net/tcp.h)
- John Nagle on the interaction: Nagle's algorithm holds small writes until outstanding data is ACKed; delayed ACK holds the ACK hoping to piggyback; "The combination of the two is awful." He blames "ACK delays, and that stupid fixed timer", recommends `TCP_QUICKACK` "unless you have a very unusual application", and notes `TCP_NODELAY` works but can hurt throughput for many small writes because each becomes a packet, so the application must manage its own buffering/flushing. [primary source, author comment] [checked 2026-11-09] — [Hacker News comment by Animats](https://news.ycombinator.com/item?id=10608356)
- Bandwidth-delay product: RFC 7323 §1.1 — "TCP performance problems arise when the bandwidth * delay product is large" (long fat networks); the 16-bit window caps the un-scaled window at `2^16 = 64 KiB`; window scaling allows up to `2^30 = 1 GiB`. [standard] [checked 2026-11-09] — [RFC 7323](https://www.rfc-editor.org/rfc/rfc7323)
- ConnectorX: a single connection "cannot saturate the network bandwidth at all" on 10 Gbit/s; four partitions did, with the speedup over single-connection shrinking from 3.16x (local) to 1.08x at 200 Mbit/s. [paper] — [PVLDB 2022](https://www.vldb.org/pvldb/vol15/p2994-wang.pdf)
- Arrow Flight / Flight SQL: servers return multiple endpoints so clients pull streams in parallel; TU Delft measured Flight using "up to half of the available system cores" to reach 6 GB/s. [vendor; third-party preprint] — [Flight blog](https://arrow.apache.org/blog/2019/10/13/introducing-arrow-flight/), [arXiv:2204.03032](https://arxiv.org/abs/2204.03032)

### Inferences (formulas; all derived unless marked)
- Round-trip bound (restated, standard): with N requests outstanding, throughput `X ≤ N / RTT`; strictly `X = N / (RTT + S_srv + S_cli)` where S_* are per-request service times. Sequential request/response is N = 1.
- Pipelining gain: k statements per round trip take `T_pipe ≈ RTT + k * s` versus `T_seq = k * (RTT + s)` (s = per-statement server time), so `speedup = k (RTT + s) / (RTT + k s)`; -> k when `RTT >> k s`, -> 1 when `s >> RTT` (the docs' "less benefit when each query takes many multiples of the RTT"). Check: k=100, RTT=0.3 s, s≈0 gives 30 s vs 0.3 s, matching the PostgreSQL example.
- Nagle/delayed-ACK stall: a driver that writes a request as two `send()` calls (e.g., header then body, or Parse then Bind then Execute then Sync as separate writes) with the server replying only after the last one pays `TCP_DELACK_MIN` = 40 ms per request on Linux. Rule: set `TCP_NODELAY` on every DB socket and coalesce each logical request into one write (vectored I/O); this preserves batching while avoiding Nagle's hold-back. The 200 ms figure is the maximum delayed-ACK timer; 40 ms is the common observed stall.
- Bandwidth-delay product: `BDP_bytes = B_bytes_per_s * RTT`. Socket buffers must hold ≥ BDP for one stream to fill the pipe (e.g., 1 Gbit/s × 0.3 ms ≈ 37.5 KB; 10 Gbit/s × 1 ms ≈ 1.25 MB; 100 Mbit/s × 25 ms ≈ 312 KB). Unscaled TCP's 64 KiB window caps a single stream at `64 KiB / RTT` (e.g., 2.6 MB/s at 25 ms RTT).
- Optimal fetch/batch size for request-per-batch protocols (derived): with F rows of b bytes each per fetch, per-batch time `t = RTT + F b / B + c0` (c0 = fixed per-batch CPU), rows/s `= F / t`, asymptote `B / b`. Link efficiency `η = (F b / B) / (RTT + F b / B) = 1 / (1 + BDP / (F b))`. To reach efficiency η: `F b ≥ (η / (1 - η)) * BDP`; for η = 0.9, batch bytes ≥ 9 × BDP (LAN example: ≥ 340 KB; WAN 100 Mbit/25 ms: ≥ 2.8 MB). Upper bound is client memory per in-flight batch and latency-to-first-row; with server-push streaming (no per-batch request) F only affects memory and decode granularity, and the ~1 MB chunk from Section 1 applies. Prefer streaming + chunking over cursor-fetch loops; if the protocol forces fetch requests, pipeline the next fetch before decoding the current one (N = 2 keeps the link busy: `X ≈ 2 / RTT` instead of `1 / RTT`).
- When to open parallel connections for a bulk read (derived from ConnectorX): one stream is limited by `min(B, C_decode_per_thread, server_single_stream_rate)`; with per-thread decode C_d ≈ 100–300 MB/s for text protocols (Section 4) and 10 Gbit/s = 1,250 MB/s links, `k ≈ ceil(B / C_d)` ≈ 4–12 connections saturate the link; beyond that, each extra connection costs the server an extra scan (k+1 scans) and buffer-pool pressure (3.5x–15.5x disk misses). Below ~1 Gbit/s one connection is already network-bound (ConnectorX's 1.08x at 200 Mbit).

### Gaps
- No peer-reviewed measurement of the 40 ms stall in database drivers specifically; the mechanism is from kernel source plus Nagle's own explanation.
- The fetch-size derivation is this note's; no paper derives it in this form.

## 7. Memory and allocation (allocators, arenas, buffer reuse, zero-copy, boxing)

### Takeaway
Per-row/per-value heap objects are the dominant memory and time cost in dataframe and JVM-style clients (Python int: 20-byte header on 8 bytes of payload and 4x peak memory; JVM `Integer`: 16 bytes plus a 4-byte reference for a 4-byte value), whereas flat typed buffers cost their payload. Allocator choice matters at the margins (mimalloc ~13% over tcmalloc on an allocation-heavy app; 2.5x over jemalloc on sh6bench), but the design wins are structural: preallocate destinations (ConnectorX), size buffers once per connection and reuse them (Raasveldt), use cache-sized chunks with allocation hints and huge pages (Instant Loading), and hand out Arrow buffers without copying.

### Cited Findings
- ConnectorX: Python int payload 8 bytes + 20-byte header; three full copies (raw bytes 12.4 GB, Python objects 52.6 GB, dataframe 24.4 GB) give 95.6 GB peak; disabling streaming needs 2.3x more memory; preallocation "to avoid extra data copy and concatenation at the end"; Rust chosen for "efficient ... data representation"; without streaming it still used 70.4 GB vs pandas 95.6 GB, "validat[ing] the efficiency of using Rust in terms of data representation." [paper] — [PVLDB 2022](https://www.vldb.org/pvldb/vol15/p2994-wang.pdf)
- JVM boxing: `java.lang.Integer` instance size 16 bytes on a 64-bit HotSpot JVM (8-byte mark word, 4-byte compressed class pointer, 4-byte value), plus a 4-byte compressed reference per element in a container, roughly 20 bytes per boxed int vs 4 bytes primitive; values -128..127 are cached; JDK 25 compact object headers reduce the header. [third party, search summary; pages not opened] — [DZone](https://dzone.com/articles/whats-wrong-with-java-boxed-numbers), [Baeldung](https://www.baeldung.com/java-size-of-object), [JavaPro on JDK 25](https://javapro.io/2026/02/10/mastering-memory-efficiency-with-compact-object-headers-in-jdk-25/)
- Raasveldt & Mühleisen: client negotiates a maximum chunk size so it "only needs to allocate a single buffer to hold the result set messages" and can "directly access the data stored without needing to unnecessarily convert and/or copy the data"; 1 MB chunks mean "the client does not need a large amount of memory to get good performance." [paper] — [PVLDB 2017](http://www.vldb.org/pvldb/vol10/p1022-muehleisen.pdf)
- Instant Loading: heap (re)allocation of partition buffers "is costly as, in general, it needs to be synchronized"; cardinality-estimate allocation hints gave +5% at 8 threads; huge pages for buffers reduce TLB competition; chunk-based merge (append a buffer pointer instead of memcpy) was 12% faster than copy-based for the column store; chunk size tied to `L3/threads`. [paper] — [PVLDB 2013](http://www.vldb.org/pvldb/vol6/p1702-muehlbauer.pdf)
- mimalloc README benchmarks (AMD 5950X 16-core, 2021-01-30; tcmalloc 2.8.1, jemalloc 5.2.1, rpmalloc 1.4.1, Hoard, Mesh, glibc 2.31): leanN ~13% faster than tcmalloc (hypothetically 1.6x if Lean spent 20% of time in the allocator); sh6bench "more than 2.5x faster than jemalloc"; sh8bench makes tcmalloc ~10x slower than on sh6bench once objects migrate between threads; cfrac "just a tad faster" than tcmalloc/jemalloc; cross-thread free is "a single CAS"; detailed percentages are in SVG charts only; a 2026-09 note says other allocators have since improved. [vendor] [checked 2026-11-09] — [microsoft/mimalloc](https://github.com/microsoft/mimalloc)
- Arrow C Data Interface: zero-copy, ABI-stable handoff with producer-owned release callbacks; consumers may move structs by bitwise copy. [vendor docs] — [CDataInterface](https://arrow.apache.org/docs/format/CDataInterface.html)
- Arrow Flight: record batches sent and rebuilt "without any memory copying or deserialization" in the C++/Java gRPC paths. [vendor] — [Flight blog](https://arrow.apache.org/blog/2019/10/13/introducing-arrow-flight/)

### Inferences
- Cost model for a row API that allocates per cell: `T_row ≈ n_cols * (t_alloc + t_decode) + t_row_alloc`; with t_alloc ≈ 20–50 ns for a general allocator fast path (not measured today; see Gaps) and 16 columns, allocation alone is ≈ 0.3–0.8 µs/row, the same order as the whole text-decoding budget in Section 4 and more than the entire binary decode. An arena/bump allocator per chunk (one `Vec<u8>` per chunk, values as offsets) or borrowed slices into the receive buffer (`&[u8]`/`&str` with the chunk's lifetime) removes this term entirely.
- Receive-buffer discipline supported by the sources: negotiate/choose a chunk size once (0.25–1 MB), keep a small ring of reusable buffers per connection (slab), decode in place, and only copy when the user asks for an owned value. Zero-copy borrowing from the socket buffer is the libpq++/Flight model (the chunk is the storage); in Rust it maps to `Bytes`-style refcounted slices.
- Zipf/cache-locality: column-major chunks make each column's decode loop stream through contiguous memory (X100's premise), while per-row object graphs scatter — the same reason X100 primitives exceeded 7.5 GB/s on cached vectors while MIL was stuck at RAM bandwidth.

### Gaps
- No primary allocator paper gives ns-per-malloc on current hardware; mimalloc's TR PDF was saved but not extracted today, and the README has charts only. The 20–50 ns figure above is a placeholder, not a cited number.
- No published measurement of JDBC per-row object allocation cost (only object-size facts) was found; the JVM sizes are from secondary sources.

## 8. Benchmarking methodology (coordinated omission, open vs closed, warm-up/JIT, statistics, benchmarking crimes)

### Takeaway
Three traps dominate client-library benchmarks: coordinated omission (a closed-loop load generator that waits for slow responses stops sampling exactly when the system is slow — Tene's example turns a true p99.99 of 100 s into a reported 1 ms), closed-vs-open confusion (Schroeder et al.: at equal load an open system's mean response time can exceed a closed one's "by an order of magnitude or more", and variability matters hugely in open systems but little in closed ones), and under-repetition/warm-up (Barrett et al.: at most 43.5% of VM/benchmark pairs reliably reach a steady state; Kalibera & Jones: repeat at the level where variance lives and report effect size with a confidence interval).

### Cited Findings
- Coordinated omission (Gil Tene): a system at 100 req/s, 1 ms each, frozen for 100 s after every 100 s of normal operation has a true 200-second average of 25 s, p75 of 50 s, p99.99 of 100 s; a naive closed-loop generator records ~10,000 × 1 ms plus one 100 s sample and reports average 10.9 ms, p75 and p99.99 of 1 ms; after a change that makes every post-stall request 5 ms, the reported p99.99 goes to 5 ms, so the "improvement" looks 5x worse. User exposure: 5 page loads × ~40 resources = 200 resources per session; `0.95^200 ≈ 0.003%` of users avoid the p95, so 99.997% see worse than p95; 18% of users see worse than p99.9; >95% see the p99.97; >99% see the p99.995. "The number one indicator you should never get rid of is the maximum value." [third party summary of Tene's talk] [checked 2026-11-09] — [bravenewgeek summary](https://bravenewgeek.com/everything-you-know-about-latency-is-wrong/); Tene's own definition and `recordValueWithExpectedInterval` fix — [mechanical-sympathy thread](https://groups.google.com/g/mechanical-sympathy/c/icNZJejUHfE); slides — [QCon SF 2015 PDF](https://videog.infoq.com/downloads/pdfdownloads/presentations/QConSF2015-GilTene-HowNOTtomeasureLatency.pdf) (403 today).
- HdrHistogram: fixed footprint ("around 185KB" for 1 µs–1 hour at 3 significant digits; quantization within 0.1%); constant-time recording "3-6 nanoseconds" (c. 2012 CPUs); `recordValueWithExpectedInterval()` back-fills synthetic samples at the expected interval when a recorded value exceeds it — in the 100 s stall example raw data shows 99.99% ≤ 1 ms, corrected shows ~50% with the rest spread 10 ms–100 s. [vendor] [checked 2026-11-09] — [HdrHistogram README](https://github.com/HdrHistogram/HdrHistogram)
- Open vs closed (Schroeder, Wierman, Harchol-Balter, NSDI 2006) [paper] [checked 2026-11-09] — [USENIX PDF](https://www.usenix.org/legacy/event/nsdi06/tech/full_papers/schroeder/schroeder.pdf). Definitions: closed = fixed multiprogramming level N of users who submit, wait, think, repeat — "a new request is only triggered by the completion of a previous request"; open = arrivals at rate λ independent of completions; partly-open = sessions arrive openly, each issues several requests closed-loop. Findings: "for a fixed load, the mean response time for an open system model can exceed that for a closed system model by an order of magnitude or more"; "there is still a significant difference ... even for an MPL of 1000". The eight principles: (i) "For a given load, mean response times are significantly lower in closed systems than in open systems"; (ii) "As the MPL grows, closed systems become open, but convergence is slow for practical purposes" (Schatte proved closed FCFS -> open M/GI/1 as N -> ∞); (iii) "While variability has a large effect in open systems, the effect is much smaller in closed systems"; (iv) open systems benefit significantly from size-based scheduling while closed systems benefit far less; (v) "Scheduling only significantly improves response time in closed systems under very specific parameter settings: moderate load (think times) and high MPL"; (vi) "Scheduling can limit the effect of variability in both open and closed systems"; (vii) "A partly-open system behaves similarly to an open system when the expected number of requests per session is small (≤ 5 as a rule-of-thumb) and similarly to a closed system when ... large (≥ 10)"; (viii) "In a partly-open system, think time has little effect on mean response time." Most web benchmarks surveyed assume a closed model and often do not say so. — same source.
- JIT warm-up (Barrett, Bolz-Tereick, Killick, Mount, Tratt, OOPSLA 2017, DOI 10.1145/3133876; arXiv 1602.00602): "at most 43.5% of <VM, benchmark> pairs consistently reach a steady state of peak performance" across three machines; small deterministic microbenchmarks often fail to reach a steady state; they use automated changepoint analysis to classify runs. [paper abstract] [checked 2026-11-09] — [arXiv:1602.00602](https://arxiv.org/abs/1602.00602)
- Kalibera & Jones, "Rigorous Benchmarking in Reasonable Time" (ISMM 2013, DOI 10.1145/2464157.2464160) [paper] [checked 2026-11-09] — [Kent repository](https://kar.kent.ac.uk/33611/), [AAM PDF](https://kar.kent.ac.uk/33611/45/p63-kaliber.pdf): "repetition is most needed where most uncertainty arises (whether between builds, between executions or between iterations)"; measurements should be taken only once the system is in an independent state — iteration times "are (statistically) independent and identically distributed", with 'initialised' (no JIT/linking/I/O warm-up) as the necessary condition; they find the DaCapo and Georges-et-al. automatic steady-state heuristics "do not perform well"; they give a cost model and "a cookbook" that yields optimal repetition counts per level for a target precision (worked tables: e.g. SPEC CPU needs 4–6 executions for 1% precision; some DaCapo benchmarks need tens of executions for 1%); summarise as "we are 95% confident that system A is faster than system B by 5.5% ± 2.5%" — "Report performance changes with effect size confidence intervals." The closed-form repetition-count formula (their Section 9.2, equation 2) was not legibly extracted today (restated qualitatively). — same source.
- criterion.rs analysis: warm-up by doubling iterations until `warm_up_time`; linear sampling `iterations = [d, 2d, ..., Nd]`; whole samples timed, not single iterations; outliers by Tukey fences at 1.5 IQR (mild) and 3 IQR (severe), kept in the analysis but flagged; statistics (slope, mean, median, MAD, std dev) with bootstrap confidence intervals; comparisons via a bootstrapped t-test with a configurable noise threshold (example ±1%). [vendor docs] [checked 2026-11-09] — [criterion.rs book](https://bheisler.github.io/criterion.rs/book/analysis.html)
- Benchmarking crimes (Heiser's list, the basis of van der Kouwe et al.): selective benchmarking (not evaluating potential degradation; subsetting without justification; selective data sets; arbitrary picking from a huge set); improper handling of results (micro-benchmarks as overall performance; "throughput degraded by x% means overhead is x%"; downplaying overheads; no indication of significance; arithmetic mean of normalised scores); wrong benchmarks (inappropriate/misleading; same data for calibration and validation); simplified simulated systems; improper comparison (no proper baseline; evaluating only against yourself; unfair benchmarking of competitors; ignoring the state of the art); missing information (platform spec; sub-benchmark results; relative numbers only). [third party] [checked 2026-11-09] — [gernot-heiser.org](https://gernot-heiser.org/benchmarking-crimes.html)
- van der Kouwe, Heiser, Andriesse, Bos, Giuffrida, "SoK: Benchmarking Flaws in Systems Security" (IEEE EuroS&P 2019; earlier arXiv 1801.02381 "Benchmarking Crimes: An Emerging Threat in Systems Security"): catalogue of 22 flaws; survey of ~50 top-tier defense papers found an average of five flaws per paper and only one paper with none; the rate was flat over time. [third party summary; paper not opened] — [VUSec project page](https://www.vusec.net/projects/benchmarking-crimes/), [PDF](https://download.vusec.net/papers/benchmarking_sp20.pdf)

### Inferences
- For a driver benchmark suite: (1) drive the server-side comparison open-loop at fixed arrival rates (or partly-open with ≥10 requests per "session" when modelling pooled app threads, per principle vii) and record with HdrHistogram's expected-interval correction; report max, p99, p99.9, not means; (2) a closed-loop "N threads hammering" test is a different experiment that will flatter tail latency and must be labelled as such; (3) compare Rust with JVM drivers only after the JVM run is shown (changepoint or Kalibera's independence test) to be in steady state, and report the JVM's warm-up separately because 56% of VM/benchmark pairs never settle; (4) repeat at the process level (new process, new connection) not just iterations, since connection setup, allocator state and server caches create between-execution variance; (5) report effect sizes with bootstrap CIs (criterion already does this) and absolute numbers alongside ratios (Heiser).
- ConnectorX's methodology (five runs averaged, no CI) and Raasveldt's (single warm run) fall short of Kalibera & Jones; karez's numbers should not.

### Gaps
- Gil Tene's slides returned HTTP 403 today; the numbers are from a detailed third-party write-up and Tene's own mailing-list definition.
- The Kalibera & Jones repetition-count formula was not legibly extracted; use the AAM PDF Section 9.
- The van der Kouwe paper itself was not opened; the 22-flaw list is from Heiser's page, which it extends.

## 9. Compression and TLS throughput (LZ4, zstd, zlib; AES-GCM, ChaCha20-Poly1305; record framing)

### Takeaway
Single-core LZ4 compresses at ~675–770 MB/s and decompresses at 3.9–5 GB/s (2.1x on Silesia); zstd -1 at ~510 MB/s / 1.55 GB/s (2.9x); zlib -1 at ~105 MB/s / 390 MB/s. Plugging these into the break-even inequality from Section 1 puts general-purpose compression's payoff below roughly 2–6 Gbit/s per core (LZ4/zstd-fast) and below ~0.5–0.8 Gbit/s for zlib, so it pays on WAN and 1 GbE, is marginal at 10 GbE, and loses at 25 GbE and on loopback. AES-GCM with AES-NI+CLMUL runs at ~0.65 cycles/byte on Skylake (≈5 GB/s per core at 3.5 GHz) and ChaCha20-Poly1305 under 2 cycles/byte on Haswell AVX2 (<1 projected with AVX-512); TLS 1.3 adds 22 bytes per record (5-byte header + 1-byte inner type + 16-byte AEAD tag), so small protocol messages should be coalesced into one record per flush.

### Cited Findings
- LZ4 README (lzbench 2.4.1, i7-9700K, GCC 13.3, Silesia, single thread): memcpy 13,700 MB/s; LZ4 1.11.0: ratio 2.112, compress 770 MB/s, decompress 4,950 MB/s; LZ4 HC -9: 2.717, 40 MB/s, 4,800 MB/s; zstd 1.5.7 -1: 2.896, 510, 1,570; Snappy 1.3.1: 2.090, 520, 1,350; zlib 1.3.2 -1: 2.743, 110, 410; zlib -6: 3.106, 36, 430; zlib-ng -1: 2.252, 250, 555. [vendor] [checked 2026-11-09] — [lz4/lz4](https://github.com/lz4/lz4)
- zstd README (lzbench, i7-9700K @ 4.9 GHz, gcc 14.2, Silesia): zstd 1.5.7 -1: 2.896, 510 MB/s, 1,550 MB/s; --fast=1: 2.439, 545, 1,850; --fast=4: 2.146, 665, 2,050; brotli -1: 2.883, 290, 425; zlib 1.3.1 -1: 2.743, 105, 390; lz4 1.10.0: 2.101, 675, 3,850; snappy 1.2.1: 2.089, 520, 1,500. Levels 2–3 are not tabulated (charts only). [vendor] [checked 2026-11-09] — [facebook/zstd](https://github.com/facebook/zstd)
- Raasveldt & Mühleisen measured break-even empirically: lightweight compression wins at ≤1 Gbit/s, heavy compression only at 10 Mbit/s, never on localhost (Table 5, Section 1). [paper]
- Cloudflare (Haswell AVX2): ChaCha20-Poly1305 "getting below 2 cycles/byte"; AVX-512 projected below 1 cycle/byte; "AES-128-GCM and AES-256-GCM both beat ChaCha20-Poly1305 for records larger than 320 bytes"; many connections never reach 16 KB records — records are often <1400 bytes, then ~4 KB, then 16 KB; their implementation beats OpenSSL 1.1.0-pre "significantly" on short records, 7% on average. [vendor] [checked 2026-11-09] — [Cloudflare blog](https://blog.cloudflare.com/it-takes-two-to-chacha-poly/)
- Shay Gueron (Intel/Haifa) talk abstract: AES-GCM went from "~23 cycles per byte in 2009" to "0.65 cycles per byte" on Skylake. [vendor/author] [checked 2026-11-09] — [Stanford security seminar page](https://crypto.stanford.edu/seclab/sem-15-16/gueron.html)
- ChaCha20 AVX-512 ~0.57 cycles/byte with Poly1305 adding ~0.35 (OpenSSL, moderncrypto list) — [third party, search summary only; page unreachable today] — [moderncrypto archive](https://moderncrypto.org/mail-archive/noise/2017/001210.html)
- TLS 1.3 record framing (RFC 8446 §5): TLSCiphertext = opaque_type (1 byte, always 23) + legacy_record_version (2 bytes, 0x0303) + length (2 bytes) + encrypted_record; TLSInnerPlaintext = content + 1-byte content type + zero padding; plaintext ≤ 2^14 bytes; ciphertext ≤ 2^14 + 256 (AEAD expansion ≤ 255 octets); "The length of the AEAD output will generally be larger than the plaintext." AES-GCM and ChaCha20-Poly1305 tags are 16 bytes (restated; RFC 5116/8439). [standard] [checked 2026-11-09] — [RFC 8446](https://www.rfc-editor.org/rfc/rfc8446)

### Inferences
- Break-even bandwidths computed from the vendor tables with the Section 1 inequalities (single core, Silesia ratios; database columns compress differently — Raasveldt saw 2.2x Snappy on lineitem, 10x on ontime):
  - LZ4 (r=2.1, C_c=770, C_d=4950 MB/s): sequential model `B < (1 - 1/2.1) / (1/770 + 1/4950) ≈ 349 MB/s ≈ 2.8 Gbit/s`; overlapped model `B < min(C_c, C_d) = 770 MB/s ≈ 6.2 Gbit/s`.
  - zstd -1 (r=2.9, 510, 1550): sequential ≈ 251 MB/s ≈ 2.0 Gbit/s; overlapped ≈ 4.1 Gbit/s. zstd --fast=4 (2.15, 665, 2050): sequential ≈ 268 MB/s ≈ 2.1 Gbit/s; overlapped ≈ 5.3 Gbit/s.
  - zlib -1 (2.74, 105, 390): sequential ≈ 52 MB/s ≈ 0.42 Gbit/s; overlapped ≈ 0.84 Gbit/s.
  - Against links: 1 Gbit/s (125 MB/s) — all of LZ4/zstd/zlib pay; 10 Gbit/s (1,250 MB/s) — none pays on one core, LZ4/zstd pay only with ≥2–3 compressing cores and overlapped pipelines; 25 Gbit/s (3,125 MB/s) — only with ≥4–6 cores per direction, i.e. not worth it for a client driver. This matches Raasveldt's heuristic and MySQL's "compression dominates even at 100 Mbit" with zlib.
  - Decompression is cheap for LZ4 (≈4–5 GB/s ≈ 32–40 Gbit/s per core): a client can always afford to accept LZ4-compressed streams; the question is only whether the server can afford to compress.
- TLS per-record overhead for small messages: `overhead_fraction = 22 / (payload + 22)`; a 64-byte message is 34% framing, a 1 KB message 2.1%, a 16 KB record 0.13%. Plus per-record AEAD setup (Cloudflare's crossover at 320 bytes shows per-record fixed cost is non-trivial). Consequence: never flush one TLS record per protocol message; buffer a pipeline/batch and write once (`writev` -> one record of up to 16 KB), and let the TLS library split large chunks into 16 KB records.
- Cipher throughput budget (derived): at 0.65 cycles/byte AES-GCM on a 3.5 GHz core ≈ 5.4 GB/s ≈ 43 Gbit/s per core; at <2 cycles/byte ChaCha20-Poly1305 ≈ 1.75 GB/s ≈ 14 Gbit/s per core (Haswell). Encryption is therefore not the bottleneck for a 10–25 GbE client with AES-NI; it is comparable to the link only on CPUs without AES-NI/CLMUL (prefer ChaCha20-Poly1305 there) and dwarfs text decoding cost either way.

### Gaps
- zstd levels 2–3 are not tabulated in the README (charts); use `zstd -b1 -e3` on the target machine.
- No single like-for-like AES-GCM vs ChaCha20-Poly1305 GB/s table on one modern CPU was reachable today; run `openssl speed -evp aes-128-gcm chacha20-poly1305` for the deployment hardware.
- Compression ratios/throughputs for database result-set chunks (not Silesia) exist only in Raasveldt's 2017 tables; they should be re-measured on current codecs with 1 MB column-major chunks.
