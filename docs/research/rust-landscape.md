# Rust database-connectivity landscape (state as of 2026-11-09)

Scope: every serious Rust crate that plays the JDBC/ODBC role, how each is built, what has been measured, where each is weak, and what an "karez" could legally and sensibly reuse.

Tagging conventions used throughout:
- `[vendor]` = number/claim published by the project itself; `[third party]` = independent measurement; `[checked 2026-11-09]` = source opened during this research (the brief asked for 2026-11-07; the web tools were rate-limited until 2026-11-09, so every live check carries that date).
- crates.io "recent downloads" is the registry's rolling ~90-day figure. GitHub "open issues" counts include open PRs.
- All crates.io and GitHub-API figures below are `[vendor][checked 2026-11-09]` unless stated otherwise; the API URLs are `https://crates.io/api/v1/crates/<name>` and `https://api.github.com/repos/<owner>/<repo>`.

## Q1. Inventory and status (last release, last commit, maintainers, license, downloads, stars) — including tokio-rs/rdbc and why it stalled

### Takeaway
The ecosystem has one dominant multi-DB async toolkit (sqlx, 184.8M downloads, 4,249 dependent crates), one dominant per-engine native driver family (rust-postgres: tokio-postgres 85M, postgres-protocol 91M), one dominant embedded binding (rusqlite, 148.9M, 6,001 dependents), and a long tail of single-vendor drivers whose maintenance ranges from excellent (odbc-api, mysql_async) to stale (rust-oracle: no release since 2025-01; suharev7 clickhouse-rs: last push 2024-07). tokio-rs/rdbc (583 stars) has had no commit since 2021-05-23; its creator called it "comatose" in Jan 2021, and every one of its successor projects (rdbc2, rdbc-rs, jdbc-rs) is also dormant. Three ownership moves happened in 2025–2026 that matter for citations: sqlx -> `transact-rs/sqlx`, rust-postgres -> `rust-postgres/rust-postgres`, tiberius -> `tiberius-rs/tiberius`, diesel_async -> `diesel-rs/diesel_async`.

### Inferences
- Measured by dependents and downloads, any new common API must interoperate with sqlx (4,249 dependents) and rusqlite (6,001 dependents) rather than displace them; the entire "RDBC" family combined has under 25k lifetime downloads.
- tokio-rs/rdbc stalled for three compounding reasons visible in its tracker: a sync, JDBC-copied API that could not express async without `async fn` in traits (stabilised only in Rust 1.75, Dec 2023), a single part-time author who moved to Ballista/DataFusion, and an unresolved trait-object-vs-generics design argument (#64) that was never decided.
- Three of the single-vendor drivers an RDBC-next would need are maintenance risks: rust-oracle (22 months without a release), tiberius (org transfer with no named maintainers, empty Releases page), and the native-protocol ClickHouse crate (abandoned; the official crate is HTTP-only).

## Q2. Architecture of each (sync/async, native vs C wrapper, protocol, caches, pipelining, TLS, types, rows, Arrow, bulk, pooling, transactions, cancellation, errors, LISTEN, type erasure)

### Takeaway
Every PostgreSQL and MySQL driver in the list implements the wire protocol in pure Rust (sqlx, rust-postgres, mysql_async, tiberius, xitca-postgres); every SQLite, DuckDB, Oracle, ODBC, and Snowflake-ADBC driver wraps a C/Go library. Only two production clients pipeline (tokio-postgres and anything built on it, plus xitca-postgres); sqlx explicitly runs I/O in the calling task and cannot pipeline. Columnar (Arrow) output exists only in the analytics layer (arrow-odbc, ADBC, connectorx, duckdb-rs, datafusion-table-providers); all OLTP drivers are row-at-a-time. The only runtime-erased common API in wide use is sqlx's `Any` driver, which is restricted to nine scalar type kinds and uses boxed trait objects selected by URL scheme.

### Cited Findings

**sqlx (transact-rs/sqlx)**
- "a pure Rust SQL crate"; supports PostgreSQL, MySQL, MariaDB, SQLite; MSSQL "was supported prior to version 0.7, but has been removed pending a full rewrite of the driver" — [README](https://raw.githubusercontent.com/launchbadge/sqlx/main/README.md) `[vendor][checked 2026-11-09]`.
- Runtimes: `runtime-tokio`, `runtime-async-std` (deprecated), and in 0.9.0 "Adds `runtime-smol` and `runtime-async-global-executor` features to replace usages of the deprecated `async-std` crate" — [CHANGELOG](https://raw.githubusercontent.com/launchbadge/sqlx/main/CHANGELOG.md).
- TLS: `tls-native-tls`, `tls-rustls` (ring/webpki), `tls-rustls-aws-lc-rs`, `tls-rustls-ring-native-roots`, `tls-none` — [docs.rs features](https://docs.rs/crate/sqlx/latest/features).
- Protocol: "Prepared statements are cached per connection" and use "a binary mode of communication (lower bandwidth and faster decoding)"; row data is "decoded on demand"; SQLite is bundled and statically linked by default (`sqlite-unbundled` links the system library) — [README](https://raw.githubusercontent.com/launchbadge/sqlx/main/README.md).
- Pipelining: not supported; maintainer abonander (2023) said SQLx "runs I/O in the calling task, while tokio-postgres uses a separate connection task" and matching that "would enable pipelining" but is "a non-trivial refactor" — [issue #2436](https://github.com/launchbadge/sqlx/issues/2436). Issue #408 "Query pipelining" (opened 2020-06-13) is still open, labelled "low priority", last comment 2026-07-30; mehcode (2020) wrote "Supporting query pipelining is fairly simple at the protocol level" but prioritised it low because API servers run "2-3 complex queries per request" — [issue #408](https://github.com/launchbadge/sqlx/issues/408). PR #3891 "Postgres: Move io to background task" (opened 2025-06-08) was closed unmerged 2026-09-14; abonander said moving only I/O would not fix desync "while stateful `.await`s remain in the calling task" and proposed encapsulating protocol handling in a worker with "per-command result channels for pipelining", which "would require a breaking change to `Executor`" — [PR #3891](https://github.com/launchbadge/sqlx/pull/3891) `[vendor][checked 2026-11-09]`.
- Types: feature-gated `uuid`, `chrono`, `time`, `bstr`, `bigdecimal`, `rust_decimal`, `ipnet`, `ipnetwork`, `mac_address`, `bit-vec`, `json` (serde_json for Postgres JSON/JSONB) — [docs.rs features](https://docs.rs/crate/sqlx/latest/features). NULL is `Option<T>`; sqlx is "not an ORM" and has no DSL — [README](https://raw.githubusercontent.com/launchbadge/sqlx/main/README.md).
- Pool: built-in `sqlx::Pool`; `PoolOptions` has `max_connections`, `min_connections`, `acquire_timeout`, `acquire_slow_threshold`, `idle_timeout`, `max_lifetime`, `test_before_acquire` (default true), hooks `after_connect`/`before_acquire`/`after_release`; the docs contain no fairness/FIFO statement — [docs.rs PoolOptions](https://docs.rs/sqlx-core/latest/sqlx_core/pool/struct.PoolOptions.html) `[checked 2026-11-09]`.
- Type erasure (`Any` driver): "The underlying database drivers are chosen at runtime from the list set via `install_drivers`"; "Any use of `AnyConnection` or `AnyPool` without this will panic"; `Any` is an "Opaque database driver... The actual driver used will be selected at runtime, from the connection url"; `AnyKind` is deprecated — [docs.rs sqlx::any](https://docs.rs/sqlx/latest/sqlx/any/index.html). `AnyTypeInfoKind` has exactly nine variants: `Null, Bool, SmallInt, Integer, BigInt, Real, Double, Text, Blob` — [docs.rs AnyTypeInfoKind](https://docs.rs/sqlx/latest/sqlx/any/enum.AnyTypeInfoKind.html) `[vendor][checked 2026-11-09]`. The SQLite `Any` adapter returns a driver error for unmapped SQLite types; sea-query's Any binding panics for IpNetwork/MacAddress/array/vector arguments — [sqlx-sqlite any.rs](https://docs.rs/sqlx-sqlite/0.8.6/src/sqlx_sqlite/any.rs.html), [sea-query-sqlx any](https://docs.rs/sea-query-sqlx/latest/src/sea_query_sqlx/sqlx_any.rs.html) `[third party, via search]`. In 2021 abonander acknowledged "the boxed trait objects in use were a known inefficiency" pending async-fn-in-traits — [issue #1481](https://github.com/launchbadge/sqlx/issues/1481).
- 0.9.0 API change relevant to a generic API: "all `query*()` functions now take `impl SqlSafeStr`" (only `&'static str` qualifies by default; dynamic SQL must be wrapped in `AssertSqlSafe`) — [CHANGELOG](https://raw.githubusercontent.com/launchbadge/sqlx/main/CHANGELOG.md), [discussion #4271](https://github.com/transact-rs/sqlx/discussions/4271).

**rust-postgres (tokio-postgres / postgres / postgres-protocol / postgres-types)**
- "An asynchronous, pipelined, PostgreSQL client"; `connect` returns a `Client` and a `Connection`: "The connection object performs the actual communication with the database, so spawn it off to run on its own"; pipelining "happens automatically when futures are polled concurrently" (e.g. `future::try_join`) — [docs.rs tokio-postgres](https://docs.rs/tokio-postgres/latest/tokio_postgres/) `[vendor][checked 2026-11-09]`.
- Runtime: works with any `AsyncRead + AsyncWrite`; `runtime` feature (default) adds tokio conveniences. TLS via external crates `postgres-openssl` and `postgres-native-tls` (rustls via third-party `tokio-postgres-rustls`, not named in docs). Type features: `with-bit-vec-0_6..0_9`, `with-chrono-0_4`, `with-cidr-0_3`, `with-eui48-1`, `with-geo-types-0_7`, `with-jiff-0_1/0_2`, `with-serde_json-1`, `with-uuid-1`, `with-time-0_3`; no rust_decimal/bigdecimal feature (rust_decimal's own `db-tokio-postgres` feature supplies NUMERIC) — [docs.rs tokio-postgres](https://docs.rs/tokio-postgres/latest/tokio_postgres/), [rust_decimal postgres driver source](https://docs.rs/crate/rust_decimal/1.33.1/source/src/postgres/driver.rs).
- COPY: `CopyInSink` for `COPY ... FROM STDIN`, `CopyOutStream` for `COPY ... TO STDOUT`, `binary_copy` module; cancellation: `CancelToken` "The capability to request cancellation of in-progress queries"; notifications: `Notification` struct and `AsyncMessage` enum delivered from the `Connection` stream — [docs.rs tokio-postgres](https://docs.rs/tokio-postgres/latest/tokio_postgres/).
- Rows: `Row::get<'a, I, T>(&'a self, idx: I) -> T where T: FromSql<'a>` — the lifetime lets `&str`/`&[u8]` borrow from the row buffer; `raw_size_bytes` exposes row size; `get` panics on bad index/type, `try_get` returns `Error` — [docs.rs Row](https://docs.rs/tokio-postgres/latest/tokio_postgres/row/struct.Row.html).
- No built-in statement cache or pool: deadpool-postgres adds `StatementCache` per `ClientWrapper` with `prepare_cached()` and `RecyclingMethod::{Fast (default since 0.8, only `is_closed`), Verified}` — [docs.rs deadpool-postgres](https://docs.rs/deadpool-postgres/latest/deadpool_postgres/).
- Sync `postgres`: "simply a wrapper around a `tokio_postgres::Client` along side a tokio `Runtime`"; has `CopyInWriter`/`CopyOutReader`, `Notifications`, `CancelToken` — [docs.rs postgres](https://docs.rs/postgres/latest/postgres/).
- postgres-protocol: "Low level Postgres protocol APIs" — modules `authentication` (SASL deps hmac/sha2), `message` (backend/frontend), `types` (binary format conversions), `escape`, `password`; "assumes that the `client_encoding` backend parameter has been set to `UTF8`"; MIT OR Apache-2.0 — [docs.rs postgres-protocol](https://docs.rs/postgres-protocol/latest/postgres_protocol/).

**xitca-postgres / may_postgres (pipelined derivatives)**
- xitca-postgres: "builds on rust-postgres", offers async and blocking APIs, "A built-in connection pool with pipelining enabled", zero-copy rows ("Row data is held in reference-counted byte buffers, so values can be sliced and parsed without copying"), rustls TLS, optional io_uring via `tokio-uring-xitca` (nightly), a QUIC transport proxy; stated cons: "public type parameters expose lifetimes" — [README](https://raw.githubusercontent.com/HFQR/xitca-web/main/postgres/README.md) `[vendor][checked 2026-11-09]`.

**mysql_async / mysql / mysql_common**
- mysql_async: "Tokio based asynchronous MySql client library"; TLS "native-tls – this is the default option" or rustls; text protocol in `query*` ("values come back as strings"), binary protocol in `exec*` ("the only way to pass Rust values as parameters"); statement cache via `stmt_cache_size`; built-in `Pool` (`pool_min`, `pool_max`, `reset_connection`; "`Pool::new` is lazy"); LOCAL INFILE handlers; protocol compression; `binlog` feature; type flags proxied to mysql_common (`bigdecimal`, `rust_decimal`, `chrono`, `time`, `frunk`); pipelining not mentioned — [README](https://raw.githubusercontent.com/blackbeam/mysql_async/master/README.md).
- mysql (sync): same split (`query*` text, `prep`/`exec*` binary), LRU statement cache (`stmt_cache_size`, bounded by server `max_prepared_stmt_count`), named parameters `:name` via `params!` (cannot mix with positional), compression levels, TLS `native-tls` / `rustls-tls` (aws-lc-rs) / `rustls-tls-ring` / bare `rustls` — [README](https://raw.githubusercontent.com/blackbeam/rust-mysql-simple/master/README.md).
- mysql_common: "an implementation of basic MySql protocol primitives" — packets, value, row, params/named_params, binlog (v4+), auth plugins `caching_sha2_password`, `mysql_native_password`, `sha256_password`, clear-text, MariaDB `client_ed25519` and `client_parsec`; `FromValue`/`FromRow` derives; MIT OR Apache-2.0 — [docs.rs mysql_common](https://docs.rs/mysql_common/latest/mysql_common/).

**rusqlite**
- Ergonomic wrapper over `libsqlite3-sys` FFI with pregenerated bindings (`buildtime_bindgen` optional); `bundled` compiles SQLite 3.54.0 (rusqlite 0.41.0 / libsqlite3-sys 0.39.0), base supports SQLite >= 3.45.3; features: `backup`, `blob` (Read/Write/Seek), `hooks`, `preupdate_hook`, `trace`, `unlock_notify`, `functions`, `window`, `load_extension`, `loadable_extension`, `collation`, `limits`, `vtab`/`series`/`csvtab`/`array`, `session`, `serialize`, `chrono`/`time`/`jiff`/`serde_json`/`uuid`/`url`, `i128_blob`, `bundled-sqlcipher`, `ffi-sqlite-wasm-rs`; MIT — [README](https://raw.githubusercontent.com/rusqlite/rusqlite/master/README.md).

**tiberius (MSSQL)**
- Pure-Rust TDS: "The `Client` takes a socket implementing the `AsyncRead` and `AsyncWrite` traits from futures-rs" (works on tokio, async-std, smol); SQL Server 2022/2019/2017 "Tested on CI", 2016–2008 "Should work", 2005 with `tds73` off; TLS `native-tls` (default), `rustls`, `vendored-openssl`; encryption `Required` (default) / `Off` (login only) / `NotSupported`; auth: SQL login, `winauth` SSPI/NTLM (Windows), `integrated-auth-gssapi`, `sspi-rs` (pure-Rust NTLM on Unix); type flags `chrono`, `time`, `rust_decimal`, `bigdecimal`; `sql-browser-tokio/-smol`; "connection pooling" is a stated non-goal — [README](https://raw.githubusercontent.com/prisma/tiberius/main/README.md), [repo page](https://github.com/tiberius-rs/tiberius). Bulk insert: `BulkLoadRequest::send(TokenRow)` flushes "only when a full packet of data is buffered"; `finalize()` required or rows are not stored — [docs.rs BulkLoadRequest](https://docs.rs/tiberius/latest/tiberius/struct.BulkLoadRequest.html). NUMERIC is stored in i128 with maximum precision 38 — [tiberius numeric.rs](https://docs.rs/crate/tiberius/latest/source/src/tds/numeric.rs) `[via search]`.

**rust-oracle**
- "an Oracle database driver for Rust based on ODPI-C"; requires "Oracle client 11.2 or later" at runtime and a C compiler at build; sync API; `Option<T>` for nullable columns otherwise `Error::NullValue`; features `chrono`, `stmt_without_lifetime`, `aq_unstable`; MSRV 1.68; UPL-1.0 or Apache-2.0 — [README](https://raw.githubusercontent.com/kubo/rust-oracle/master/README.md).

**odbc-api / arrow-odbc**
- "Write ODBC Applications in (mostly) safe Rust"; targets "An ODBC 3.8 environment"; block cursors fetch whole row sets into bound buffers; `ColumnarBulkInserter` for array-parameter inserts; narrow vs UTF-16 string binding; polling variants (`CursorPolling`, `ConcurrentBlockCursor` on a dedicated thread) exist, so not strictly sync-only; MIT — [docs.rs odbc-api](https://docs.rs/odbc-api/latest/odbc_api/).
- arrow-odbc: reads an ODBC source "as a sequence of Arrow record batches", batch size via `with_max_bytes_per_batch`; type map: Integer->Int32, BigInt->Int64, Numeric/Decimal (precision <=38)->Decimal128, Date->Date32, Time32/Time64 and Timestamp precision by ODBC precision, Varbinary->Binary, fallback Utf8; write path maps Arrow->ODBC with timezone timestamps degraded to VarChar; author calls the write mapping "not the optimal yet" — [README](https://raw.githubusercontent.com/pacman82/arrow-odbc/main/README.md).

**diesel / diesel-async**
- diesel backends are C-library bound: `postgres` feature adds `pq-sys` (libpq), `mysql` adds `mysqlclient-sys`, `sqlite` adds `libsqlite3-sys`; `pq-src`/`mysqlclient-src` bundle the client sources; `numeric` = bigdecimal; column-count features 32/64/128; 27 features — [docs.rs diesel features](https://docs.rs/crate/diesel/latest/features). diesel.rs notes Diesel and rusqlite "depend on native C client libraries that must be installed first" while diesel-async, SQLx, SeaORM (except SQLite), tokio-postgres, postgres, mysql-async, mysql are pure Rust — [compare_diesel](https://diesel.rs/compare_diesel.html).
- diesel-async: "designed to work in combination with diesel, not to replace diesel"; backends `postgres` (tokio-postgres) and `mysql` (mysql_async); pools deadpool, bb8, mobc; transactions auto-roll-back on closure error; dual MIT/Apache-2.0 — [README](https://raw.githubusercontent.com/weiznich/diesel_async/main/README.md). Pipelining "is supported by diesel-async and tokio-postgres, but not by SQLx or SeaORM" — [compare_diesel](https://diesel.rs/compare_diesel.html).

**sea-orm / sea-query**

**Pools**
- r2d2: sync, `ManageConnection` trait; adapters r2d2-postgres, r2d2-mysql, r2d2-sqlite, r2d2-oracle, r2d2-odbc, redis via redis-rs feature; r2d2-mongodb deprecated — [README](https://raw.githubusercontent.com/sfackler/r2d2/master/README.md).

**Arrow-native layer**
- arrow-adbc Rust: "An abstract Rust API to be implemented by vendor-specific drivers" (`Driver`, `Database`, `Connection`, `Statement` traits), "A driver manager which implements this same API, but dynamically loads drivers internally" over the C ABI, and a driver exporter (`adbc_ffi::export_driver!`, crate-type `cdylib`) — [rust/README](https://raw.githubusercontent.com/apache/arrow-adbc/main/rust/README.md). adbc_snowflake "is a Rust wrapper around the Go ADBC Snowflake driver, not a pure-Rust implementation"; `bundled` (default) "requires a Go compiler at build time", `linked` uses a prebuilt library, or runtime-only loading; results are Arrow record batches; docs.rs failed to build 0.18–0.23 — [docs.rs adbc_snowflake](https://docs.rs/adbc_snowflake/latest/adbc_snowflake/).

- duckdb-rs: API modeled on rusqlite; `Connection` is `Send` but not `Sync`; `appender-arrow` bulk inserts Arrow data; `vtab-arrow` converts RecordBatch<->DuckDB chunks; `polars`, `r2d2`, `extensions-full` (json, parquet); ICU extension excluded from `bundled` because of crates.io size limits — [README](https://raw.githubusercontent.com/duckdb/duckdb-rs/main/README.md).
- clickhouse (official): "Uses `RowBinaryWithNamesAndTypes` or `RowBinary` formats over HTTP transport"; "There are plans to implement `Native` format over TCP"; LZ4/LZ4HC/ZSTD; `native-tls` or `rustls-tls`; `inserter` feature; `Client::with_validation(false)` gives "x1.1 to x3 performance improvement" depending on data — [README](https://raw.githubusercontent.com/ClickHouse/clickhouse-rs/main/README.md).

**Generic API shapes**
- tokio-rs/rdbc: five traits `Driver` (`Sync + Send`, `connect(&self, url) -> Box<dyn Connection>`), `Connection` (`create`/`prepare` -> `Box<dyn Statement + '_>`), `Statement` (`execute_query(&[Value])` / `execute_update`), `ResultSet` (`next()`, typed getters `get_i8..get_f64/get_string/get_bytes` returning `Option`, 0-based), `ResultSetMetaData`; "the provided RDBC drivers are just wrappers around existing database driver crates"; "There is currently no `async` support"; "This is just an experimental PoC and is not currently suitable for anything" — [README](https://raw.githubusercontent.com/tokio-rs/rdbc/master/README.md). The trait-object-vs-generics debate (#64, 2020-07 to 2021-01) ended without decision: mversic wanted associated-type generics with a boxed wrapper, aloucks a `RawConnectionVTable` like `futures::task::RawWaker`, nmusatti (5 upvotes) argued dynamic dispatch is negligible next to I/O and that "sqlx already offers the generic approach, so RDBC should focus on the runtime-pluggable model" — [issue #64](https://github.com/tokio-rs/rdbc/issues/64).
- rdbc2: single `Database::new(url)` with `execute_query[_with_params]` and JSON/raw serialisation variants; no Connection/Statement/Row types documented — [README](https://raw.githubusercontent.com/CoLearn-Dev/rdbc2/main/README.md).
- jdbc-rs: `Builder::new().jdbc_url(..).build()`, `get_connection()`, `prepare_statement()`, `set_int`, `execute_query()`, `next()`, `get_string/get_int` over a JVM via JNI — [docs.rs README](https://docs.rs/crate/jdbc/latest/source/README.md).

### Inferences
- The two pipelining designs that exist (rust-postgres's split `Client`/`Connection` task, and xitca's pooled pipelining) both rely on a dedicated I/O task plus per-request response channels; sqlx's maintainers have now (2026-09) described exactly this design as the required path and flagged it as a breaking `Executor` change, so an RDBC-next that bakes in a worker-per-connection model would be ahead of sqlx, not behind.
- Nothing in the OLTP tier exposes SQLSTATE uniformly; each driver has its own error enum (sqlx `DatabaseError` trait, tokio-postgres `DbError` with `code()`, mysql `ServerError`, tiberius `Error::Server`). A common API would have to normalise these itself. (Direct doc fetches for the error types were not made; see Gaps.)
- The only engines for which a Rust-native wire implementation does not exist are Oracle (ODPI-C), Snowflake (REST or Go ADBC), and SQLite/DuckDB by nature; everything else can be pure Rust.

### Gaps
- `DatabaseConnection` enum variants for sea-orm 2.0, `AnyConnectionBackend` method list, and per-driver error/SQLSTATE surfaces were not fetched (docs.rs paths 404'd or were not attempted); they should be read from source before design.
- Row-buffer internals for sqlx (`PgRow`) and whether it allocates per column were not confirmed from source; searches surfaced only other crates' layouts.
- Decimal/JSON/array representation tables per driver were not compiled beyond the feature-flag names above.

**Compile-time measurements**

- Kobzol (2026-06-21) found `#[sqlx::test]` compile cost is dominated by generated code, not the proc macro itself — [blog](https://kobzol.github.io/rust/2026/06/21/optimizing-sqlx-test-rebuild-time.html) `[third party, via search]`.

### Inferences
- The TechEmpower gap is a pipelining/architecture gap, not a language gap: the same frameworks (axum, salvo, viz) differ 20–40x purely by swapping the driver, and all fast variants have a dedicated connection task that lets requests from many in-flight handlers share one socket.
- Diesel's suite is the right harness to reuse for an RDBC-next (daily, Criterion, three databases, already includes sqlx/sea-orm/tokio-postgres/rusqlite and newcomers like zero-postgres), but its results need the R pipeline to become readable; no one has published a table from it.
- No published benchmark covers MSSQL (tiberius), Oracle, or ODBC throughput in Rust.

### Gaps
- TechEmpower R23 single-query, multiple-query and update tables for Rust were not captured (browser daemon failed on the second pass); only Fortunes is recorded. Hardware details for `hw=ph` were not extracted.
- Diesel metrics: the full CSV (>10 MB) was not downloaded, so no cross-crate table at a common date is given; only schema, date range, and the newest rows are confirmed.
- ConnectorX paper experiment section (instance sizes, Dask/Modin/Turbodbc numbers) could not be parsed from the PDF text dump and the PDF renderer was unavailable locally.

- adbc_snowflake default build "requires a Go compiler at build time" — [docs.rs](https://docs.rs/adbc_snowflake/latest/adbc_snowflake/).

### Inferences
- Pure-Rust drivers converge on ~18–20 direct runtime dependencies (tokio, bytes, futures-*, TLS-agnostic) regardless of vendor; a new driver family can budget to that.
- sqlx's lockfile problem is structural to "one facade crate, many optional drivers" designs under current Cargo; an RDBC-next with per-driver crates and a thin trait crate avoids it by construction.

### Gaps
- Transitive dependency counts and binary-size contributions were not obtainable: lib.rs (which publishes them) returned 403 for every crate; the brief forbade running cargo on downloaded code. Only wtx self-publishes a size figure.
- rusqlite/duckdb-rs bundled C compile times were not found in published form.

## Q5. Known weaknesses recorded in issues

### Takeaway
sqlx's tracker documents the structural limits a common API must avoid: no pipelining (open since 2020), I/O in the calling task causing cancellation-safety desyncs, a nine-type `Any` driver, lockfile bloat, and macro compile cost. tokio-postgres's weaknesses are omissions rather than bugs (no pool, no statement cache, no rustls in-tree, no rust_decimal). tiberius's weakness is governance. Decimal handling is fragile across the board because every driver delegates to `rust_decimal` (96-bit mantissa, max 28 scale) or `bigdecimal`.

### Cited Findings
- sqlx `Any` limits: nine `AnyTypeInfoKind`s only — [docs.rs](https://docs.rs/sqlx/latest/sqlx/any/enum.AnyTypeInfoKind.html); SQLite adapter errors on unmapped types; downstream (sea-query) panics on IpNetwork/MacAddress/array/vector under Any; one project avoided Any because JSON "is implemented for Postgres and SQLite but not across every backend" — [search results](https://docs.rs/sea-query-sqlx/latest/src/sea_query_sqlx/sqlx_any.rs.html) `[third party]`. 0.9.0 still changed Any semantics ("breaking(any+mysql): correctly convert text and blob types to `AnyTypeInfo`", #4255) — [CHANGELOG](https://raw.githubusercontent.com/launchbadge/sqlx/main/CHANGELOG.md).
- sqlx pipelining/cancellation: issue #408 open since 2020-06-13 with activity in July 2026; PR #3891 closed 2026-09-14 because background I/O alone "would not fix the desync issues"; the author listed cancellation-safety, CopyBoth (#2924), query cancellation and `PgListener` drop as all blocked on the same refactor — [#408](https://github.com/launchbadge/sqlx/issues/408), [#3891](https://github.com/launchbadge/sqlx/pull/3891).
- sqlx SQLite: no non-blocking API, so "the sqlx driver runs commands on a background thread and returns results over an async channel", which was the explanation for the 2021 "60x" spikes — [#1481](https://github.com/launchbadge/sqlx/issues/1481).
- sqlx type inference: declaring parameters as TEXT caused a planner regression against `char(N)` columns (#2436) — [#2436](https://github.com/launchbadge/sqlx/issues/2436).
- sqlx decimal: #2688 "mismatched types" decoding DECIMAL into `rust_decimal::Decimal`; in #2887 a maintainer noted rust_decimal's 96-bit mantissa means out-of-range values "may result in truncation and thus loss of precision" — [#2688](https://redirect.github.com/launchbadge/sqlx/issues/2688), [#2887](https://github.hscsec.cn/launchbadge/sqlx/issues/2887) `[via search]`. rust_decimal PR #647 capped rescale so unbounded Postgres NUMERIC does not reach scale 29; rust_decimal 1.36.0 fixed `Numeric::NaN` being decoded as 0 — [rust-decimal PR #647](https://redirect.github.com/paupino/rust-decimal/pull/647), [CHANGELOG](https://rust-digger.code-maven.com/src/rust_decimal-1.36.0/CHANGELOG.md) `[via search]`.
- sqlx dependency/lockfile bloat and compile time: #3211, #3908, #4070, #1598 (see Q4).
- sqlx 0.9.0 process: `Cargo.lock` removed from git, breaking `cargo install --locked sqlx-cli`; a commenter objected on reproducibility grounds and the maintainer said the decision "is not set in stone" — [discussion #4271](https://github.com/transact-rs/sqlx/discussions/4271).
- tokio-postgres omissions: no statement cache (added by deadpool-postgres), no pool, rustls not in-tree, no rust_decimal feature — [docs.rs tokio-postgres](https://docs.rs/tokio-postgres/latest/tokio_postgres/), [docs.rs deadpool-postgres](https://docs.rs/deadpool-postgres/latest/deadpool_postgres/). deadpool-postgres's default `RecyclingMethod::Fast` "can occasionally return a connection that is no longer usable" on unreliable networks — [docs.rs deadpool-postgres](https://docs.rs/deadpool-postgres/latest/deadpool_postgres/).
- Pool fairness: sqlx `PoolOptions` docs make no fairness statement — [docs.rs](https://docs.rs/sqlx-core/latest/sqlx_core/pool/struct.PoolOptions.html); an old sqlx bench file compared "(fair)" vs "(unfair)" acquire, implying a removed or internal knob — [pg_pool.rs bench](https://github-redirect.dependabot.com/launchbadge/sqlx/blob/f02ff94e9ca6a26f741383e99071b6e60624fd0e/sqlx-bench/benches/pg_pool.rs) `[via search]`; bb8 exposes `QueueStrategy::{Fifo, Lifo}` explicitly — [docs.rs](https://docs.rs/bb8/latest/bb8/enum.QueueStrategy.html); deadpool documents only that "a Semaphore is used to make this Mutex as little contested as possible" — [docs.rs deadpool](https://docs.rs/deadpool/latest/deadpool/).
- tiberius maintenance: moved to `tiberius-rs` org with no named maintainers, empty Releases page, security contact still prisma.io — [repo](https://github.com/tiberius-rs/tiberius); historical RUSTSEC-2020-0010 unmaintained advisory on the original author's repo — [RustSec](https://rustsec.org/advisories/RUSTSEC-2020-0010.html); a third-party scorer rated tiberius 0.11.8 "62/100" with maintenance 5/25 — [depscope](https://depscope.dev/pkg/cargo/tiberius) `[third party, via search]`. connectorx still pins tiberius 0.7 — [Cargo.toml](https://raw.githubusercontent.com/sfu-db/connector-x/main/connectorx/Cargo.toml).
- rust-oracle: no release since 2025-01-02 and no push since 2025-03-23 — [GitHub API](https://api.github.com/repos/kubo/rust-oracle).
- ClickHouse: official crate has no native TCP protocol ("plans to implement `Native` format over TCP"); the native crate is dormant since 2024 — [README](https://raw.githubusercontent.com/ClickHouse/clickhouse-rs/main/README.md), [GitHub API](https://api.github.com/repos/suharev7/clickhouse-rs).
- diesel/rusqlite: native C client libraries "can make the first compilation harder"; trait-heavy crates "can produce hard-to-read error messages" — [compare_diesel](https://diesel.rs/compare_diesel.html) `[vendor]`.
- rdbc: fails to compile due to a `sqlparser` error (reported 2020-07 in #64; PR #68 "update sqlparser" never merged) — [#64](https://github.com/tokio-rs/rdbc/issues/64), [issues list](https://api.github.com/repos/tokio-rs/rdbc/issues?state=all&per_page=100).
- xitca-postgres self-reported weakness: "public type parameters expose lifetimes, which makes it hard to return these types from functions" — [README](https://raw.githubusercontent.com/HFQR/xitca-web/main/postgres/README.md).

### Inferences
- The failure mode shared by sqlx-Any and rdbc is the same: a lowest-common-denominator scalar type set with no escape hatch to driver-native types; both trackers show users leaving for driver-specific crates as a result.
- Decimal handling cannot be solved by picking a crate; a common API needs a wire-faithful decimal representation (digits + scale) with lossless conversion to rust_decimal/bigdecimal on request.

### Gaps
- No issue specifically documenting sqlx "allocation per row" was found; the claim in the brief could not be sourced.
- mysql_async and rusqlite weakness threads were not surveyed beyond their READMEs.

## Q6. What a new project could legally and sensibly reuse vs write from scratch

### Takeaway
Every protocol-level building block for PostgreSQL and MySQL is available under MIT OR Apache-2.0 and is already consumed by multiple independent drivers: `postgres-protocol`/`postgres-types` (82 direct dependents) and `mysql_common` (60 direct dependents) are explicitly designed as shared primitives. TDS has no separate protocol crate (tiberius is monolithic, MIT/Apache-2.0, forkable). ODBC, Oracle, SQLite and DuckDB must remain FFI wrappers over C libraries with their own licences (SQLite public domain, DuckDB MIT, ODPI-C UPL/Apache, unixODBC LGPL on Linux). Only wtx (MPL-2.0) and snowflake-api (Apache-2.0 but built on an undocumented API) carry licence or stability caveats.

### Cited Findings
- postgres-protocol: "building block for higher-level libraries such as rust-postgres"; message encode/decode, binary type conversion, SASL auth, escaping, password hashing; MIT OR Apache-2.0; 82 direct reverse dependencies — [docs.rs](https://docs.rs/postgres-protocol/latest/postgres_protocol/), [reverse deps](https://crates.io/api/v1/crates/postgres-protocol/reverse_dependencies?per_page=1). xitca-postgres already demonstrates a pipelined, zero-copy client "builds on rust-postgres" pieces — [README](https://raw.githubusercontent.com/HFQR/xitca-web/main/postgres/README.md).
- postgres-types: 0.2.14, MIT OR Apache-2.0, 90.5M downloads — [crates.io](https://crates.io/api/v1/crates/postgres-types).
- mysql_common: packets, values, rows, params, auth plugins (incl. MariaDB ed25519/parsec), binlog, derives; MIT OR Apache-2.0; already shared by `mysql` and `mysql_async`, and connectorx depends on it directly (0.32) rather than on a client — [docs.rs](https://docs.rs/mysql_common/latest/mysql_common/), [connectorx Cargo.toml](https://raw.githubusercontent.com/sfu-db/connector-x/main/connectorx/Cargo.toml).
- tiberius: MIT/Apache-2.0 dual licence; no separate TDS protocol crate exists in the inventory; bulk load, encryption modes, SSPI/GSSAPI/sspi-rs auth and i128 NUMERIC are implemented inside the one crate — [crates.io](https://crates.io/api/v1/crates/tiberius), [repo](https://github.com/tiberius-rs/tiberius), [BulkLoadRequest](https://docs.rs/tiberius/latest/tiberius/struct.BulkLoadRequest.html).
- sqlx: MIT OR Apache-2.0 — [crates.io](https://crates.io/api/v1/crates/sqlx). Its `sqlx-postgres`/`sqlx-mysql` protocol code is reusable by licence but is coupled to sqlx-core's `Executor`/`Connection` traits and its in-task I/O model that maintainers now plan to replace — [PR #3891](https://github.com/launchbadge/sqlx/pull/3891).
- rusqlite/libsqlite3-sys: MIT; bundled SQLite public domain; bundled SQLCipher BSD-style — [README](https://raw.githubusercontent.com/rusqlite/rusqlite/master/README.md). duckdb-rs: MIT, "copyright Stichting DuckDB Foundation" — [README](https://raw.githubusercontent.com/duckdb/duckdb-rs/main/README.md).
- rust-oracle: UPL-1.0 or Apache-2.0; needs Oracle Client 11.2+ at runtime (proprietary redistributable), compiles ODPI-C with a C compiler — [README](https://raw.githubusercontent.com/kubo/rust-oracle/master/README.md).
- odbc-api/arrow-odbc: MIT; require a platform ODBC driver manager — [docs.rs odbc-api](https://docs.rs/odbc-api/latest/odbc_api/), [arrow-odbc README](https://raw.githubusercontent.com/pacman82/arrow-odbc/main/README.md).
- arrow-adbc Rust: Apache-2.0; `adbc_core` traits (`Driver`, `Database`, `Connection`, `Statement`) plus `adbc_ffi::export_driver!` let a Rust driver be loaded by any language's ADBC driver manager — [rust/README](https://raw.githubusercontent.com/apache/arrow-adbc/main/rust/README.md), [adbc_core](https://crates.io/api/v1/crates/adbc_core). The Snowflake driver is Go behind FFI — [docs.rs adbc_snowflake](https://docs.rs/adbc_snowflake/latest/adbc_snowflake/).
- connectorx: MIT; it is itself a federation of `postgres`, `mysql_common`, `rusqlite`, `tiberius`, `oracle`, `clickhouse`, `gcp-bigquery-client`, `prusto` behind `src_*` features — [Cargo.toml](https://raw.githubusercontent.com/sfu-db/connector-x/main/connectorx/Cargo.toml).
- datafusion-table-providers: Apache-2.0; same federation pattern over bb8/r2d2 + duckdb/clickhouse/oracle/adbc_core/arrow-odbc/arrow-flight — [Cargo.toml](https://raw.githubusercontent.com/datafusion-contrib/datafusion-table-providers/main/Cargo.toml).
- Pools: r2d2 MIT/Apache-2.0, bb8 MIT, deadpool MIT OR Apache-2.0, mobc MIT/Apache-2.0 — [r2d2](https://crates.io/api/v1/crates/r2d2), [bb8](https://crates.io/api/v1/crates/bb8), [deadpool](https://crates.io/api/v1/crates/deadpool), [mobc](https://crates.io/api/v1/crates/mobc).
- Licence caveats: wtx is MPL-2.0 — [crates.io](https://crates.io/api/v1/crates/wtx); rdbc-rs licence is "non-standard" with no repository — [crates.io](https://crates.io/api/v1/crates/rdbc-rs); rdbc2's GitHub licence field is null although crates.io says MIT — [GitHub API](https://api.github.com/repos/CoLearn-Dev/rdbc2), [crates.io](https://crates.io/api/v1/crates/rdbc2); rust-oracle's GitHub licence field is null (dual UPL/Apache per README) — [GitHub API](https://api.github.com/repos/kubo/rust-oracle); sea-query's GitHub licence shows NOASSERTION (crates.io: MIT OR Apache-2.0) — [GitHub API](https://api.github.com/repos/SeaQL/sea-query).
- tokio-rs/rdbc itself: Apache-2.0, "intentionally modeled directly after ODBC and JDBC", drivers "just wrappers around existing database driver crates" — [README](https://raw.githubusercontent.com/tokio-rs/rdbc/master/README.md).

### Inferences
- Reuse: postgres-protocol + postgres-types (wire + binary types), mysql_common (packets, auth, values, binlog), rusqlite/libsqlite3-sys, duckdb-rs, odbc-api (+arrow-odbc for columnar), rust-oracle (ODPI-C), adbc_core/adbc_ffi (to export drivers to other languages), bb8/deadpool as pool references. All are permissive and already multi-consumer.
- Write from scratch or fork: a TDS protocol crate (tiberius is monolithic and its governance is unclear; forking under MIT/Apache is legally clean), a ClickHouse native-TCP client (nothing maintained exists), the connection-worker/pipelining core (no reusable crate; xitca's is coupled to its web stack), the common type model (sqlx-Any's nine kinds are the only precedent and are inadequate), and SQLSTATE/error normalisation (nothing shared exists).
- Avoid as dependencies: wtx (MPL-2.0 copyleft-lite on a permissive stack), snowflake-api (undocumented upstream API), any of the rdbc-family crates (dormant, licence ambiguity).

### Gaps
- Licence texts of the C libraries behind ODBC driver managers (unixODBC LGPL-2.1, iODBC BSD/LGPL) and Oracle Instant Client redistribution terms were not fetched; they matter for static-linking decisions.
- Whether `postgres-protocol`'s API is stable enough to pin (its docs make no stability statement beyond the UTF-8 assumption) was not established beyond its 0.6.x line running since 2019.
