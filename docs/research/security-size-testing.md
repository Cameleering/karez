## Q1. Which authentication mechanisms must the driver implement per database, and which are must-haves for JDBC parity?

### Takeaway
For PostgreSQL the floor is SCRAM-SHA-256 with SCRAM-SHA-256-PLUS (tls-server-end-point) channel binding, plus MD5 only as a deprecated legacy; for MySQL it is `caching_sha2_password` with the RSA public-key fallback (since `mysql_native_password` is gone from 9.0); for MariaDB add `ed25519` and the newer PARSEC; for SQL Server it is SQL auth plus NTLM/Kerberos via SSPI and an Entra ID token (FedAuth) path. Cloud IAM flows (AWS RDS, GCP Cloud SQL) are all "short-lived token used as the password over TLS" and need only a pluggable password-provider hook, not a protocol change.

### Cited Findings

**PostgreSQL**
- PostgreSQL implements three SASL mechanisms: `SCRAM-SHA-256`, `SCRAM-SHA-256-PLUS` and (new in PG 18) `OAUTHBEARER`; SCRAM cites RFC 7677 and RFC 5802; the channel-binding type is `tls-server-end-point`; a channel-binding-capable client "should choose the channel-binding variant if it can support it". The server lists `SCRAM-SHA-256-PLUS` before `SCRAM-SHA-256` when built with SSL. OAUTHBEARER has no `-PLUS` variant and uses a two-connection discovery flow. [vendor][checked 2026-11-09] — [PostgreSQL 18 docs §54.3 SASL Authentication](https://www.postgresql.org/docs/current/sasl-authentication.html)
- RFC 5929 (July 2010) defines `tls-server-end-point` as a hash of the server certificate; if the certificate signature uses MD5 or SHA-1 the hash is SHA-256, otherwise the certificate's own hash algorithm; it is undefined when no or multiple hash functions are used and unavailable for PSK/anon-DH suites. The RFC recommends `tls-unique` in most cases but `tls-server-end-point` works through unmodified TLS-terminating proxies. [third party (IETF)][checked 2026-11-09] — [RFC 5929](https://www.rfc-editor.org/rfc/rfc5929.html)
- SCRAM base spec: [RFC 5802](https://www.rfc-editor.org/rfc/rfc5802.html); SCRAM-SHA-256 / -PLUS: [RFC 7677](https://www.rfc-editor.org/rfc/rfc7677.html) (URLs cited; not re-fetched this session).
- libpq `channel_binding` values are `require|prefer|disable`, default `prefer` when built with SSL; channel binding is "only supported over SSL connections with PostgreSQL 11 or later servers using the SCRAM authentication method". libpq `require_auth` accepts `password, md5, gss, sspi, scram-sha-256, oauth, none`, negatable with `!`, so a client can demand e.g. `require_auth=scram-sha-256` or `!password,!md5`. `gssencmode` default `prefer`; `sslcertmode` default `allow`. [vendor][checked 2026-11-09] — [libpq connection parameters (PG 18)](https://www.postgresql.org/docs/current/libpq-connect.html)
- Password methods: `scram-sha-256` is "the most secure of the currently provided methods"; `md5` is a custom, less secure challenge-response and the page carries a warning that "support for MD5-encrypted passwords is deprecated and will be removed in a future release"; `password` sends cleartext. If `md5` is in `pg_hba.conf` but the stored hash is SCRAM, the server automatically uses SCRAM. [vendor][checked 2026-11-09] — [PG 18 docs §20.5 Password Authentication](https://www.postgresql.org/docs/current/auth-password.html)
- pgJDBC parity reference: `channelBinding` default `prefer`; `gssEncMode` default `allow`; `requireAuth` supports `password, md5, gss, sspi, scram-sha-256, none`; `authenticationPluginClassName` is a pluggable password provider; `preferQueryMode` default `extended` ("always use bind/execute messages"); `sslfactory` default `org.postgresql.ssl.LibPQFactory`, `sslhostnameverifier` default `PGjdbcHostnameVerifier`. [project][checked 2026-11-09] — [pgJDBC connection properties](https://jdbc.postgresql.org/documentation/use/)

**MySQL**
- "The `mysql_native_password` authentication plugin is deprecated as of MySQL 8.0.34, disabled by default in MySQL 8.4, and removed as of MySQL 9.0.0." In 8.4 it can be re-enabled with `mysqld --mysql-native-password=ON`; with it disabled, accounts using it fail with `ERROR 1045` and `CREATE USER ... IDENTIFIED WITH 'mysql_native_password'` fails with `ERROR 1524`. 8.4 clients default to `caching_sha2_password`. [vendor][checked 2026-11-09] — [MySQL 8.4 manual, Native Pluggable Authentication](https://docs.oracle.com/cd/E17952_01/mysql-8.4-en/native-pluggable-authentication.html)
- MySQL 9.0.0 (released 2024-07-01) release notes: the plugin "has been removed, and the server now rejects `mysql_native` authentication requests from older client programs which do not have `CLIENT_PLUGIN_AUTH` capability. For backward compatibility, `mysql_native_password` remains available on the client; the client-side built-in authentication plugin has been converted into a dynamically loadable plugin." Removed server options: `--mysql-native-password`, `--mysql-native-password-proxy-users`, `default_authentication_plugin`. [vendor][checked 2026-11-09] — [MySQL 9.0.0 release notes](https://dev.mysql.com/doc/relnotes/mysql/9.0/en/news-9-0-0.html)
- `caching_sha2_password` (default in 8.4 via `authentication_policy`): SHA-256 hashes in `mysql.user`; in-memory server cache of successful logins; cache hit uses a challenge-response that "does not require a secure connection". First login after account creation / password change / `RENAME USER` / `FLUSH PRIVILEGES` must use either secure transport (TLS, Unix socket, shared memory) or RSA key-pair exchange (`--get-server-public-key` fetches the key from the server, less secure; `--server-public-key-path` uses a trusted local copy). Otherwise: `ERROR 2061 (HY000): Authentication plugin 'caching_sha2_password' reported error: Authentication requires secure connection.` `sha256_password` is deprecated and "subject to removal". [vendor][checked 2026-11-09] — [MySQL 8.4 manual, Caching SHA-2 Pluggable Authentication](https://dev.mysql.com/doc/refman/8.4/en/caching-sha2-pluggable-authentication.html)
- An Oracle MySQL blog post titled "MySQL 9.0: it's time to abandon the weak authentication method" exists but returned HTTP 403 to automated fetch; the dev.mysql.com manual pages above cover the same timeline. [vendor][checked 2026-11-09] — [blogs.oracle.com post](https://blogs.oracle.com/mysql/post/mysql-90-its-time-to-abandon-the-weak-authentication-method)

**MariaDB**
- PARSEC ("Password Authentication using Response Signed with Elliptic Curve") is available from MariaDB 11.6; stores salted passwords with PBKDF2 as KDF; the stored hash is an ed25519 public key derived from the PBKDF2 output; server sends a 32-byte scramble in an Authentication Switch Request, client requests the ext-salt with an empty packet, then returns its own 32-byte scramble plus an ed25519 signature over the concatenated scrambles. `parsec_iterations` variable added in MariaDB 13.1. Not the default in any shipped version; "intended to be the default in a future release" (MDEV-12320). [vendor][checked 2026-11-09] — [MariaDB KB: Authentication Plugin – PARSEC](https://mariadb.com/kb/en/authentication-plugin-parsec/)
- The MariaDB KB `ed25519` page did not render the plugin content (returned the generic installation page), so introduction version and mechanism are in Gaps. [checked 2026-11-09] — [MariaDB KB ed25519 URL](https://mariadb.com/kb/en/authentication-plugin-ed25519/)

**SQL Server**
- Microsoft JDBC Driver authentication modes and the version that introduced each: `ActiveDirectoryPassword` (6.0, now DEPRECATED), `ActiveDirectoryIntegrated` (6.0), `ActiveDirectoryMSI`/`ActiveDirectoryManagedIdentity` (8.3.1), `ActiveDirectoryInteractive` (9.2), `ActiveDirectoryServicePrincipal` (9.2), `ActiveDirectoryDefault` (12.2), `ActiveDirectoryServicePrincipalCertificate` (12.4), plus `SqlPassword` and the `accessToken` property for a caller-supplied token. Early versions depended on `Adal4j` 1.3.0–1.6.5, later on MSAL4J. Page dated 2026-01-16, updated 2026-09-18. [vendor][checked 2026-11-09] — [Connect using Microsoft Entra authentication – JDBC](https://learn.microsoft.com/en-us/sql/connect/jdbc/connecting-using-azure-active-directory-authentication)
- Tiberius (Rust) tests `IntegratedSecurity=true` on Windows with the `winauth` feature (SSPI) against SQL Server 2019 in CI (see Q11 for the full matrix). [project][checked 2026-11-09] — [tiberius test.yml](https://raw.githubusercontent.com/prisma/tiberius/main/.github/workflows/test.yml)

**Cloud IAM**
- AWS RDS IAM DB auth works with MariaDB, MySQL and PostgreSQL; tokens are generated with SigV4, have a 15-minute lifetime, are used as the password, and traffic must be SSL/TLS-encrypted. Token size is "generally about 1 KB but can be larger", so drivers must not truncate the password field. IAM auth needs 300–1000 MiB extra memory on the instance; custom Route 53 names cannot be used to generate the token; IAM + Kerberos cannot both be enabled for PostgreSQL. [vendor][checked 2026-11-09] — [RDS IAM database authentication](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/UsingWithRDS.IAMDBAuth.html)
- GCP Cloud SQL (PostgreSQL) manual IAM auth: pass an OAuth 2.0 access token (`gcloud sql generate-login-token`) as the password with `sslmode=require`; username is the full IAM e-mail (service accounts drop `.gserviceaccount.com`); the token is "too long to paste" so is passed via `PGPASSWORD`; automatic IAM auth is via Cloud SQL Auth Proxy v2 `--auto-iam-authn` or language connectors (Go, Java JDBC/R2DBC, Node.js, Python); roles needed `roles/cloudsql.instanceUser` (+`roles/cloudsql.client` with proxy). [vendor][checked 2026-11-09] — [Cloud SQL for PostgreSQL IAM logins](https://docs.cloud.google.com/sql/docs/postgres/iam-logins)
- Cloud SQL IAM tokens are OAuth 2.0 access tokens "valid for only one hour". [vendor][checked 2026-11-09] — [Cloud SQL MySQL IAM overview](https://docs.cloud.google.com/sql/docs/mysql/iam-overview)

**Oracle**
- Oracle Autonomous Database mTLS "requires that you supply Oracle database credentials including the Oracle wallets or Java KeyStore (JKS) files"; wallet URL pattern `jdbc:oracle:thin:@<service>?TNS_ADMIN=<wallet dir>`; TLS-only connections need no wallet on JDK 8u162+; JDBC uses TLS 1.3 when supported, fallback 1.2. [vendor][checked 2026-11-09] — [JDBC Thin connections with a wallet (mTLS)](https://docs.oracle.com/en/cloud/paas/autonomous-database/serverless/adbsb/connect-jdbc-thin-wallet.html), [without a wallet (TLS)](https://docs.oracle.com/en/cloud/paas/autonomous-database/serverless/adbsb/connect-jdbc-thin-tls.html)

### Inferences
- A driver that only ships SCRAM-SHA-256 (no `-PLUS`) is already behind libpq and pgJDBC, both of which default to `channel_binding=prefer`; the -PLUS variant costs one certificate hash and is the only thing that stops a certificate-relaying MITM when `sslmode<verify-full`.
- MD5 for PostgreSQL should be implemented but behind a "legacy" feature or runtime warning, mirroring the server's own deprecation; a `require_auth`-style allow-list (`scram-sha-256` only by default when TLS is on) prevents downgrade to `password`/`md5` by a hostile server.
- For MySQL, `caching_sha2_password` fast path + full path over TLS is mandatory; RSA public-key exchange over plaintext is needed for parity with libmysqlclient but should default to **off** unless the key file is supplied locally (`--server-public-key-path` semantics), because fetching the key from the server over plaintext is trivially MITM-able.
- `mysql_native_password` can be kept client-side (as Oracle did) at ~zero cost (SHA-1 scramble), but should not be selected by default.
- All cloud IAM schemes reduce to "password = short-lived token; TLS mandatory; token up to several KB; refresh before 15 min/1 h". A `PasswordProvider`/`TokenProvider` trait callable per connection attempt (not per pool) covers RDS, Cloud SQL, Entra `accessToken` and PG 18 OAUTHBEARER.
- SQL Server parity with mssql-jdbc needs SQL auth, NTLM/Kerberos via SSPI (Windows) / GSSAPI (Unix) and FedAuth token injection; the interactive/MSAL device-code flows are application concerns and can be left to a token provider.

### Gaps
- MariaDB `ed25519` plugin page did not render; introduction version (believed 10.1.22/10.2.5) and the "no salt" weakness PARSEC was designed to fix are unsourced here.
- Oracle Thin-driver Kerberos documentation for 23ai was not found in search results; only wallet/mTLS pages surfaced.
- The exact RFC 5802/7677 text was not re-fetched; only RFC 5929 was. The PostgreSQL SASL page does not cite RFC 5929 for `tls-server-end-point`, though it names the type.
- No document found that defines a formal "JDBC parity" checklist; the per-driver property tables above are the closest proxy.

## Q2. TLS: options in Rust, sslmode semantics and safe defaults, PG 17 direct SSL, TDS 8.0 strict, MySQL TLS 1.3, trust stores, measured rustls vs OpenSSL

### Takeaway
Every ecosystem's *default* is still "prefer/optional" for backward compatibility while the vendors themselves say it is not recommended; TDS 8.0 `Encrypt=strict` and libpq `sslrootcert=system` (which forces `verify-full`) show the direction. rustls (aws-lc-rs) now wins 14 of 16 ISRG benchmark tests against OpenSSL 3.6.1 and BoringSSL; `rustls-platform-verifier` is the recommended trust-store path; the std-only `cameleer-tls` crate exists (v0.4.0, published 2026-11-05/06) with a credible feature list but is self-declared unaudited and has non-constant-time AES.

### Cited Findings

**sslmode semantics and defaults**
- libpq `sslmode` table: `disable` (no eavesdrop/MITM protection), `allow`, `prefer` (**default**, "not recommended in secure deployments"), `require` (eavesdrop yes, MITM no), `verify-ca` (MITM "depends on CA policy"), `verify-full` (yes/yes). Quirk: if a root CA file exists, `require` behaves like `verify-ca`; apps "should not rely on this". `verify-full` matches SAN dNSName/iPAddress first, CN only if no SAN; wildcard `*` does not match `.`. [vendor][checked 2026-11-09] — [libpq SSL support](https://www.postgresql.org/docs/current/libpq-ssl.html)
- `sslrootcert=system` loads the SSL implementation's trusted roots and "the default `sslmode` is changed to `verify-full`, and any weaker setting will result in an error." `ssl_min_protocol_version` default `TLSv1.2`. [vendor][checked 2026-11-09] — [libpq connection parameters](https://www.postgresql.org/docs/current/libpq-connect.html)
- PostgreSQL 17 `sslnegotiation=direct`: "start SSL handshake directly after establishing the TCP/IP connection. This is only allowed with `sslmode=require` or higher, because the weaker settings could lead to unintended fallback to plaintext authentication when the server does not support direct SSL handshake." Default remains `postgres` (SSLRequest negotiation). [vendor][checked 2026-11-09] — [libpq connection parameters](https://www.postgresql.org/docs/current/libpq-connect.html)
- TDS 8.0 (SQL Server 2022+, Azure SQL DB/MI, Fabric): "The TLS handshake now precedes any TDS messages"; `Encrypt=strict` triggers TDS 8.0; TDS 7.x supports TLS only up to 1.2 while TDS 8.0 supports TLS 1.3; with `strict`, `TrustServerCertificate=true` is not allowed and `HostNameInCertificate` must be used instead. Connection string `Encrypt` default is **false**; `mandatory|true|yes` = TDS 7.x + TLS; `optional|false|no` = encrypt only if server requires. Minimum driver versions for `strict`: ADO.NET 5.1, ODBC 18.1.2.1, OLE DB 19.2.0, JDBC 11.2.0, PHP 5.10. SQL Server 2025 extends TDS 8.0 to Agent, sqlcmd, bcp, replication, AGs, linked servers. Page dated 2026-07-14. [vendor][checked 2026-11-09] — [TDS 8.0 – SQL Server](https://learn.microsoft.com/en-us/sql/relational-databases/security/networking/tds-8)
- mssql-jdbc's CVE-2025-59250 fix line was reported by a downstream vendor to have "encryption now enabled by default" as a breaking change (restore with `;encrypt=false`). [third party][checked 2026-11-09] — [CoreMedia release note CMS-28866](https://documentation.coremedia.com/cmcc-12/current/release-notes-webhelp/content/CMS-28866-1-2406.2.2.html)
- MySQL 8.4 "supports the TLSv1.2 and TLSv1.3 protocols" and "does not support the old TLSv1 and TLSv1.1 protocols" (removed in 8.0). TLS 1.3 requires server and client compiled with OpenSSL 1.1.1+; default TLS 1.3 ciphersuites: `TLS_AES_128_GCM_SHA256, TLS_AES_256_GCM_SHA384, TLS_CHACHA20_POLY1305_SHA256, TLS_AES_128_CCM_SHA256`; `TLS_AES_128_CCM_8_SHA256` is deprecated. [vendor][checked 2026-11-09] — [MySQL 8.4 Encrypted Connection TLS Protocols and Ciphers](https://dev.mysql.com/doc/refman/8.4/en/encrypted-connection-protocols-ciphers.html)

**TLS stacks available in Rust**
- `rustls-platform-verifier`: uses Windows CryptoAPI store (revocation supported), macOS/iOS Security.framework (revocation supported), Android Trust Manager (revocation "sometimes", API 24+), Linux/BSD system CA bundle via `webpki` (no revocation, loaded once at startup), WASM `webpki` roots. Maintainers recommend it as "the default for client-side apps on common OSes"; `webpki-roots` (static Mozilla roots) suggested for frequently redeployed containers; vs `rustls-native-certs` it honours per-root OS trust status and avoids parsing every CA. MSRV 1.85; example pins `0.5`. [project][checked 2026-11-09] — [rustls-platform-verifier README](https://github.com/rustls/rustls-platform-verifier)
- `cameleer-tls` (crates.io): description "Cameleer std-only TLS 1.3 / TLS 1.2 client and server with from-scratch cryptography"; versions 0.2.0 (2026-11-05), 0.2.1, 0.3.0, 0.4.0 (2026-11-06); 297 downloads; Apache-2.0; repo `github.com/pmsudhi/cameleer`; keywords `crypto, tls, camel, x509, std-only`. [project][checked 2026-11-09] — [crates.io API record](https://crates.io/api/v1/crates/cameleer-tls)
- `cameleer-tls` 0.4.0 docs: TLS 1.3 (RFC 8446) suites `TLS_AES_128_GCM_SHA256`, `TLS_AES_256_GCM_SHA384`, `TLS_CHACHA20_POLY1305_SHA256`, HelloRetryRequest, KeyUpdate, middlebox-compat, no 0-RTT; TLS 1.2 ECDHE-only with AEAD suites, extended master secret (RFC 7627), renegotiation refused; groups x25519, secp256r1, secp384r1; handshake sigs Ed25519, ECDSA P-256/P-384, RSA-PSS and PKCS#1 v1.5 (SHA-256/384/512); X.509 checks signatures, validity, basicConstraints, keyUsage, serverAuth EKU, pathLen; SAN DNS/IP matching with one left-most wildcard label, CN only without SAN; CRL revocation (cert with no matching CRL accepted); name constraints and policies tolerated not enforced; OCSP status contradictory (listed as not implemented and as an `ocsp` module); resumption via PSK tickets (1.3) and RFC 5077 (1.2); client certs supported; RNG `/dev/urandom` / `BCryptGenRandom` feeding ChaCha20 DRBG. Constant-time claims are "best effort": ChaCha20/Poly1305/X25519/GHASH/P-256/P-384 intended constant-time, **AES uses table-based S-boxes (cache-timing exposed; docs recommend ChaCha20-Poly1305 on shared hardware), RSA has no CRT or blinding, secrets are not zeroized on drop**, and the implementation "has not been audited". Only dependency is `cameleer-core ^0.4.0`; source 752.9 kB; doc coverage 54.54 %. Modules include `asn1, certgen, crypto, keystore, ocsp, pem, sasl, tls, x509`. [project][checked 2026-11-09] — [docs.rs cameleer_tls](https://docs.rs/cameleer-tls/latest/cameleer_tls/), [docs.rs crate page](https://docs.rs/crate/cameleer-tls/latest)
- Parent repo `pmsudhi/cameleer`: Apache-2.0 Rust reimplementation of Apache Camel, 17 workspace crates, "nothing but the Rust standard library" / "Dependencies: none" badge, 2,600+ hermetic tests, live suites against PostgreSQL/Redis/RabbitMQ etc., no third-party security audit mentioned, 2 stars, 365 commits, claims "5.8 MB binary" with only the `core` feature and 3 ms (README) vs 10 ms (About) startup. [project][checked 2026-11-09] — [github.com/pmsudhi/cameleer](https://github.com/pmsudhi/cameleer)
- Other stacks (named in the sqlx/tiberius CI matrices, Q11): `native-tls` (SChannel / Secure Transport / OpenSSL), `rustls` with `aws-lc-rs` or `ring` providers, `vendored-openssl`. Tiberius CI notes native-tls (Secure Transport) "can't complete the SQL Server TLS handshake" on macOS, so it omits that combination. [project][checked 2026-11-09] — [tiberius test.yml](https://raw.githubusercontent.com/prisma/tiberius/main/.github/workflows/test.yml)

**Measured performance**
- ISRG/Prossimo Q1 2026 update (published 2026-04-09, tests run March 2026): Rustls 0.23.37 + aws-lc-rs 1.16.0 vs OpenSSL 3.6.1 vs BoringSSL (March 2026 snapshot). Placements across all tests: Rustls 14 first / 2 second / 0 third; BoringSSL 2/10/4; OpenSSL 0/4/12. Hardware and per-suite MB/s are only in chart images. [project (ISRG funds rustls)][checked 2026-11-09] — [Q1 2026 Rustls Performance Update](https://www.memorysafety.org/blog/26q1-rustls-performance/)
- InfoQ summary of the same series: OpenSSL "about 1.38x slower on handshakes and about 1.18x slower on throughput" than Rustls on x86_64. [third party][checked 2026-11-09] — [InfoQ, Rustls one decade](https://www.infoq.com/news/2026/09/rustls-one-decade/)
- Earlier ISRG report (Jan 2024, Rustls 0.22.0 vs OpenSSL 3.2.0): bulk send roughly even on AES suites, receive 7–17 % slower due to an extra copy, ChaCha20 ~45 % behind (AVX-512 in OpenSSL). [project][checked 2026-11-09] — [Rustls on track to outperform OpenSSL](https://www.memorysafety.org/blog/rustls-performance/)
- ISRG server-side report (2025): Rustls core handshake latency roughly 2x lower than OpenSSL. [project][checked 2026-11-09] — [Rustls Server-Side Performance](https://www.memorysafety.org/blog/rustls-server-perf/)
- Original author's 2019 benchmark showed a smaller (~20 %) handshake advantage. [third party][checked 2026-11-09] — [jbp.io 2019](https://jbp.io/2019/07/02/rustls-vs-openssl-handshake-performance.html)

### Inferences
- Safe 2026 default for a new driver: **`verify-full` semantics when any TLS is requested, with `prefer` kept only as an explicit opt-in**, mirroring `sslrootcert=system` behaviour; expose `require`/`verify-ca` for self-signed deployments; make `disable` explicit. For SQL Server, default to `Encrypt=mandatory` with certificate validation and support `strict` (TDS 8.0, TLS-first) so TLS 1.3 is reachable.
- Implement PG 17 direct SSL as an optimisation only when `sslmode>=require` (as libpq enforces) — saves one round trip and lets a network filter see a plain TLS ClientHello, same rationale as TDS 8.0.
- `cameleer-tls` meets the *feature* bar for database TLS (1.3+1.2, x25519/P-256, ECDSA/RSA-PSS/Ed25519, SAN hostname check, client certs, CRLs) and is dependency-free, but its own docs disqualify it as a *default* for a security product today: non-constant-time AES-GCM (the most common suite servers pick), unblinded RSA, no zeroization, no audit. A reasonable posture: rustls+aws-lc-rs (or ring for size) as default, cameleer-tls as an opt-in `std-only` feature, and route "shared hardware" users to ChaCha20 if cameleer-tls is enabled.
- Certificate pinning is achievable in either stack via a custom verifier; `tls-server-end-point` channel binding needs access to the leaf certificate's DER and signature-algorithm OID from the TLS stack — confirm both rustls and any in-house stack expose this before committing to SCRAM-PLUS.

### Gaps
- No independent (non-ISRG) 2025/2026 rustls-vs-OpenSSL benchmark was found; all headline numbers come from the project's own benchmark harness (code is public).
- No measured handshake or throughput numbers for `cameleer-tls` exist anywhere found; nor a statement of its default trust-root behaviour (a `RootStore` type and a "system trust store" comment exist; defaults unconfirmed).
- `--ssl-mode` client default for MySQL (`PREFERRED`) and `VERIFY_IDENTITY` semantics were not on the fetched page; believed to be in the "Configuring MySQL to Use Encrypted Connections" chapter.
- MariaDB TLS 1.3 support specifics were not researched (MariaDB links against OpenSSL/wolfSSL/GnuTLS; not verified this session).

## Q3. CVE history of existing drivers and the design rule each implies

### Takeaway
The record splits into four recurring classes: (1) **client-side parameter inlining** (pgJDBC CVE-2024-1597, pgx CVE-2024-27289 — the `-` + placeholder → `--` comment bug; psycopg/libpq CVE-2006-2314 and CVE-2025-1094 — escaping fails under non-UTF-8 or invalid multibyte input); (2) **length-prefix integer overflow** letting one message become many (sqlx RUSTSEC-2024-0363, pgx CVE-2024-27304); (3) **connection-string-driven class loading / deserialisation / file reads** (pgJDBC CVE-2022-21724, Connector/J CVE-2017-3523/2023-21971/2023-22102, MySQL `LOAD DATA LOCAL` rogue-server attacks incl. 2026 MariaDB Connector/J CVEs); (4) **driver-built SQL with unescaped identifiers** (pgJDBC CVE-2022-31197). Each maps to one design rule below.

### Cited Findings

**Class 1 — client-side literal inlining**
- CVE-2024-1597 (pgJDBC, GHSA-24rp-q3w6-vc56, published 2024-02-21, CVSS 10.0, credit Paul Gerste/Sonar): only with non-default `preferQueryMode=simple`; "When a numeric placeholder directly follows a minus sign, the negated value becomes a `--` comment marker" that swallows the opening quote of a later string placeholder; a newline in the string then lands unescaped. Needs: numeric placeholder preceded by `-`, a string placeholder on the same line, both user-controlled. Fix: all inlined parameters wrapped as literals e.g. `-('-1'::int4)`. Fixed 42.2.28, 42.3.9, 42.4.4, 42.5.5, 42.6.1, 42.7.2. [project][checked 2026-11-09] — [GHSA-24rp-q3w6-vc56](https://github.com/pgjdbc/pgjdbc/security/advisories/GHSA-24rp-q3w6-vc56)
- CVE-2024-27289 (pgx Go, GHSA-m7wr-2xf7-cm9p): same bug class — non-default simple protocol, numeric placeholder preceded by minus, string placeholder on the same line; fixed 4.18.2; CVSS 8.1. **Class 4 — driver-generated SQL**

[project][checked 2026-11-09] — [GHSA-r38f-c4h4-hqq2](https://github.com/pgjdbc/pgjdbc/security/advisories/GHSA-r38f-c4h4-hqq2)

### Inferences (design rules)
1. **Never inline parameters client-side by default.** If a "simple/text protocol" mode exists for pipelining or proxies, wrap every inlined literal in a typed cast with explicit parentheses (pgJDBC's `-('-1'::int4)` fix) and reject or escape newlines/`--`/`/*` inside the generated text; add a regression test for `-?` followed by `?` on the same line.
2. **Escaping must be encoding-aware and fail closed.** Validate client-encoding bytes before quoting; refuse to quote invalid multibyte sequences (CVE-2025-1094); prefer `''` over `\'`; on PostgreSQL emit `E''` or standard_conforming_strings-aware output; where possible force the session to UTF-8 and reject SJIS/BIG5/GBK/GB18030/UHC in literal-inlining paths.
3. **Checked length arithmetic everywhere.** All protocol length prefixes (PG `i32`, MySQL 3-byte packet length with 16 MiB continuation, TDS packet/stream lengths) go through `try_from`/`checked_add` and a configurable `max_message_size`; never `as i32`/`as u32`; `clippy::cast_possible_truncation` as `deny` in codec crates; fuzz the *encoder* as well as the decoder (both sqlx and pgx bugs were on the encode side).
4. **No code loading or type instantiation from connection strings.** Plugins (auth, TLS verifier, socket factory) are Rust trait objects supplied by the application via a builder, never resolved from a URL string. Unknown connection-string keys are errors, not ignored. Treat database-name/user fields as untrusted when they come from end users (OpenRefine vector).
5. **Server-initiated client actions are opt-in per statement.** `LOAD DATA LOCAL` upload only if the *application* requested it for *that* statement and the filename matches what it asked for (MariaDB's 2026 fix direction); never deserialize server-sent bytes into executable/typed objects beyond declared column types; cap BLOB/row sizes.
6. **Driver-built SQL must quote identifiers.** Any metadata/refresh/`RETURNING`-synthesis path uses the driver's identifier quoter (`"..."` with doubled quotes, `` ` `` for MySQL, `[]`/`""` for TDS) — tested with identifiers containing `;`, quotes, newlines and `--`.
7. **Credential hygiene.** Tokens of ≥1 KB must survive the password path (RDS); passwords/tokens go in a `Secret<String>`-style wrapper with redacted `Debug`, zeroized on drop (a gap `cameleer-tls` admits for itself), and are never logged at any level.

### Gaps
- No MySQL Connector/J CVE in 2024–2025 with public root cause was found; Oracle CPUs do not publish technical detail.
- The CVE-2025-59250 root cause is undisclosed; only the CWE-20 classification and fix PR numbers are public.
- Whether Postgres.js or DuckDB clients were affected by the Gerste 4 GiB class was not confirmed from the talk (pgx and sqlx were).
- No published CVE was found that is specifically a DNS-rebinding attack on a database driver; the connection-string injection evidence comes from the OpenRefine/Connector-J LOCAL INFILE family.

## Q4. Injection-proof design: binding, statement splitting, identifier escaping, encodings, overflow checks, size limits, fuzzing, Miri/sanitizers, unsafe policy, supply chain

### Takeaway
The evidence-backed baseline is: extended/binary protocol with server-side binding as the only default; checked integer arithmetic on all lengths; cargo-fuzz (libFuzzer, nightly, x86-64/AArch64 Unix only) or proptest harnesses on every decoder *and* encoder; Miri plus ASan runs the way diesel does; and cargo-vet/cargo-deny/cargo-audit in CI. No existing Rust driver CI found runs fuzzing or Miri except diesel.

### Cited Findings
- pgJDBC default `preferQueryMode=extended` "always use bind/execute messages"; the simple-mode CVE class (Q3) exists only when that default is overridden. [project][checked 2026-11-09] — [pgJDBC docs](https://jdbc.postgresql.org/documentation/use/)
- RUSTSEC-2024-0363 mitigation text: "validate untrusted input and reject values over 4 GiB, or any input that could encode to a string longer than 4 GiB"; web backends should "consider adding some middleware that limits the size of request bodies by default". [third party][checked 2026-11-09] — [RUSTSEC-2024-0363](https://rustsec.org/advisories/RUSTSEC-2024-0363.html)
- `cargo-fuzz` is "a `cargo` subcommand for fuzzing with `libFuzzer`"; "needs a nightly compiler since it uses some unstable command-line flags"; "only works on x86-64 and Aarch64, and only on Unix-like operating systems (not Windows)"; requires a C++11 compiler; commands `init, add, run, fmt, tmin, cmin, coverage`. [project][checked 2026-11-09] — [rust-fuzz/cargo-fuzz](https://github.com/rust-fuzz/cargo-fuzz). The Rust Fuzz Book documents two tools, `afl.rs` and `cargo-fuzz`, with chapters on structure-aware fuzzing, coverage, Windows, and CI. [project][checked 2026-11-09] — [rust-fuzz book](https://rust-fuzz.github.io/book/introduction.html)
- Existing Rust protocol fuzz examples are mostly proptest-based: `pg-wired` `tests/protocol_fuzz.rs` feeds random bytes to `parse_message` and checks for panics, unknown tags, truncated bodies, bad length fields; `qail-pg` has a wire proptest expecting rejection of buffers shorter than the header and of declared lengths exceeding actual bytes; `spg-server` hand-rolled a harness because "cargo fuzz requires nightly + libFuzzer". [project][checked 2026-11-09] — [pg-wired protocol_fuzz.rs](https://docs.rs/crate/pg-wired/0.4.0/source/tests/protocol_fuzz.rs), [qail-pg wire_proptest.rs](https://docs.rs/crate/qail-pg/latest/source/tests/wire_proptest.rs), [spg-server e2e_fuzz.rs](https://docs.rs/crate/spg-server/7.8.0/source/tests/e2e_fuzz.rs)
- Diesel CI runs: AddressSanitizer for the sqlite-bundled, postgres-bundled (under Valgrind-enabled Linux) and mysql-bundled builds; nightly **Miri** on the default target and on big-endian `s390x`, plus a native-library SQLite Miri run; `cargo xtask semver-checks`; a `riscv32imac-unknown-none-elf` no-std SQLite build and `wasm32-unknown-unknown` tests. [project][checked 2026-11-09] — [diesel ci.yml](https://raw.githubusercontent.com/diesel-rs/diesel/master/.github/workflows/ci.yml)
- sqlx CI has "No docs build, Miri, fuzzing, or proptest jobs"; rust-postgres CI has none either (see Q11 matrices). [project][checked 2026-11-09] — [sqlx.yml](https://raw.githubusercontent.com/launchbadge/sqlx/main/.github/workflows/sqlx.yml), [rust-postgres ci.yml](https://raw.githubusercontent.com/sfackler/rust-postgres/master/.github/workflows/ci.yml)
- `cargo-vet` "helps projects confirm that third-party Rust dependencies were audited by a trusted entity"; supports sharing audits between projects, relative (diff) audits, and deferred audits via an exemptions list; under active development. [project (Mozilla)][checked 2026-11-09] — [cargo-vet book](https://mozilla.github.io/cargo-vet/)
- RustSec advisory DB (source of `cargo audit` data) carries the sqlx advisory as RUSTSEC-2024-0363 and is cross-listed on OSV. [third party][checked 2026-11-09] — [rustsec.org](https://rustsec.org/advisories/RUSTSEC-2024-0363.html), [OSV](https://osv.dev/vulnerability/RUSTSEC-2024-0363)

### Inferences
- Statement splitting (multi-statement strings) should be *disabled* by default in the extended protocol (PostgreSQL's Parse rejects multiple statements anyway); if a text/batch mode is provided it needs a real tokenizer that understands dollar-quoting, `E''`, nested `/* */`, and MySQL `DELIMITER`, and is itself fuzzed.
- A per-crate policy of `#![forbid(unsafe_code)]` on all protocol/codec crates is realistic (none of the parsing needs unsafe); an `unsafe` budget should be confined to FFI crates (SQLite, SSPI/GSSAPI, SChannel) and to any in-house crypto, each with `// SAFETY:` comments and Miri coverage — diesel shows Miri on big-endian is practical in CI.
- Because cargo-fuzz is Unix-only, run libFuzzer targets on Linux x86-64/AArch64 CI and keep a `proptest` fallback (`cargo test`) so Windows/macOS still exercise the same corpora; store crash corpora in the repo as regression tests.
- Supply chain: `cargo-deny` (licences, bans, duplicate versions, advisories), `cargo-audit` (RustSec), and `cargo-vet` with imported Mozilla/Google audits cover complementary ground; a near-zero-dependency driver makes `cargo vet` tractable.

### Gaps
- No public example of a libFuzzer harness in a mainstream Rust DB driver (sqlx, tokio-postgres, mysql_async, tiberius) was found.
- No measured data on Miri run-time cost for a protocol codec test suite.
- No documented `unsafe` count for sqlx/tokio-postgres/tiberius was found (cargo-geiger output not located).

## Q5. Measured techniques for small Rust binaries and the realistic footprint of a database driver stack

### Takeaway
Hard numbers exist only for the hello-world floor (51 KB → 30 KB → 8 KB with nightly `build-std`, `panic=immediate-abort`, `no_main`) and for anecdotal dependency trimming (reqwest native-tls→rustls ~4 MB, regex ~1 MB, tokio feature-trim ~100 KB); no public cargo-bloat table for sqlx or tokio-postgres was found. Comparable data points: Alpine's statically built `sqlx` CLI (postgres+mysql+sqlite+rustls) installs at 3.3 MiB, and the std-only Cameleer runtime claims 5.8 MB for an entire integration engine.

### Cited Findings
- min-sized-rust measured steps (macOS x86_64, nightly): `build-std` + `optimize_for_size` → **51 KB stripped**; + `panic=immediate-abort` → **30 KB**; `no_main` with careful libstd → **8 KB**; `no_std + no_main + libc` → "around 8KB". Unmeasured but listed: `strip=true` (Rust ≥1.59), `opt-level="z"` (≥1.28; `"s"` sometimes smaller), `lto=true`, `codegen-units=1` (release default 16), `panic="abort"` (≥1.10), `-Zlocation-detail=none`, `-Zfmt-debug=none` (nightly), UPX "50–70 %" claim. Debug builds "30% or more larger". `prefer-dynamic` rejected (no stable ABI). [third party][checked 2026-11-09] — [johnthagen/min-sized-rust](https://github.com/johnthagen/min-sized-rust)
- Real-world trim (CLI with clap/reqwest/tokio/regex, posted 2025-11-09): 11 MB → ~10 MB with `lto=true, strip=true, opt-level=3, codegen-units=1, panic="abort"` → **4.5 MB** after feature trimming; per-change savings: reqwest native-tls→rustls-tls "~4MB (the biggest win)", regex Unicode off ~1 MB, easy-archive ~1 MB, clap 100–200 KB, tokio limited to `rt-multi-thread`+`macros` ~100 KB; "about 80% of the binary came from about 20% of dependencies". [third party][checked 2026-11-09] — [dev.to/ahaoboy](https://dev.to/ahaoboy/i-shrunk-my-rust-binary-from-11mb-to-45mb-with-bloaty-metafile-1n7i)
- Counter-example: AerynOS `boulder` shrank from 15.2 MiB to 13.1 MiB by switching reqwest *from* rustls *to* native-tls because it links the **system** OpenSSL dynamically. [third party][checked 2026-11-09] — [AerynOS/os-tools PR 283](https://github-users.yhajoa.workers.dev/AerynOS/os-tools/pull/283)
- On Android, native-tls "ends up compiling openssl ... and statically linking it", producing much larger binaries than on Apple where a system TLS lib is linkable. [third party][checked 2026-11-09] — [users.rust-lang.org thread](https://users.rust-lang.org/t/android-targets-having-significantly-larger-text-size/56832)
- Alpine Linux `sqlx` (sqlx-cli) package v3.22 x86_64: **1.8 MiB download, 3.3 MiB installed** (musl static; stripping status not stated). [third party][checked 2026-11-09] — [pkgs.alpinelinux.org sqlx](https://pkgs.alpinelinux.org/package/v3.22/community/x86_64/sqlx)
- Cameleer (std-only, ~230 components) claims a **5.8 MB** binary with only the `core` feature; "~10 MB RAM"; startup 3 ms (README) vs 10 ms (About). [project][checked 2026-11-09] — [github.com/pmsudhi/cameleer](https://github.com/pmsudhi/cameleer)
- Tokio MSRV is 1.85 (releases ≥1.54); MSRV policy "at least 6 months" and changes only in minor releases; LTS lines 1.51.x (to March 2027) and 1.53.x (to September 2027). [project][checked 2026-11-09] — [tokio README](https://raw.githubusercontent.com/tokio-rs/tokio/master/README.md)
- `abi_stable` 0.11.3 (dated 2026-10-17 on docs.rs): Rust-to-Rust FFI for libraries loaded at startup with load-time type-layout checking, `#[sabi_trait]` ffi-safe trait objects, `StableAbi` derive, `RVec` etc., `LIB_HEADER` versioning, prefix types for ABI-compatible field additions; MSRV 1.61. No code-size or runtime-check cost stated. [project][checked 2026-11-09] — [docs.rs abi_stable](https://docs.rs/abi_stable/latest/abi_stable/)
- `stabby`: "stable ABI for Rust with compact sum types"; its `IStable` trait is "similar to abi_stable::Stable" but represents layout incl. niches via associated types; generates ABI-stable vtables; warns a Rust 1.78 change may hurt trait-object performance on non-nightly; recent docs.rs versions in the 70s with at least one failed docs build. [project][checked 2026-11-09] — [docs.rs stabby](https://docs.rs/stabby/latest/stabby/)

### Inferences
- A size budget should be stated per configuration, e.g. (a) single driver, blocking std I/O, rustls-ring, `opt-level="z"`, LTO fat, cgu=1, panic=abort, strip — target low single-digit MB on glibc; (b) same with all five drivers; (c) musl static. The only hard external anchor is sqlx-cli's 3.3 MiB installed (three drivers + CLI + rustls), so a well-trimmed driver library *below* that is plausible but must be measured in-repo with `cargo bloat --release --crates` since no public table exists.
- Expected big-ticket items from the trimming reports: TLS stack (rustls+aws-lc-rs vs ring; vendored OpenSSL is the worst case), `regex` (avoid entirely in a driver), `chrono`/`time` (feature-gate), `serde` (feature-gate JSON types; hand-written codecs for the wire protocol), and tokio (use `rt` + `net` + `io-util` only, or offer a blocking `std::net` backend).
- `panic=abort` is attractive for size but changes pool semantics (a panic in one connection task kills the process); offer it as a profile recommendation, not a library default.
- Dynamic driver loading via C ABI/`abi_stable`/`stabby` buys per-driver download size at the cost of a runtime layout check, loss of cross-crate inlining and LTO, and `unsafe` at the boundary; for a library whose stated goal is minimal size and `forbid(unsafe_code)`, static linking with Cargo features per driver is the lower-risk default, with an optional C-ABI plugin surface for third-party drivers.

### Gaps
- **No public cargo-bloat table or stripped hello-world size for tokio-postgres, sqlx, mysql_async, tiberius or rusqlite (bundled) was found** — this must be measured in-house (the brief forbids running cargo on downloaded code, so it belongs in the project's own CI).
- No public `cargo tree` dependency counts for sqlx-all-drivers vs tokio-postgres vs rusqlite; only lib.rs reverse-dependency counts (rusqlite used by 992 crates, sqlx-core by 1,248) which measure popularity not footprint. [third party][checked 2026-11-09] — [lib.rs rusqlite rev](https://www.lib.rs/crates/rusqlite/rev), [lib.rs sqlx-core rev](https://lib.rs/crates/sqlx-core/rev)
- No compile-time measurements for sqlx vs tokio-postgres found beyond a forum remark that sqlx's compile-time query checking "may have a severe impact on compile times". [third party][checked 2026-11-09] — [users.rust-lang.org](https://users.rust-lang.org/t/which-one-to-use-postgres-vs-sqlx/63680)
- No measured cost of monomorphisation vs trait objects ("polymorphisation") for database drivers specifically; no head-to-head abi_stable vs stabby benchmark.
- No measured tokio vs smol vs blocking-std binary-size delta; the only datum is the ~100 KB tokio feature-trim saving above.

## Q6. Test suites and conformance kits available for database drivers

### Takeaway
Reusable kits exist at three levels: API-level TCKs (R2DBC's `r2dbc-spi-test` 1.0.0.RELEASE is open and Maven-published; the JDBC TCK is Oracle-licensed and no public download was found), driver-agnostic lifecycle suites (ADBC's C++ `c/validation` and Go `validation.go`), and SQL-semantics corpora (sqllogictest, with a maintained Rust runner used by RisingWave/DataFusion/Databend). Microsoft's ODBC Test is open source; no unixODBC conformance suite was found.

### Cited Findings
- R2DBC: `io.r2dbc:r2dbc-spi-test` is the TCK; drivers add it test-scoped and subclass `TestKit`; Oracle R2DBC's build includes `*TestKit.java`; TCK accepted "query syntax customization" (#138) and renamed a column `VALUE`→`TEST_VALUE` (#258); Maven Central lists 1.0.0.RELEASE; R2DBC 1.0 GA (2022-04-25) shipped the SPI and TCK; Apache-2.0. [project][checked 2026-11-09] — [r2dbc-spi repo](https://github.com/r2dbc/r2dbc-spi), [Maven Central r2dbc-spi-test](https://central.sonatype.com/artifact/io.r2dbc/r2dbc-spi-test), [R2DBC 1.0 GA post](https://r2dbc.io/2022/04/25/r2dbc-1.0-goes-ga)
- JDBC TCK: Java TCKs are licensed under Oracle stand-alone TCK agreements that grant internal use for developing/testing, forbid "comparative compatibility" claims (e.g., "90% compatible"), and historically were free to qualified not-for-profits/individuals (JSR 101 page, old). No JDBC-specific download page surfaced. ### Inferences

- The JDBC TCK is not a practical dependency (licence, Java-only); the R2DBC TCK's test *list* is the best open specification of what a "complete" driver must do.
- ODBC parity testing can be done on Windows with Microsoft ODBC Test's Quick Test if an ODBC façade is ever shipped.

## Q7. Protocol-conformance techniques: differential testing, record/replay, property-based codec tests, type matrices

### Takeaway
The public evidence shows property-based round-trip tests on wire codecs (proptest) as the common Rust practice, ASan/Miri where C libraries are bundled (diesel), and SSL-client-auth containers (sqlx) for auth-path coverage; nothing found publicly implements replay-based differential testing against libpq/libmysqlclient/FreeTDS, so that would be novel for a Rust driver.

### Cited Findings
- proptest harnesses on PostgreSQL wire codecs in `pg-wired` (random bytes → `parse_message`; asserts no panic, handles unknown tags, truncated bodies, bad lengths) and `qail-pg` (encoder/decoder property tests; reject short headers and over-declared lengths). [project][checked 2026-11-09] — [pg-wired](https://docs.rs/crate/pg-wired/0.4.0/source/tests/protocol_fuzz.rs), [qail-pg](https://docs.rs/crate/qail-pg/latest/source/tests/wire_proptest.rs)
- sqlx runs separate `*_client_ssl` compose services (Postgres 13/17, MySQL 8, each MariaDB version) that replace the plain container on the same port, exercising client-certificate auth across `native-tls`, `rustls-aws-lc-rs`, `rustls-ring`. [project][checked 2026-11-09] — [sqlx.yml](https://raw.githubusercontent.com/launchbadge/sqlx/main/.github/workflows/sqlx.yml)
- rust-postgres tests against `docker.io/postgres:18` with `POSTGRES_PASSWORD` and an init script (`docker/sql_setup.sh`); no SSL/SCRAM settings in the compose file itself. [project][checked 2026-11-09] — [rust-postgres docker-compose.yml](https://raw.githubusercontent.com/sfackler/rust-postgres/master/docker-compose.yml)
- diesel: `diesel_compile_tests` (trybuild-style), `cargo xtask semver-checks`, Miri on big-endian `s390x`, ASan on bundled C libraries. [project][checked 2026-11-09] — [diesel ci.yml](https://raw.githubusercontent.com/diesel-rs/diesel/master/.github/workflows/ci.yml)
- RFC 5929's hash-selection rule (SHA-256 for MD5/SHA-1-signed certs, else the cert's own hash) is a concrete conformance case for channel-binding tests. [third party][checked 2026-11-09] — [RFC 5929](https://www.rfc-editor.org/rfc/rfc5929.html)

### Inferences
- Round-trip laws to encode as proptest properties: `decode(encode(v)) == v` for every SQL type × NULL × extreme values (i16/i32/i64 bounds, NaN/±Inf, max-precision NUMERIC, dates at 4713 BC / 294276 AD, `infinity`, 1 µs timestamps, time zones incl. half-hour offsets); `encode(v).len() == size_hint(v)` (the sqlx advisory explicitly flags `size_hint` lies); and "any byte string either decodes or returns `Err` without panic".
- Differential testing: capture libpq/libmysqlclient/FreeTDS traffic with a TCP proxy for a fixed script, then replay server bytes to the Rust decoder and compare decoded rows to the reference client's output; conversely replay Rust client bytes to a real server. Record/replay also gives deterministic offline CI for auth flows (SCRAM nonces must be injectable).
- Big-endian (s390x via Miri or QEMU) and 32-bit targets catch endianness and `usize` truncation bugs in length handling — directly relevant to the 4 GiB class.

### Gaps
- No public record/replay proxy or differential-testing harness against libpq/libmysqlclient/FreeTDS for a Rust driver was found.
- No published "type-mapping matrix" test artefact from sqlx/tokio-postgres/tiberius was located (their tests exist in-repo but were not enumerated).

## Q8. Cross-platform CI, MUSL, ARM64 and MSRV policy as practised by comparable Rust drivers

### Takeaway
Only diesel runs the full OS×arch matrix (Ubuntu x86-64 and ARM64, macOS 26, Windows 2025); sqlx and rust-postgres are Linux-only; tiberius adds Windows (SQL 2019, SSPI via `winauth`) and macOS (SQL 2022 in colima). MSRVs in late 2026 cluster at 1.85–1.88 (tokio 1.85, rust-postgres pins 1.85.0, tiberius 1.88, diesel 1.88, rustls-platform-verifier 1.85).

### Cited Findings
