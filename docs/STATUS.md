## Decisions already made

- The project is a standalone repository named karez, not a fork of tokio-rs/rdbc.
- Licence: Apache-2.0.
- Architecture option D in the plan: new sans-io protocol crates, a pipelined connection,
  Arrow-layout chunks with a row view, a standards-shaped API, and ADBC, ODBC and JDBC exports.
- On single-row queries the target is parity with the fastest Rust client; the large-margin
  claims are for the bulk and columnar path only.
- `cameleer-tls` is an opt-in TLS backend only, until it is audited and has a hardware AES path.
- Oracle is out of 1.0 pending a legal review.

## Decisions of 2026-11-13 (owner)

- **TLS:** an opt-in cargo feature backed by the `rustls` crate; the core stays dependency-free. **Built 2026-11-13** ([design/tls-decision.md](design/tls-decision.md) stands in for the issue AGENTS.md asks for; no issue was opened). Verified on 14.25, 16.15 and 17.12. Over `karez-rt` too. `execute_many` over 64 KiB works on a blocking TLS connection since 2026-11-19 (sent in windows, each read before the next).
- **Async (`karez-rt`):** a small design with no async runtime (std-only I/O threads and channels over the sans-io crates), informed by what the simoom project learnt. The simoom session answered: thread per connection with sans-io crates suits a database client, and a pump thread only helps from two requests in flight (see [research/simoom-io-learnings.md](research/simoom-io-learnings.md), second-hand and unchecked). The design is in [design/karez-rt.md](design/karez-rt.md); steps 0 to 4 are built (section 13 of it lists the gaps), step 5 (benchmarks) is not.
- **Replay:** only commands never written to a dead connection move to a new one; a written command is never resent automatically.
- **Slow streams:** a stream leases its connection; other commands wait in a bounded queue. No automatic second connection.
- **Audit:** ~~plan and fund an external audit before 1.0~~ **Changed 2026-11-16 by the owner: no paid audit.** Assurance comes from tests, fuzzing (30 CPU-days without a new crash, plan M8), `cargo audit`, `cargo deny`, review of every `unsafe` block in the ODBC FFI crate and public review. This is a lower assurance than a paid audit for an ODBC driver that BI tools would load; the risk is recorded in plan section 9.
- **Names:** reserve `karez` and `karez-*` on crates.io, PyPI and npm now, as minimal placeholders. **crates.io done 2026-11-16** (`karez`, `karez-chunk`, `karez-proto-pg`, `karez-pg`, `karez-rt`, version 0.0.1, no code; the owner told me to publish them with the existing cargo login). **npm and PyPI not done**: there is no login on this machine (`npm whoami` fails, no PyPI token); the packages are built and checked in `packaging/placeholders/`, and need the owner to log in. Planned names beyond these five (`karez-odbc`, `karez-adbc`, `karez-jdbc`, ...) are not reserved: crates.io forbids squatting, so reserve each when it has code.
- **PostgreSQL versions:** the real-server suite passes on 13.23, 14.25, 15.20, 16.16, 17.11 and 18.7 (plain on all six; TLS on all six too; `tests/docker/compose.yaml` has a profile for each; 2026-11-19). The partitioned scan needs 14 or later and the tests check its refusal on 13.

## Milestone 1 (started 2026-11-18)

The owner moved the project from Milestone 0 to Milestone 1 on 2026-11-18 and chose to start with the core API and the fuzz and differential harnesses. The plan, refined against the code, is [design/m1-plan.md](design/m1-plan.md). Step 1 is done: SQLSTATE class and a transient flag on errors, and a std-only mutation fuzzer for every server-to-client parser (400,000 mutated streams per target in release mode, no panic; not coverage-guided). Step 1b is done: the owner decided on 2026-11-18 to extract the pool now, so `karez-pool` is a driver-neutral crate (a `Manager` trait and a first-come-first-served `Pool`) and `karez-pg`'s `Pool` is a thin wrapper over it with the same API (m1-plan.md section 3). The two large-batch tests that failed on Windows were not a library bug: the WSL localhost relay stalls on large two-way transfers (a plain echo server does too), and all 47 real-server tests pass on Windows through `tests/docker/windows-test.ps1` (tests/docker/README.md, "Windows"). Step 2 is done: multi-host URLs, `target_session_attrs` and `load_balance_hosts` (m1-plan.md step 2; tested against a real primary and standby on PostgreSQL 16, 2026-11-19). Step 3 is built (2026-11-19): `numeric(p,s)` as `Decimal128`, `interval` and `time` as native columns, binary parameters for them and for arrays, with the per-type decisions in m1-plan.md; step 4, the differential harness, is built for the 15 native types (`crates/karez-pg/tests/differential.rs`; the server judges edge, random and array values on PostgreSQL 14, 16 and 17; see m1-plan.md step 4), so step 3's exit holds for them. Step 5 is built (2026-11-19): server-side cursors (`Connection::portal`, `fetch`, `close_portal`, so a cursor can be half read while the connection runs other statements in the same transaction) and ADBC-shaped catalog metadata as flat chunks (`conn.metadata()`), with the schemas compared field by field with ADBC 1.1.0 (m1-plan.md step 5). The gaps left by step 5 were closed the same day: ADBC `GetInfo` and the statistics calls (flat results, with new `UInt32` and `UInt64` chunk columns), the remaining `xdbc_*` fields that PostgreSQL can answer, a borrow-free `PortalCursor`, and portals in `karez-rt`. Step 6 is built (2026-11-19): `conn.pipeline()` and `conn.batch(&stmt)` in the blocking API (one `Sync` per group, per-statement results with `Error::Skipped` after a failure, atomic batches), with a local one-connection report of the point select pipelined and unpipelined (perf-program.md section 21; it is not the plan's S2 gate). Step 7 is built (2026-11-19) except Windows SSPI: SCRAM-SHA-256-PLUS (`tls-server-end-point`, the only binding PostgreSQL has), OAUTHBEARER with a token callback and discovery, and Kerberos (GSSAPI) on Unix in the new `karez-gss` crate (12 `unsafe` blocks with a written argument, [design/gss-safety.md](design/gss-safety.md)); each against a real server (a SHA-384 certificate on PostgreSQL 18, a validator module on PostgreSQL 18, a KDC with PostgreSQL 16). Client certificates (`sslcert`, `sslkey`) and `sslnegotiation=direct` were added the same day (tested against PostgreSQL 17). Step 8 is built (2026-11-19): seven coverage-guided libFuzzer targets in `fuzz/` (frame, message, row, SCRAM, OAuth, certificate and URL parsers), a seed corpus, `fuzz/run.sh` and a weekly workflow; a first run of 89.7 million executions in 28 CPU-minutes found no crash (far below the plan's 30 CPU-days, so it shows the harness works, not that the parsers are safe; m1-plan.md step 8). The Kerberos tests also pass under AddressSanitizer with LeakSanitizer ([design/gss-safety.md](design/gss-safety.md)). Step 9, the exit measurements, was run in part on 2026-11-19 (the owner's eighth spend exception: two shared-CPU droplets because `c-4` was unavailable, 77 minutes, about $0.18; [bench/results/2026-11-19-exit/REPORT.md](../bench/results/2026-11-19-exit/REPORT.md)): S6 COPY of 10,000,000 rows is **0.89x of PgBulkInsert** in rows per second (karez at 0.66x its CPU), so the plan's 1.5x gate is **not met on that droplet class and not decided** (the server was the likely limit; it needs a rerun on `c-4`); TLS bulk reads were measured for nine clients (TLS costs every client 3% to 36% of its S4 rate); the open-loop S1 to S3 and S8 over TLS found no result on shared droplets and are not measured. Step 9 was rerun on `c-4` droplets in `nyc1` the same day (the owner's ninth spend exception, about $0.83; [bench/results/2026-11-19-exit-c4/REPORT.md](../bench/results/2026-11-19-exit-c4/REPORT.md)) with the new binary COPY (`Connection::copy_in_binary`, tested on PostgreSQL 13 to 18): **S6 is 1.36x PgBulkInsert plain and 1.43x over TLS, so the plan's 1.5x gate is still not met** (karez 899,596 rows/s, 0.16x the CPU; the server's single insert backend is the probable limit), and the open-loop S1 to S3 over TLS are level with the best clients. The run found two defects: **`karez-pool` collapsed under 512 workers on a pool of 32** (S8: 10,000 requests a second against 42,000 for libpq's pool; **fixed the same day**: a release woke every waiter, now only the front one; 512 threads on 32 connections went from 1,150 to 49,258 gets/s on a mock pool, and the bench adapter now serves 32,000 requests a second locally where it served none above 8,000; remeasured on `c-4` in `sfo2` on 2026-11-20: 31,040 requests a second plain and 30,100 over TLS inside the 2 ms bound, against 38,000 and 31,871 for libpq; [bench/results/2026-11-20-recheck-c4/REPORT.md](../bench/results/2026-11-20-recheck-c4/REPORT.md)) and **the chunk path over TLS was 44% slower than plain on the droplets** (S4; looked into locally on 2026-11-20: it does not reproduce, TLS costs the chunk path 10% to 20% there, the same as the row view; the droplet result is unexplained; a second `c-4` run on 2026-11-20 did not reproduce it either: the chunk path over TLS was 19% slower than plain, like the row view, on a slow and unstable pair). Next: karez over TLS was slower than tokio-postgres on the `sfo2` pair (open, not a finding); a quieter pair would settle it when there is a run to spend on, and decide what to do with the S6 gate (the owner's call). The open PostgreSQL items were closed on 2026-11-20 (m1-plan.md step 10): a command dropped before it was written never reaches the server, `LISTEN` on an idle shared connection (`Options::keep_listening`), an idle-connection probe and pool validation so a failover does not cost the first query an error, a failover test with open connections (primary killed, standby promoted), and SCRAM SASLprep as the optional feature `saslprep` ([design/saslprep-decision.md](design/saslprep-decision.md)). Open and not mine to close: Windows SSPI (no Windows realm to test against), the logo and social image, the two paywalled standards texts, making the repository public, the npm and PyPI placeholders (need the owner's logins), and the parked faster-network test.
